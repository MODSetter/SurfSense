# ADR 0082: The license server delivers job packs itself, from a private repository's releases, to a license whose jobs list them

- **Status:** Accepted
- **Date:** 2026-11-03
- **Source:** [ADR 0067 L18–30](https://github.com/MODSetter/SurfSense/blob/51c593551cc8efae53473708eb2a03671a91e1c7/docs/adr/0067-b2b-jobs-ship-as-paid-plugins.md#L18-L30), [bundles README L132–166](https://github.com/MODSetter/SurfSense/blob/51c593551cc8efae53473708eb2a03671a91e1c7/docs/proposals/plugins/bundles/README.md#L132-L166), [ADR 0080](0080-surfsense-sells-one-business-license-priced-per-person.md) L14 and L31, maintainer decisions, 3 Nov 2026 (no permalink)

## Context

ADR 0067 makes SurfSense's B2B jobs paid plugins that the license server delivers only to a valid license, never in the installer or the public plugin list, and says what holds is delivery and terms, since a check in the app can be stripped. [ADR 0080](0080-surfsense-sells-one-business-license-priced-per-person.md) makes Business, or its 14-day trial, the license that unlocks them, and lists the license server's route for paid bundles among what must exist before Business is sold. A job ships as a job pack: signed data, no code (`surfsense-job-pack/1`, a manifest listing every file's sha256 and signed with SurfSense's Ed25519 pack key; about 20 KB for the security questionnaire), which the app installs from a folder or a zip and checks before every read. Until now it installs only from a path on the computer.

What constrains where the server gets a pack and how it hands it over:

- The content is private, under a closed license, and kept in a private repository beside third-party evaluation workbooks that may never be redistributed. The backend's image is built from the public repository, so a pack cannot be baked into it, and a credential that reads the private repository would read the workbooks too.
- The app follows no redirect, and its consent is per host: `api.surfsense.com` is one row, today labelled for renewal ([ADR 0027](0027-egress-consent-per-host.md), [ADR 0060](0060-one-consent-question-per-user-action.md)). A pack from a second host would need a second question and would show that host every licensed computer's address.
- The app unlocks a job from `metadata.jobs` in its license file, offline. Keygen also holds the jobs as entitlements on the Business policies, which every license on a policy inherits, and the two can disagree.
- An older app refuses a whole pack that names a runner it does not have, and an app installs every job of a pack it accepts.
- Packs are signed by hand on the maintainer's machine, where the key is. The private repository has no CI, and the server has no database and usually runs as one copy without Redis.

## Decision

- **One route.** `POST /api/v1/license/job-pack` on the license server, with `{key, entitlement, installed_version?, runners}` in the body, answers the newest pack the license may run as a zip, `204` when the app already has it, or a refusal with a code ([contract 6](../contracts/06-job-pack-delivery.md)). The key is in the body, never logged or echoed, and limited per address and per key, as the refresh is.
- **Who gets a pack.** Keygen validates the key, unscoped, and must answer `VALID`; `EXPIRED` is refused, since a Business license's expiry already includes the 30 days after the year paid for. The license's `metadata.jobs` must list the job, and every job in the pack it gets: every job of a paid pack carries an entitlement, so no license receives a job it did not buy. `metadata.jobs` is the one source of truth on both sides, so the server never delivers a pack the app would keep locked; Keygen's policy entitlements are not read.
- **Which pack.** The highest version among the packs the license covers whose every runner the app listed. A pack that needs something new, a runner or a later schema, names a runner only the apps that have it list, so an older app is never sent a pack it would refuse.
- **Where packs come from.** GitHub releases of a private repository that holds only releases, named by the maintainer (for example `MODSetter/surfsense-job-packs`), read with a fine-grained token limited to that repository with read access to its contents (`JOB_PACKS_GITHUB_REPO`, `JOB_PACKS_GITHUB_TOKEN`). Each release is tagged `<id>-v<version>` and carries one asset, `<id>-<version>.zip`. A folder of the same zips (`JOB_PACKS_DIR`) sits behind the same interface for tests, local runs and emergencies, and is read instead when set.
- **One id per job, versions only grow.** Once a pack with a job for an entitlement is published, every later pack with a job for it keeps the same id and a higher version; a published version never changes.
- **Checked before it is served.** The server checks every zip by contract 6's zip rules: safe names at the root, at most 50 MB and 1,000 members, the manifest's schema, every listed file's sha256 and no unlisted file, and the signatures against the same compiled pack keys the app trusts. It also requires `access: paid`, an entitlement on every job, and names matching the release. A zip that fails, or cannot be read at all, is never served and is logged; the versions that passed keep being served. Contract 6 holds the app to the same zip rules, the same way on every system, with two leniencies: a file imported by hand may wrap the pack in one folder, which the server never serves, and one signature line that verifies is enough, where the server needs every line (below).
- **More than one signature.** `job-pack.sig` holds one signature a line. An app accepts a pack when any line verifies with its keys; the server requires every line to verify with its own. A key rotation signs with the old and the new key until the apps that trust only the old one have aged out.
- **Served from memory, never redirected.** The server lists the releases at most every 10 minutes, downloads each release once, keeps the verified bytes in memory and the last good list when GitHub fails, and answers with the bytes itself.
- **Published by one script.** `tools/publish_pack.py` in the private pack repository checks a sealed, signed pack with the app's checks and the server's, refuses a version that is not higher or a second id for an entitlement, zips it and runs `gh release create`.
- **The app** reaches only the license server for a pack, under the one consent row for `api.surfsense.com`, now "License server", whose question names renewal and pack downloads. It asks on the user's action (adding or replacing a license, Check for renewal, Download, Check for updates) and checks without asking at startup, daily, and once a run that held a check back ends, while a license with jobs is active, a trial's included. It installs only a newer pack whose manifest carries the job and no job the license lacks, never while a run of that pack is going, and keeps the installed pack when anything fails.
- **Not Keygen artifacts.** Keygen can host release files and gate them by entitlement, but CE has no object store configured (it needs R2, S3 or MinIO on its web and worker containers), publishing would go through an instance with no public address, an artifact answers with a redirect to the store that the server would follow and proxy anyway, and its gate reads policy entitlements rather than `metadata.jobs`: all for a 20 KB file.
- **Not a volume upload.** Copying zips into a volume on the production host needs host access for every release, the same volume on every copy of the backend, and leaves no history or review. It stays only as the `JOB_PACKS_DIR` emergency path.
- **Not a CDN or a GitHub redirect.** The app follows no redirect and its consent names `api.surfsense.com` alone; a second host would need its own question and would see every licensed computer, and a signed link outlives the check that issued it.
- **Not the public repository.** Neither its tree, which is Apache-2.0 and public, nor its releases, which every installed app reads as an app update ([bundles README L166](https://github.com/MODSetter/SurfSense/blob/51c593551cc8efae53473708eb2a03671a91e1c7/docs/proposals/plugins/bundles/README.md#L166)).
- **Not email.** A mailed pack reaches no app by itself, every update would be a mail, an attachment leaves SurfSense's hands the moment it is forwarded, mail filters strip zips, and a lapsed license's old mail keeps its pack. Mail keeps carrying the license file alone; support sends a pack file by hand only to a computer that cannot reach the server.

## Consequences

- A license with jobs gets them without the user fetching anything: adding the license asks once for the license server, and the daily check keeps the pack current. A computer that cannot reach the server imports a pack file that SurfSense support sends by hand.
- GitHub is a runtime dependency for new versions and cold starts. The last good packs stay served while it fails; a copy that starts while it fails answers `503` until GitHub answers or `JOB_PACKS_DIR` is set.
- The token expires and has to be replaced before it does; a refused token is logged on every try and leaves the packs already in memory served.
- The pack public keys live in two places, the app's `PACK_PUBLIC_KEYS_HEX` and the server's, and change together; each side's tests pin the shipped key and refuse the test keys. A rotation first releases apps that trust the new key, then signs with both keys, then drops the old one from the server. A leaked key is dropped from the server's list at once, which stops delivery of the packs it signed, and from the next app release.
- Each copy of the backend reads the store on its own, so a new version reaches apps within 10 minutes of publishing.
- `cryptography` becomes a direct dependency of the backend.
- A job added to `jobs.py` reaches only licenses whose `metadata.jobs` lists it, and a license converted or issued by hand must have `jobs` written to get a pack.
- The license server learns, per request, the key, one job code, the installed version, the app's runners and the computer's address, and keeps none of it beyond the rate limit's counts, dropped an hour after the last request, and its access log; Keygen notes when the license was last validated.
- Running it, from making the repository and the token to publishing a pack and replacing the token, is the [license portal's](../architecture/license/portal.md#job-packs) runbook.

## Where the code stands

- Built on the server ([portal](../architecture/license/portal.md#post-licensejob-pack)): the route, the GitHub and folder stores, the checks and the cache.
- Not built: the app's side (delivery, the hand import, the Jobs screen and the consent copy), which comes in the app's own change; until it lands nothing calls the route. `tools/publish_pack.py` lives in the private pack repository, and no pack has been published yet.
