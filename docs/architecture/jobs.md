# Jobs

A job pack adds B2B jobs to the app: a security questionnaire filled in from the firm's own policies is the first. The pack is data only (prompts, header words, answer rules and the job's skill), so installing one starts no process; the app's runner reads it, asks the selected model one question at a time, checks every answer against the sources, and writes a revised copy of the requester's workbook. The user's file is never written. SurfSense's B2B jobs are paid plugins ([ADR 0067](../adr/0067-b2b-jobs-ship-as-paid-plugins.md)): their packs live outside this repository, while everything here is the shared job infrastructure, free under Apache-2.0.

**Code:** [`surfsense_local/backend/modules/jobs/`](../../surfsense_local/backend/modules/jobs/), [`worker/studio/job_run/`](../../surfsense_local/backend/worker/studio/job_run/), [`tool_endpoint/run_job.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/run_job.py), the Excel engine's inspection ([studio](studio.md#revised-copies)), and the eval harness in [`scripts/job_eval/`](../../surfsense_local/backend/scripts/job_eval/).
**Decisions:** [ADR 0067](../adr/0067-b2b-jobs-ship-as-paid-plugins.md). The design it follows is [08](../../plans/community-local/seo/08-b2b-artifact-jobs.md#what-the-agent-needs-one-engine-for-many-jobs), items 1 to 5 and 11.

## The parts

| Part | Where | Does |
|---|---|---|
| Packs | `jobs/packs/` | the manifest, the sha256 of every file, installing from a folder or a `.zip`, the paid check, the skills a pack brings |
| Runner | `jobs/workbook_rows/` | `workbook-rows/1`: finding a workbook's questions, one schema-held call per question, the checks, the engine's operations |
| Evidence | `jobs/evidence/` | the sources cut into numbered passages; all of them when they fit, else per question the best by BM25 and by the app's embedder in turn, with the passages the pack's standing queries find |
| Provenance | `jobs/provenance/quote_check.py` | whether a quote is in a source, word for word |
| Runs | `jobs/runs/`, `worker/studio/job_run/` | a run as a revised copy whose operations the Studio worker works out, and confirming its suggested answers |
| Settings | `jobs/settings/` | the firm's choices for each job, kept across its runs: the settings its pack declares and the checker model |
| Routes | `jobs/router.py` | the installed packs, install and remove, a job's settings, start and read a run, confirm its suggestions |
| Agent | `tool_endpoint/run_job.py`, `tool_endpoint/confirm_job.py`, `opencode_config.py` | the job tools and the pack's skill in an Agentic chat |
| Evals | `scripts/run_job_eval.py`, `scripts/job_eval/` | the same runner on a pack's real-data cases, per model |

## Packs

A pack is a folder with `job-pack.json` ([`manifest.py`](../../surfsense_local/backend/modules/jobs/packs/manifest.py)): schema `surfsense-job-pack/1`, an id and a three-number version, its name, publisher and description, `access` `free` or `paid`, its licence file, its jobs, and `files`, every other file of the pack with its sha256. A job names its key, its runner (only `workbook-rows/1` today; another refuses the pack with `NEEDS_NEWER_APP`), its config file, optionally its skill folder, named `surfsense-job-<key>` and holding a `SKILL.md`, and, in a paid pack, its `entitlement`, the licence code that unlocks it (the questionnaire's: `JOB_QUESTIONNAIRE`). Paths are relative, in forward slashes, and never leave the pack.

**Signing** ([`signature.py`](../../surfsense_local/backend/modules/jobs/packs/signature.py)). Beside the manifest sits `job-pack.sig`, SurfSense's Ed25519 signature over the manifest, which lists every file's sha256, so it covers the whole pack. What is signed is the manifest as canonical JSON, after a domain prefix, so a checkout that changes its line endings or a reindent leaves the signature good while any name, version, file or sha256 breaks it. The app compiles in the pack key's public halves, newest first, as it does the registry's, so a release can trust an old and a new key while the key is rotated; it never reads a key from config or disk. A pack that is unsigned (`PACK_NOT_SIGNED`) or whose signature no listed key makes (`PACK_BAD_SIGNATURE`) is refused on install and left out on every read. Sealing changes the manifest, so a pack is sealed first and signed after, by the script beside the packs' own content, which holds the private key's place; the private key lives in the maintainer's hands or as that repository's secret, never in a repository. Tests sign their packs with a fixed test key, which the app trusts only while they run.

Installing ([`install.py`](../../surfsense_local/backend/modules/jobs/packs/install.py)) copies the folder, or extracts the `.zip` (plain files at safe paths only, at most 50 MB, one top folder holding the manifest allowed), into a scratch folder under `<data>/job-packs/`, checks it, then replaces whatever version of the same pack was installed: one version per pack. The check refuses a pack its signature does not cover (below), a file the manifest does not list, a listed file missing, and a file whose sha256 differs ([`integrity.py`](../../surfsense_local/backend/modules/jobs/packs/integrity.py)). Every read of the installed packs checks them again, so a pack changed on disk is left out with a log line. `scripts/job_pack.py seal` writes a folder's `files`, and `zip` packs it with its signature. A dev build installs the folders or `.zip` files named in `SURFSENSE_LOCAL_JOB_PACKS` (separated as `PATH` is) when the API starts; a refused one is logged and the API starts anyway ([`dev_packs.py`](../../surfsense_local/backend/modules/jobs/packs/dev_packs.py)).

**Access** ([`access.py`](../../surfsense_local/backend/modules/jobs/packs/access.py)). One function decides for every run and every listing of a job. A free pack's jobs run. A paid pack's job runs on a licence that is active (its signature good, its expiry ahead, the clock trusted) and whose `metadata.jobs`, comma-separated entitlement codes, holds the job's own code: every Business licence of ADR 0079 carries it, and so does the Business trial, a `trial` plan, so the plan itself decides nothing. A licence's expiry is the end of the period paid for plus 30 days, which is the grace already, so the app adds none. An expired licence, a clock behind one already seen, a licence without the code and a job that names none are each refused with their own sentence. `SURFSENSE_LOCAL_JOBS_UNLOCKED=1` in the API's environment runs paid jobs without a licence, for development. As every check in the app, this is honesty, not enforcement: what holds is that the licence server delivers paid packs only to a valid licence, and the pack's own terms. `GET /job-packs` says per job whether it may run, and why not.

## The runner

A job's config ([`config.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/config.py)) is the job's content: its answers (for the questionnaire Yes, No, N/A and Needs review), which of them need a quote, the dropdown spellings each may take, the one fallback answer; the header words that name question, answer, comment, evidence and context columns; placeholder texts a requester leaves in an empty cell; sheets that are the requester's own (an evaluator's tab); the system, question and repair prompts; how a comment, an evidence cell and a free-text answer read; and the names of the two sheets it adds.

1. **The questions** ([`layout.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/layout.py)). On each visible sheet the runner reads every cell as it shows, a formula by its stored result, since HECVAT shows each question through a formula over a hidden sheet. A table is the first header row within 40 rows naming a question and an answer column, whose question column averages at least 20 characters below it; failing that, the column with the most dropdown cells is the answers and the longest text to its left the questions, with comment and evidence columns taken from the nearest row above that labels the answer column. Within a table, a row whose answer cell has no dropdown, where most do, is a section heading unless it asks (a question mark, a verb asking for prose, or the requester's placeholder). A hidden row, a locked answer cell and an answer already given are skipped, each kept with its reason for the exceptions sheet. A context cell merged down several rows, as CAIQ's control title and specification are, is read for every row it covers, so a question that points back to "the exercise" or "these processes" carries what it points to; before, only the merge's first row did. CAIQ v4.1 gives 283 questions this way and HECVAT 4.1.6 317 across its eight vendor tabs.
2. **The passages** ([`passages.py`](../../surfsense_local/backend/modules/jobs/evidence/passages.py), [`retrieval.py`](../../surfsense_local/backend/modules/jobs/evidence/retrieval.py)). Each source's text, as ingest made it, is cut into passages of about 900 characters, never across a Markdown heading, each knowing its lines and section. Every question sees all of them, in the same order, when their characters fit half the model's window at three characters a token and at most 120,000 characters; otherwise it sees its best few for the question alone (the pack says how many; the questionnaire's pack shows 24), since a row's own columns, such as CAIQ's control text, repeat the same words on every row. The best are BM25's ranking and, where the app has an embedder, the embedder's ranking by cosine, taken in turn: meaning finds a "third party" policy for a "supply chain" question, which no shared word does, and words find an exact term the embedder misses. Over the CAIQ and HECVAT dev rows the deciding passage was among the 24 shown for 34 of 48 gold Yes answers by BM25 alone and 36 with both in turn; chat's own blend of cosine and term coverage found 32. A passage is indexed with its document's title as well as its section and words, since a policy is named for what it covers: without the title, half of CAIQ's gold Yes answers never saw their deciding passage. A pack may also name standing queries, whose best passages (one each unless the pack says more, by the same ranking; a second pick was often off the subject) every question is shown, first and under the pack's label when it gives one: the questionnaire's ask how the firm approves and reviews its policies and how it publishes them, which a question about any one policy needs in words it never uses.
3. **The call** ([`ask.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/ask.py)). One request per question: the job's system prompt, then the passages, then the question with its row's context and the values the cell takes, under a JSON schema of `quotes` (each a `passage` number and a `quote`), `answer` (the job's answers as an enum), `comment` and `confidence`, with no null-able types and no bounds, which not every structured-output engine takes. An answer may rest on several quotes because a question's parts often sit in different documents, such as a policy and the rule that every policy is reviewed each year; the runner keeps the first few (the pack says how many; the questionnaire's allows 3). The passages come first so a provider that reuses a prompt's start reads them once. A reply that holds no usable answer is asked again once; an empty one (a call that failed after its tries) is asked again in a single user turn, since an API refuses an empty assistant turn.
4. **The checks** ([`decide.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/decide.py)). Each quote counts only when it, at least 15 characters, is in a source word for word ([`quote_check.py`](../../surfsense_local/backend/modules/jobs/provenance/quote_check.py)): as a reader sees the text, case, punctuation, quotes and Markdown marks fold away and a link reads as its text, but digits and words do not, so "72 hours" never matches "24 hours" and "not encrypted" never matches "encrypted"; parts joined by "..." must each be in the same source, all within 300 words of each other, and the words a "..." skips may hold no negation, since "data is ... encrypted at rest" would otherwise be found in "data is not encrypted at rest". A quote found nowhere is dropped, and an answer that needs a quote stands only on the quotes that are found. When none is, it is sent back once with the reason and the source sentence closest to it, if one shares most of its words and the same negations and numbers, which small models paraphrase for about one quoted answer in ten; still none, the answer becomes the fallback, with `QUOTE_NOT_FOUND` and what the model said. So no "Yes" is ever written without a passage that holds its quote. A pack may also ask an answer that fell back to look once more, part by part, before it goes to a person: only a doubtful one, which quotes something, is unsure or says nothing of what is open, since those were the gold's Yes most often; a new answer then goes through the same checks, and the pack may limit what that look may answer (the questionnaire's: Yes only, since all 12 No and N/A that second looks wrote in the v0.2.0 dev sweeps were wrong). A pack may name answers that need a statement (the questionnaire's: No and N/A): such a draft whose found quote speaks of a scope or a provider, or whose comment says the documents are silent, goes to a person with `NO_STATEMENT`, by the pack's own patterns, read against the quote's words so a hyphen or a line break changes nothing, since a scope, a provider or silence does not say the firm does not do something and no check can make it say so; a refused No or N/A asked again onto such a quote keeps its refusal; on Qwen3.8-27B's dev runs this cut wrong answers from 3.7 to 1.7 a pass. An answer the pack lets the job suggest (the questionnaire's: N/A), resting on a provider or a scope but not on silence, goes on to the check instead, and one the check supports is left to a person as a suggestion, with `SUGGESTED` and its checked quotes in the comment cell ("Suggested: N/A. Evidence: ..."), so the person confirms it in one step ([Runs](#runs)). A firm setting the pack names (the questionnaire's "Treat provider-run controls as N/A", off unless the firm turns it on) writes a checked answer whose quote names a provider running the thing for the firm, by the pack's provider pattern, instead of suggesting it; one resting on a scope stays a suggestion either way. For the answers the pack names (the questionnaire's: Yes, No and N/A), the found quotes then get a second call, on the firm's checker model when it chose one and else on the answering model, under its own schema, asking whether together they are evidence for the answer: at least one about the very control the question asks after, and saying the firm does it; for a quote whose parts "..." joins, the check is shown the source in full from its first part to its last ([`verify.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/verify.py)). Refused, the model is told why, and which of its quotes were not found, and asked once more, to keep the answer on better evidence or give way; refused again, kept on quotes that are in no source, or a check that cannot be read, makes the answer the fallback with `NOT_SUPPORTED` and the reason, the row keeping the refused quotes for the person who looks, and a different answer on that turn makes it the fallback with `ANSWER_SWITCHED`, since nothing has checked the new answer (every No that Qwen gave on that turn was refused). Each row keeps a trace of every answer and check on the way, which the eval records. The quote check proves a passage exists; this checks it is evidence, which models often get wrong by quoting a related control, even when the answer itself is right. The answer is then written as the cell's own dropdown spelling (N/A as `NA` on CAIQ), or left blank when the list has none, with `NOT_ON_DROPDOWN`; a free-text cell gets the answer in words.
5. **The operations** ([`operations.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/operations.py)). Each answer in its own cell, a comment and the source in the requester's comment and evidence columns where they are empty, then `add_sheet` twice: "SurfSense answers", one row per quote (one for a question with none) with its answer, what the cell got, confidence, source, section, line, quote and comment, and "SurfSense exceptions", one row per reason a person should look. A name already taken gets " (2)".

The runner is pure over files and a model ([`fill.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/fill.py)), so Studio's worker and the eval harness run the same code. Questions run four at a time on a remote model and one at a time on a local one; a stop is read on the run's own thread, before each question and every 2 seconds while they run, and never interrupts a call. A checker that cannot be loaded beside the answering model, which is the case for two local models since the local runtime holds one at a time, takes turns with it: up to 128 questions are under way at once, a call to the model out of turn waits, and the turn passes once the model in turn has no call running or waiting and no question is still working towards one, so a run loads each model a few times instead of twice a question. While questions wait for their turn, a stop makes every call not yet made raise, and so does a run that fails. A question whose call fails outright goes to a person with `CALL_FAILED` and the reason, and the others are answered; failures on every question, or on three and more than a tenth of them, fail the run instead, since then the connection is at fault. Passage vectors are kept in memory by embedder (its id and weights' sha256) and exact text, at most 8,192 of them ([`vectors.py`](../../surfsense_local/backend/modules/jobs/evidence/vectors.py)), so the worker's next run over an unchanged library, and an eval's next run, embed no passage again, while each question's query and the standing queries still are; the first run embeds them all, about 25 seconds for 318 passages on a laptop's CPU.

## Runs

`POST /workspaces/{id}/job-runs` with `job`, `document_id` (the workbook) and `source_ids` starts one ([`start.py`](../../surfsense_local/backend/modules/jobs/runs/start.py)): the job must be installed and allowed, the workbook a `.xlsx` or `.xlsm` source, and every source ready with text. The run is v1 of a revised copy of the workbook with no operations and a `job_run` record (pack, version, job, sources, the firm's settings and checker as they are when it starts, `report: null`) ([`record.py`](../../surfsense_local/backend/modules/jobs/runs/record.py)), so a change to the settings applies from the next run. Refused, the route answers `409` with the reason.

In the Studio worker the revise path first works the run out ([`pipeline.py`](../../surfsense_local/backend/worker/studio/job_run/pipeline.py)): it loads the pack's config, reads the workbook's original and the sources' text, resolves the selected text model and its window, the run's checker (through the API's model route, as the selected model is reached) and the active index's embedder (none before onboarding chooses one, and passages are then found by their words alone), commits, runs the runner with the run's settings, then stores the operations in `revision` and the report in `job_run` (the model and checker, the settings, seconds, counts, how many answers are suggested, the names of the two added sheets, each answer with its source and quote, its suggestion with what confirming it writes and where its lines sit on the added sheets, the exceptions), and the engine applies them as for any revised copy. Two different local models take turns, as above. A reply may run to 8,192 tokens, since a remote connection does not turn a thinking model's thinking off. An endpoint that refuses the JSON schema, as Anthropic's OpenAI-compatible API does without `strict`, is asked by prompt from then on, with the schema written into the system message, and the reply is read leniently (quotes given as bare strings take their passage numbers from a list beside them): held to no schema and shown none, Sonnet gave bare strings and lost 5 of 15 answers on the live WISP case. A call that stalls or fails for a moment (a stream quiet for 30 seconds, a dropped connection, the provider's 408, 429 or 5xx) is tried twice more, after the pause a rate limit's Retry-After asks for (up to a minute) or a short one; still failing, its row goes to a person as unreadable, so one stall among a workbook's hundreds of calls no longer fails the run, while an error trying again cannot fix, such as a refused key, still does. A cancel stops the run between questions. A run that fails is not retried. `GET /workspaces/{id}/job-runs/{artifact}` reads its status, error and report.

`POST /workspaces/{id}/job-runs/{artifact}/confirm` confirms a finished run's suggested answers, those at the `cells` it names (sheet and answer cell) or every one not yet confirmed ([`confirm.py`](../../surfsense_local/backend/modules/jobs/runs/confirm.py)). It makes the next version of the run's revised copy, which writes each as the job would have written it, in the answer cell's own dropdown spelling with the comment and evidence an answer gets, and marks its lines on both added sheets confirmed. The run records which version confirmed each suggestion, once that version is made, and does not offer it again while that version stands; one whose version failed, was cancelled or was deleted is offered again. A suggestion the answer cell cannot hold is never offered, and the report counts only the ones a step confirms. While a version of the copy is still being made, the route answers `409`, as an edit would.

`GET /job-packs/jobs/{job}/settings` reads the firm's settings for a job: every setting the pack declares, with its label, description, default and value, and the checker, a text model by provider, name and connection, or none to check on the answering model. `PUT` sets them whole, a setting left out going to its default; a setting the job does not declare, a value that is not true or false, and a checker that is neither the local runtime nor a connection that exists are refused with `422` ([`service.py`](../../surfsense_local/backend/modules/jobs/settings/service.py)). They are kept in `job_settings`, one row per job, and a setting a newer pack no longer declares is dropped when a run starts.

`GET /job-packs` lists the installed packs with whether each may run and why not; `POST /job-packs/install` takes a folder or `.zip` path on this computer; `DELETE /job-packs/{id}` removes one.

## The agent

While a pack is installed the job tool is listed, naming the pack's jobs ([`run_job.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/run_job.py), [agent](agent.md#surfsensess-tools)), and each job's skill folder joins opencode's `skills`, allowed by name ([agent](agent.md#the-configuration)). The skill tells the agent to call `surfsense_run_job` with the ticked workbook and policies, never to answer the questions itself, and to report the counts and the exceptions. The tool starts the run and waits up to 150 seconds; a longer run says it will appear in Studio. Its reply says how many answers are suggested; once the user has checked them and asks, `surfsense_confirm_job_suggestions`, listed while a pack is installed, confirms them, all or by cell, and waits for the version as the job tool waits for a run ([`confirm_job.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/confirm_job.py)).

## Evals

`scripts/run_job_eval.py run --pack <pack> --eval <eval folder> --model anthropic:<id> --model openrouter:<id>` runs a pack's cases, each a `case.json` naming a real workbook, real source files and a gold file, with each file's source and licence ([`cases.py`](../../surfsense_local/backend/scripts/job_eval/cases.py)). Sources are read as ingest reads them: Word through the app's own reader, PDF from its text layer, Markdown and text as they are. Each run writes its filled workbook and a record: questions found, accuracy over the gold cells (an answer the cell could not hold counts as the blank the requester gets, and a gold answer the cell cannot hold expects that blank), false Yes (a Yes the gold does not support), Yes without a quote, dropdown violations, integrity problems (a sheet moved, a cell changed outside the answers, a dropdown, protection, merge, macro, chart or medium changed, or a file openpyxl cannot open), tokens, dollars and seconds, and per row its trace and the passages it was shown ([`score.py`](../../surfsense_local/backend/scripts/job_eval/score.py), [`workbook_integrity.py`](../../surfsense_local/backend/scripts/job_eval/workbook_integrity.py)); `report` rolls them up per case and model. `--checker <model>` makes the second checks on another model and `--setting key=true` turns on one of the job's firm settings. A suggestion scores as the person's blank it is, and one its cell can hold is counted apart, as right when it is the gold answer, a confirmation one step away, or else wrong; and since the provider setting changes only how a checked provider answer ends, written or suggested, never a call, each run is also scored as if the setting were the other way round. Claude runs through Anthropic's Messages API with structured outputs, open models through OpenRouter with the schema required of the provider; neither falls back to another model, and Opus and Fable are refused. `--reasoning off` turns an open model's thinking off, which the app's connection does not. Passages are found with the app's bundled embedder, as on a fresh install, unless `--embedder none`. The cases and their gold live with the pack, outside this tree, and are built from real documents only. `tests/live/test_job_run_live.py` runs one case through the app itself.

## Known gaps

- The licence server does not deliver packs yet: a pack installs from a path on this computer.
- The licence module does not yet read a licence's `metadata.jobs`, so until it does, no licence unlocks a paid job, and paid jobs run only under the developer switch.
- No screen starts a run or lists packs: a run starts from the agent's tool or the route. Nor does one show a run's suggestions with a button to confirm them, or a job's settings: the routes and the agent's tools serve them.
- Scoping questions (HECVAT's REQU rows, which decide which tabs apply) are answered like any other question; nothing marks the tabs they rule out N/A.
- CAIQ's "SSRM Control Ownership" column and other required columns that are not an answer, comment or evidence column are left empty.
- An approved answer library is not built: past answers count only as another source the user ticks.
- A run's first embedding of a library is not kept across app restarts, and ingest's own chunk vectors are not reused, since a job cuts its passages differently.
- A checker on a second local model takes turns with the answering one, and each turn still loads a model, which costs a local run some minutes; with the local runtime holding one model at a time, there is no way to keep both loaded.
- A No that rests on a provider is never suggested, only an N/A: the gate sends it to a person with no answer to confirm.
- Claude connections reach the job through Anthropic's OpenAI-compatible API, which takes no structured schema without `strict` and no effort setting, while the eval calls the Messages API at low effort: the live tests are what measure the app's own path.
