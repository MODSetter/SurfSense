# Jobs

A job pack adds B2B jobs to the app: a security questionnaire filled in from the firm's own policies is the first. The pack is data only (prompts, header words, answer rules and the job's skill), so installing one starts no process; the app's runner reads it, asks the selected model one question at a time, checks every answer against the sources, and writes a revised copy of the requester's workbook. The user's file is never written. SurfSense's B2B jobs are paid plugins ([ADR 0067](../adr/0067-b2b-jobs-ship-as-paid-plugins.md)): their packs live outside this repository, while everything here is the shared job infrastructure, free under Apache-2.0. The packs reach the app from SurfSense's licence server, which sends a pack only to a licence whose `metadata.jobs` lists its jobs ([Delivery](#delivery)), and the Jobs screen lists the jobs a licence offers, runs one on a workbook and shows its progress, its answers and the suggestions left to confirm ([The Jobs screen](#the-jobs-screen)).

**Code:** [`surfsense_local/backend/modules/jobs/`](../../surfsense_local/backend/modules/jobs/), [`worker/studio/job_run/`](../../surfsense_local/backend/worker/studio/job_run/), [`tool_endpoint/run_job.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/run_job.py), the Excel engine's inspection ([studio](studio.md#revised-copies)), the eval harness in [`scripts/job_eval/`](../../surfsense_local/backend/scripts/job_eval/), and the screen in [`surfsense_local/frontend/src/features/jobs/`](../../surfsense_local/frontend/src/features/jobs/).
**Decisions:** [ADR 0067](../adr/0067-b2b-jobs-ship-as-paid-plugins.md); ADR 0080 for the licence that unlocks the jobs, a Business licence or its 14-day trial (on the `docs/business-license` branch); ADR 0082 and contract 6 for how the licence server delivers the packs. The design it follows is [08](../../plans/community-local/seo/08-b2b-artifact-jobs.md#what-the-agent-needs-one-engine-for-many-jobs), items 1 to 5 and 11.

## Packs

A pack is a folder with `job-pack.json` ([`manifest.py`](../../surfsense_local/backend/modules/jobs/packs/manifest.py)): schema `surfsense-job-pack/1`, an id and a version of three numbers of 1 to 9 ASCII digits each (`BAD_MANIFEST` otherwise), which goes back in every request as `installed_version`, its name, publisher and description, `access` `free` or `paid`, its licence file, its jobs, and `files`, every other file of the pack with its sha256. A job names its key, its runner (a name and a version in contract 6's form, such as `workbook-rows/1`, else `BAD_MANIFEST`; this app has only `workbook-rows/1`, and any other refuses the pack with `NEEDS_NEWER_APP`), its config file, optionally its skill folder, named `surfsense-job-<key>` and holding a `SKILL.md`, and, in a paid pack, its `entitlement`, the licence code that unlocks it (the questionnaire's: `JOB_QUESTIONNAIRE`). Paths are relative, in forward slashes, never leave the pack, and follow the zip's name rules below, a skill folder's included, so none ends in `/` (`BAD_PATH`).

**Signing** ([`signature.py`](../../surfsense_local/backend/modules/jobs/packs/signature.py)). Beside the manifest sits `job-pack.sig`, one to eight lines, each the base64 of an Ed25519 signature over the manifest, which lists every file's sha256, so each covers the whole pack. What is signed is the manifest as canonical JSON, after a domain prefix, so the manifest may be rewritten with other line endings or indents while any name, version, file or sha256 breaks the signature; the other files are checked by their exact bytes, so a pack's repository converts no line endings (the private one's `.gitattributes` keeps every file as it is). The manifest is read once, and the copy whose signature is checked is the copy used. The app compiles in the pack key's public halves, newest first, as it does the registry's, and accepts a pack when any one line verifies with any of them, so a rotation can sign with the old and the new key and both kinds of app install the pack; it never reads a key from config or disk. A pack that is unsigned (`PACK_NOT_SIGNED`), whose signature file is empty, holds more than eight lines or a line that is not 64 bytes of strict base64, or none of whose lines a listed key made (`PACK_BAD_SIGNATURE`) is refused on install and left out on every read. Sealing changes the manifest, so a pack is sealed first and signed after, by the script beside the packs' own content, which holds the private key's place; the private key lives in the maintainer's hands or as that repository's secret, never in a repository. Tests sign their packs with a fixed test key, which the app trusts only while they run. `tests/unit/jobs/test_job_pack_sample.py` installs contract 6's sample, the bytes the licence server's tests check, with the sample's key trusted beside the shipped ones, and finds it refused with the shipped keys alone (`PACK_BAD_SIGNATURE`); it skips only while contract 6 is not in this tree, and once contract 6 is, a sample missing beside it fails the test.

Installing ([`install.py`](../../surfsense_local/backend/modules/jobs/packs/install.py)) copies the folder, or extracts the `.zip`, into a scratch folder `.installing-*` under `<data>/job-packs/`, checks it, and only then puts it in place, one install at a time: dev packs, the path route, an import, a download and the app's own checks take one lock for the whole process, and removing a pack takes it too. A `.zip` is held to contract 6's rules on its own list of members, before anything is written and the same way on every system, whatever its file system would accept: at most 1,000 members, folder entries included, since no pack holds more (`NOT_A_PACK`), and 50 MB once extracted, folder entries' declared sizes counted (`PACK_TOO_LARGE`); each file stored or deflated and not encrypted, and a folder entry carrying nothing, its declared size 0 (`NOT_A_PACK`); none a symlink, no two names equal but for case, folder entries' included, no file named, whatever the case, as the folder of another member (a file `a` beside `a/b` or beside a folder entry `a/`), no folder spelled two ways that differ only in case, and every name, read as the zip stores it, a folder entry's final `/` aside, at most 255 bytes in UTF-8, relative, in forward slashes and in normal form, with no empty or dot part (`a//b`, `./a`, a lone `.`) and no NUL, and without `:`, `..`, a part ending in a dot or a space, a name Windows reserves, such as `CON`, `NUL`, `COM1` or `aux.txt`, a part ending in `~` and ASCII digits before its last dot, or at its end when it has none, as a Windows short name such as `REPORT~1.MD` does, which Windows could take for another file's short name, any of `<`, `>`, `"`, `|`, `?` and `*`, or a character below U+0020 (`BAD_PATH`). A name the rules pass that a disk still cannot hold as the zip has it, such as one too long for a file system that allows less than 255 bytes, is `BAD_PATH` too, not a disk failure; a disk that refuses the write, as a full one does, is a download's `not_written` and an import's `500 PACK_NOT_WRITTEN`. One top folder holding the manifest is still allowed, for a zip made by hand, and a file that cannot be read as a zip at all is `NOT_A_PACK`. The check refuses a pack its signature does not cover (Signing, above), a file the manifest does not list, a listed file missing, and a file whose sha256 differs ([`integrity.py`](../../surfsense_local/backend/modules/jobs/packs/integrity.py)). The caller's own rule then decides, before anything installed changes: a download's and an import's are under [Delivery](#delivery). The new version is renamed into `<id>/<version>/` before the old one leaves, so a reader always finds a version of the pack; every other version of its id is then moved to a `.replaced-*` folder and deleted, and one that cannot be moved is left for the next install, with the new one listed. The same signed pack installed again moves nothing. A different pack under a version already installed is refused with `PACK_VERSION_TAKEN`, except through the path route and dev packs, which replace it for a developer. Every read skips the scratch names, `.installing-*`, `.replaced-*`, `.download-*` and `.upload-*`, and each install sweeps the ones older than an hour, which a killed process leaves. Every read of the installed packs checks them again, manifest rules included, and lists the newest verified version of each id, so a pack changed on disk, or one a rule made stricter since refuses, is left out with a log line, and a version that vanishes mid-read has its id read once more. `scripts/job_pack.py seal` writes a folder's `files`, and `zip` packs it with its signature. A dev build installs the folders or `.zip` files named in `SURFSENSE_LOCAL_JOB_PACKS` (separated as `PATH` is) when the API starts; a refused one is logged and the API starts anyway ([`dev_packs.py`](../../surfsense_local/backend/modules/jobs/packs/dev_packs.py)).

**Access** ([`access.py`](../../surfsense_local/backend/modules/jobs/packs/access.py)). One function decides, when a run starts and again when the worker works it out, so a run retried in Studio is checked as well; `GET /job-packs` reports what it answers for each job, with its sentence and a `locked_code` the screen picks its words by: `none` with no licence, `not_included` for a licence without the job's code in any state, `expired`, `clock` for a clock behind one already seen, `no_entitlement` for a paid job that names no code, and null when the job may run. A pack's own code is its first job's, null while any of its jobs may run. The agent's job tools and skills are listed while a pack is installed, whatever it answers, and a run they start is checked like any other. A free pack's jobs run. A paid pack's job runs on a licence that is active (its signature good, its expiry ahead, the clock trusted) and whose `metadata.jobs`, comma-separated entitlement codes, holds the job's own code: every Business licence of ADR 0080 carries it, and so does the Business trial, a `trial` plan, so the plan itself decides nothing. A licence's expiry is the end of the period paid for plus 30 days, which is the grace already, so the app adds none. An expired licence, a clock behind one already seen, a licence without the code and a job that names none are each refused with their own sentence, and a licence without the code is never told to renew, since renewing it would not unlock the job. `SURFSENSE_LOCAL_JOBS_UNLOCKED=1` runs paid jobs without a licence, for development; it goes in the environment of the API and of the Studio worker, which checks again when it works a run out. As every check in the app, this is honesty, not enforcement: what holds is that the licence server delivers paid packs only to a valid licence, and the pack's own terms.

## Delivery

A licence's packs come from SurfSense's licence server, which answers each request with the newest pack of one job that the licence and this app may have, or with a refusal and its code (contract 6; why, ADR 0082). The app's side is [`packs/delivery/`](../../surfsense_local/backend/modules/jobs/packs/delivery/).

- **What is asked.** `deliver_packs()` (`deliver.py`) plans in one short session of its own: the installed packs, the licence's key, its state and its jobs. With no licence it stops at `license_none`, with one that is not `active` at `license_not_active`, and with one that lists no jobs at `license_no_jobs`, each before anything is sent. A licence code that contract 6's request does not take, anything but `^[A-Z][A-Z0-9_]{0,63}$`, which only a hand-issued licence can list, is never sent: it ends as `unknown_job`, logged at info. For each other code of the licence, or each code the call names, it sends `POST <licence server>/api/v1/license/job-pack` with `{key, entitlement, installed_version?, runners}` and `User-Agent: SurfSense` (`pack_request.py`): `installed_version` is the version of the newest installed pack with a job for that code, left out when there is none, and `runners` every runner this app ships, today `workbook-rows/1`. The key travels in the body, never in the URL or a log, and goes nowhere else for a pack: the app never asks Keygen or GitHub. A redirect is not followed, so a `3xx` is a failure; the request allows 10 seconds to connect and 60 per read. A `200` must be `application/zip`, and its body streams into a `.download-*` file under `<data>/job-packs/`, stopped past 50 MB; the `X-Job-Pack-*` headers are only logged, since the zip's own manifest decides.
- **Consent.** The licence server's host must be allowed first: `host:api.surfsense.com`, the row Settings › Network names License server, or a mirror's host when `SURFSENSE_LOCAL_LICENSE_SERVER_URL` names another ([licence in the app](license/app.md#renewal)). The refusal carries `purpose: "job_packs"`, which words the question for this errand ([egress](egress.md#asking-for-consent)). It is checked when some code the call asks for is in the licence and one a request may carry: for a person's request, `POST /job-packs/download`, even when a run holds every such code back, since the check made once the run ends is the app's own, which never asks and would find the host off; for the app's own checks, only when such a code is not held back, so one in which runs hold back every such code only records them for the follow-up. A call whose codes are all missing from the licence or not ones a request may carry asks nothing. Allowed, the check stamps the host's last call in Settings › Network only when a code is sent: a person's request that runs hold back entirely stamps nothing, and the check made once the run ends stamps the call it makes.
- **Outcomes.** One per code, in order (`outcomes.py`), each with a sentence and, for `installed`, `current`, `deferred` and `license_outdated`, the version installed now: `installed`; `current`, for a `204` or a pack no newer than the installed one; `deferred`, when a run of the pack is pending or processing, found before anything is sent or just before the swap (`PACK_IN_USE`, below), and the code is checked again once the run ends (`delivering_daily()`, below); it names the installed version it kept; for a job no installed pack has, the version a run of the job itself reads (its pack has failed its checks since the run began, as when a listed file changed on disk, so no listed pack has that version and no line shows on the Jobs screen or in Settings › License), or none when the run is of another of the pack's jobs, as when a newer version of a pack adds the job, and then its sentence says a run of another job in the same pack was under way; `job_not_included`, when the licence lists no such code, so nothing is sent, or for the server's `403 job_not_included`, whose own record of the licence's jobs lacks it; `pack_not_covered` for the server's `403 pack_not_covered`, when every pack with the job also holds a job the licence lacks; `license_not_valid` for any other `403`; `license_not_found` for a `404 license_not_found`; `license_outdated` when a downloaded pack holds a job this computer's licence file does not list (`PACK_NOT_INCLUDED` in `detail`, below); `needs_newer_app` for a `409 needs_newer_app`, or a pack naming a runner this app lacks; `unknown_job` for a `422 unknown_job`, or a licence code no request may carry, which is never sent; `rate_limited` for a `429`; `unavailable` for a `503`, a `3xx`, a `404` or `405` from a server without the route, a `200` of another type, a `422` whose `detail` is a list, which is the app's own bug and is logged by status and each error's `type` and `loc` alone, any other answer, no answer and a timeout; `refused` when the pack fails the app's checks or runs past 50 MB, its code in `detail`, such as `NOT_A_PACK`, `BAD_PATH`, `PACK_WRONG_JOB` or `PACK_TOO_LARGE`; and `not_written` when the disk refuses it, as a full one does, or the packs folder cannot be made, and the codes after it are still asked for. A refused or failed request never touches the installed pack, and nothing is retried in a loop: the next check or user action asks again.
- **Acceptance.** A downloaded zip installs through `install_pack()` with `accept_delivered()` (`acceptance.py`), and is deleted afterwards whatever happens. Its manifest must have a job for the code asked for (`PACK_WRONG_JOB`), every job's `entitlement` must be among the licence's jobs (`PACK_NOT_INCLUDED`, reported as `license_outdated` and logged at info: the server sends a pack only when its own record of the licence lists every job in it, so this computer's licence file is the older one, which Check for renewal replaces), its version must be newer than the newest installed pack, of any id, with a job for that code (`PACK_NOT_NEWER`, reported as `current`), and no run of the pack may be pending or processing (`PACK_IN_USE`, reported as `deferred`). That last check is read under the install lock, just before the swap, so a pack a run reads is never replaced: the code is checked again once the run ends.

Three triggers ask, and each install takes the lock above:

- `POST /job-packs/download`, with `{entitlements}` naming up to 32 codes or no body for every code of the licence (`delivery/router.py`): Download on the Jobs screen, Download and Check for updates in Settings › License, and the frontend's own call once a licence that is active and lists jobs is added or replaced, or a Check for renewal succeeds. It answers `200` `{outcomes, packs}` even when every outcome failed, `409` `license_none`, `license_not_active` or `license_no_jobs` with nothing sent, a `422` list for a code in the body that is not one, where a licence's own code that is not one ends as `unknown_job`, and `403 egress_disabled` with `destination`, `host`, `hosts` and `purpose: "job_packs"`, even when runs hold back every code it asks for (Consent, above), raised only after the planning session has committed, so a mirror's host stays recorded off for Settings › Network to list; the renderer's `request()` turns it into the consent question and retries once.
- `POST /job-packs/import`, a multipart upload of one `.zip` (`uploaded_pack.py`): the hand delivery for a computer that cannot reach the server, whose pack file SurfSense support sends. The upload is copied in 1 MB chunks into a `.upload-*` file under `<data>/job-packs/` and refused past 50 MB with `413 PACK_TOO_LARGE`, as is a zip whose members add up to more than 50 MB once extracted; one holding more than 1,000 members, folder entries included, is `422 NOT_A_PACK`, since no pack holds that many. `accept_imported()` refuses a version older than an installed one of the same id (`409 PACK_OLDER`) and a pack a run is using (`409 PACK_IN_USE`), committing that read before any file moves, and the install refuses a different pack at an installed version (`409 PACK_VERSION_TAKEN`), so the same signed pack, or a newer one, imports. Any other refusal is `422` with its code, `NOT_A_PACK` naming the file, `BAD_PATH` for a name the zip's rules refuse or this system cannot create and `BAD_MANIFEST` for a manifest the app does not take, such as a version part of ten digits, and a disk that refuses the write, as a full one does, is `500 PACK_NOT_WRITTEN`. It answers the listing, and sends nothing anywhere. It replaces the path route for people: `POST /job-packs/install` stays for developers and the live tests, installing any version and replacing one at the same version.
- `delivering_daily()` (`delivery_schedule.py`), the last task of the API's lifespan, after `install_dev_packs()`: a check at startup, then one every 24 hours whatever the outcome, through `deliver_if_due()` (`automatic_delivery.py`), which asks only while the licence is `active` and lists jobs, whatever its plan, so a trial's packs stay current too. It never raises a consent question: a host not allowed is logged as `egress_blocked` with the host, and nothing is sent ([ADR 0060](../adr/0060-one-consent-question-per-user-action.md)). A licence removed, ended or without jobs is logged at info as `license_none`, `license_not_active` or `license_no_jobs`, and each code's outcome is logged, `refused` and `not_written` as warnings and the rest, `license_outdated` among them, at info. The same loop follows up a check a run held back: `deliver_packs()` records each code it defers, whichever trigger asked, with the id of the pack whose run held it (`HELD_BACK`, `held_back.py`), and any other outcome for the code takes it out. While a code is recorded, the loop looks every `FOLLOW_UP_EVERY`, 60 seconds, reading only whether a run of that pack is still pending or processing, never hashing the installed packs, and a code recorded while it waits for the next day wakes it; once no run holds a code, `deliver_held_back()` takes it out and checks it once more through `deliver_if_due()`, logging `job packs checked again once their runs ended: <codes>`, then each outcome as above, so a code held back again is recorded again. Nothing runs more often than that, and a follow-up never moves the daily check. The record is in memory only: a restart begins with the startup check, which asks for every code anyway, and a run the last session left processing, which the Studio worker marks failed only once it starts, holds that check back by about a minute, not a day. It has the renewal check's shape ([licence in the app](license/app.md#the-daily-check)): a stopping event the loop ends on, 2 seconds' grace for a check under way, then a cancel, and every database stretch in a session of its own (`transact_fresh()` in `api/dependencies.py`), so no session is ever closed under a worker thread.

Removing a licence, or one that lapses, leaves its packs on disk: [Access](#packs) keeps their jobs locked until a licence lists their codes again.

## The runner

A job's config ([`config.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/config.py)) is the job's content: its answers (for the questionnaire Yes, No, N/A and Needs review), which of them need a quote, the dropdown spellings each may take, the one fallback answer; the header words that name question, answer, comment, evidence and context columns; placeholder texts a requester leaves in an empty cell; sheets that are the requester's own (an evaluator's tab); the system, question and repair prompts; how a comment, an evidence cell and a free-text answer read; and the names of the two sheets it adds.

1. **The questions** ([`layout.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/layout.py)). On each visible sheet the runner reads every cell as it shows, a formula by its stored result, since HECVAT shows each question through a formula over a hidden sheet. A table is the first header row within 40 rows naming a question and an answer column, whose question column averages at least 20 characters below it; failing that, the column with the most dropdown cells is the answers and the longest text to its left the questions, with comment and evidence columns taken from the nearest row above that labels the answer column. Within a table, a row whose answer cell has no dropdown, where most do, is a section heading unless it asks (a question mark, a verb asking for prose, or the requester's placeholder). A hidden row, a locked answer cell and an answer already given are skipped, each kept with its reason for the exceptions sheet. A context cell merged down several rows, as CAIQ's control title and specification are, is read for every row it covers, so a question that points back to "the exercise" or "these processes" carries what it points to; before, only the merge's first row did. CAIQ v4.1 gives 283 questions this way and HECVAT 4.1.6 317 across its eight vendor tabs.
2. **The passages** ([`passages.py`](../../surfsense_local/backend/modules/jobs/evidence/passages.py), [`retrieval.py`](../../surfsense_local/backend/modules/jobs/evidence/retrieval.py)). Each source's text, as ingest made it, is cut into passages of about 900 characters, never across a Markdown heading, each knowing its lines and section. Every question sees all of them, in the same order, when their characters fit half the model's window at three characters a token and at most 120,000 characters; otherwise it sees its best few for the question alone (the pack says how many; the questionnaire's pack shows 24), since a row's own columns, such as CAIQ's control text, repeat the same words on every row. The best are BM25's ranking and, where the app has an embedder, the embedder's ranking by cosine, taken in turn: meaning finds a "third party" policy for a "supply chain" question, which no shared word does, and words find an exact term the embedder misses. Over the CAIQ and HECVAT dev rows the deciding passage was among the 24 shown for 34 of 48 gold Yes answers by BM25 alone and 36 with both in turn; chat's own blend of cosine and term coverage found 32. A passage is indexed with its document's title as well as its section and words, since a policy is named for what it covers: without the title, half of CAIQ's gold Yes answers never saw their deciding passage. A pack may also name standing queries, whose best passages (one each unless the pack says more, by the same ranking; a second pick was often off the subject) every question is shown, first and under the pack's label when it gives one: the questionnaire's ask how the firm approves and reviews its policies and how it publishes them, which a question about any one policy needs in words it never uses.
3. **The call** ([`ask.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/ask.py)). One request per question: the job's system prompt, then the passages, then the question with its row's context and the values the cell takes, under a JSON schema of `quotes` (each a `passage` number and a `quote`), `answer` (the job's answers as an enum), `comment` and `confidence`, with no null-able types and no bounds, which not every structured-output engine takes. An answer may rest on several quotes because a question's parts often sit in different documents, such as a policy and the rule that every policy is reviewed each year; the runner keeps the first few (the pack says how many; the questionnaire's allows 3). The passages come first so a provider that reuses a prompt's start reads them once. A reply that holds no usable answer is asked again once; an empty one (a call that failed after its tries) is asked again in a single user turn, since an API refuses an empty assistant turn.
4. **The checks** ([`decide.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/decide.py)). Each quote counts only when it, at least 15 characters, is in a source word for word ([`quote_check.py`](../../surfsense_local/backend/modules/jobs/provenance/quote_check.py)): as a reader sees the text, case, punctuation, quotes and Markdown marks fold away and a link reads as its text, but digits and words do not, so "72 hours" never matches "24 hours" and "not encrypted" never matches "encrypted"; parts joined by "..." must each be in the same source, all within 300 words of each other, and the words a "..." skips may hold no negation, since "data is ... encrypted at rest" would otherwise be found in "data is not encrypted at rest". A quote found nowhere is dropped, and an answer that needs a quote stands only on the quotes that are found. When none is, it is sent back once with the reason and the source sentence closest to it, if one shares most of its words and the same negations and numbers, which small models paraphrase for about one quoted answer in ten; still none, the answer becomes the fallback, with `QUOTE_NOT_FOUND` and what the model said. So no "Yes" is ever written without a passage that holds its quote. A pack may also ask an answer that fell back to look once more, part by part, before it goes to a person: only a doubtful one, which quotes something, is unsure or says nothing of what is open, since those were the gold's Yes most often; a new answer then goes through the same checks, and the pack may limit what that look may answer (the questionnaire's: Yes only, since all 12 No and N/A that second looks wrote in the v0.2.0 dev sweeps were wrong). A pack may name answers that need a statement (the questionnaire's: No and N/A): such a draft whose found quote speaks of a scope or a provider, or whose comment says the documents are silent, goes to a person with `NO_STATEMENT`, by the pack's own patterns, read against the quote's words so a hyphen or a line break changes nothing, since a scope, a provider or silence does not say the firm does not do something and no check can make it say so; a refused No or N/A asked again onto such a quote keeps its refusal; on Qwen3.8-27B's dev runs this cut wrong answers from 3.7 to 1.7 a pass. An answer the pack lets the job suggest (the questionnaire's: N/A), resting on a provider or a scope but not on silence, goes on to a check instead: the gate's own, when the pack gives one (the questionnaire's does), so the main check keeps its wording for every other answer, since rewording it to accept a provider's N/A cost Haiku right Yes answers on rows that had nothing to do with N/A. One the check supports is left to a person as a suggestion, with `SUGGESTED` and its checked quotes in the comment cell ("Suggested: N/A. Evidence: ..."), so the person confirms it in one step ([Runs](#runs)). A firm setting the pack names (the questionnaire's "Treat provider-run controls as N/A", off unless the firm turns it on) writes a checked answer whose quote names a provider running the thing for the firm, by the pack's provider pattern, instead of suggesting it; one resting on a scope stays a suggestion either way. For the answers the pack names (the questionnaire's: Yes, No and N/A), the found quotes then get a second call, on the firm's checker model when it chose one and else on the answering model, under its own schema, asking whether together they are evidence for the answer: at least one about the very control the question asks after, and saying the firm does it; for a quote whose parts "..." joins, the check is shown the source in full from its first part to its last ([`verify.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/verify.py)). Refused, the model is told why, and which of its quotes were not found, and asked once more, to keep the answer on better evidence or give way; refused again, kept on quotes that are in no source, or a check that cannot be read, makes the answer the fallback with `NOT_SUPPORTED` and the reason, the row keeping the refused quotes for the person who looks, and a different answer on that turn makes it the fallback with `ANSWER_SWITCHED`, since nothing has checked the new answer (every No that Qwen gave on that turn was refused). Each row keeps a trace of every answer and check on the way, which the eval records. The quote check proves a passage exists; this checks it is evidence, which models often get wrong by quoting a related control, even when the answer itself is right. The answer is then written as the cell's own dropdown spelling (N/A as `NA` on CAIQ), or left blank when the list has none, with `NOT_ON_DROPDOWN`; a free-text cell gets the answer in words.
5. **The operations** ([`operations.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/operations.py)). Each answer in its own cell, a comment and the source in the requester's comment and evidence columns where they are empty, then `add_sheet` twice: "SurfSense answers", one row per quote (one for a question with none) with its answer, what the cell got, confidence, source, section, line, quote and comment, and "SurfSense exceptions", one row per reason a person should look. A name already taken gets " (2)".

The runner is pure over files and a model ([`fill.py`](../../surfsense_local/backend/modules/jobs/workbook_rows/fill.py)), so Studio's worker and the eval harness run the same code. Questions run four at a time on a remote model and one at a time on a local one; a stop is read on the run's own thread, before each question and every 2 seconds while they run, and never interrupts a call. A checker that cannot be loaded beside the answering model, which is the case for two local models since the local runtime holds one at a time, takes turns with it: up to 128 questions are under way at once, a call to the model out of turn waits, and the turn passes once the model in turn has no call running or waiting and no question is still working towards one, so a run loads each model a few times instead of twice a question. While questions wait for their turn, a stop makes every call not yet made raise, and so does a run that fails. A question whose call fails outright goes to a person with `CALL_FAILED` and the reason, and the others are answered; failures on every question, or on three and more than a tenth of them, fail the run instead, since then the connection is at fault. Passage vectors are kept in memory by embedder (its id and weights' sha256) and exact text, at most 8,192 of them ([`vectors.py`](../../surfsense_local/backend/modules/jobs/evidence/vectors.py)), so the worker's next run over an unchanged library, and an eval's next run, embed no passage again, while each question's query and the standing queries still are; the first run embeds them all, about 25 seconds for 318 passages on a laptop's CPU.

## Runs

The Jobs screen ([below](#the-jobs-screen)) or the agent's tool ([The agent](#the-agent)) starts one with `POST /workspaces/{id}/job-runs`, sending `job`, `document_id` (the workbook) and `source_ids` ([`start.py`](../../surfsense_local/backend/modules/jobs/runs/start.py)): the job must be installed and allowed, the workbook a `.xlsx` or `.xlsm` source, and every source ready with text. The run is v1 of a revised copy of the workbook with no operations and a `job_run` record (pack, version, job, sources, the firm's settings and checker as they are when it starts, `progress: null`, `report: null`) ([`record.py`](../../surfsense_local/backend/modules/jobs/runs/record.py)), so a change to the settings applies from the next run. Refused, the route answers `409` with the reason.

In the Studio worker the revise path first works the run out ([`pipeline.py`](../../surfsense_local/backend/worker/studio/job_run/pipeline.py)): it loads the pack's config, reads the workbook's original and the sources' text, resolves the selected text model and its window, the run's checker (through the API's model route, as the selected model is reached) and the active index's embedder (none before onboarding chooses one, and passages are then found by their words alone), commits, runs the runner with the run's settings, then stores the operations in `revision` and the report in `job_run` (the model and checker, the settings, seconds, counts, how many answers are suggested, the names of the two added sheets, each answer with its source and quote, its suggestion with what confirming it writes and where its lines sit on the added sheets, the exceptions), and the engine applies them as for any revised copy. Two different local models take turns, as above. A reply may run to 8,192 tokens, since a remote connection does not turn a thinking model's thinking off. An endpoint that refuses the JSON schema, as Anthropic's OpenAI-compatible API does without `strict`, is asked by prompt from then on, with the schema written into the system message, and the reply is read leniently (quotes given as bare strings take their passage numbers from a list beside them): held to no schema and shown none, Sonnet gave bare strings and lost 5 of 15 answers on the live WISP case. A call that stalls or fails for a moment (a stream quiet for 30 seconds, a dropped connection, the provider's 408, 429 or 5xx) is tried twice more, after the pause a rate limit's Retry-After asks for (up to a minute) or a short one; still failing, its row goes to a person as unreadable, so one stall among a workbook's hundreds of calls no longer fails the run, while an error trying again cannot fix, such as a refused key, still does. A cancel stops the run between questions. A run that fails is not retried. A workbook in which the runner finds no question fails the run with a sentence saying what it needs, a column of questions and a column for answers or answer dropdowns, before anything is embedded.

**Progress** (`worker/studio/job_run/progress.py`). Once the questions are found, and before any passage is embedded, the runner reports `on_row(0, total)`, then each row it finishes. `RunProgress` writes `{done, total}` into `job_run.progress` at once for the total and then at most every 2 seconds, each write one `UPDATE` by `json_set` on a short session of its own, so it never touches the run's session or expires what the question threads read. A locked database skips that write, which the next row tries again, and the final write keeps the last count beside the report. A cancelled or failed run keeps the last count written; Run again overwrites it at its first row. No event is sent for it: the screens poll the read route.

**Reading runs** (`run_read.py`, `run_tally.py`, `open_suggestions.py`). `GET /workspaces/{id}/job-runs?limit=` lists a workspace's runs, newest first (1 to 200, 50 by default), and `GET /workspaces/{id}/job-runs/{artifact}` reads one from the id of any version of its copy; a revised copy that is not a run, and another workspace's run, are `404 NOT_FOUND`. Each run gives its v1's `artifact_id`, title, job, pack id and version, status, error and `created_at`; `progress`; `tally`, null without a report, which splits the report's `questions` into `answered` (no reason code), `suggested` (a suggestion one step can confirm) and `for_person` (the rest, a suggestion its cell cannot hold included), so the three always add up, with the `skipped` rows beside them; `open_suggestion_count`, which drops as suggestions are confirmed or a person writes their cells; the copy's newest version and newest ready version; and `running`, true while any version of the copy is pending or processing. The read adds the pack as one string, the stored report, each open suggestion with its sheet, cell, question, suggested answer, the cell's own spelling of it and the comment, and the run's record of which version confirmed which cell, kept as history even when that version later failed.

`POST /workspaces/{id}/job-runs/{artifact}/confirm` confirms a finished run's suggested answers, those at the `cells` it names (sheet and answer cell) or every one not yet confirmed ([`confirm.py`](../../surfsense_local/backend/modules/jobs/runs/confirm.py)). It makes the next version of the run's revised copy, which writes each as the job would have written it, in the answer cell's own dropdown spelling with the comment and evidence an answer gets, and marks its lines on both added sheets confirmed. A suggestion is offered while no later version of the copy that stands writes its answer cell, which is read from the versions themselves rather than from a record of their ids, since the database hands a deleted row's id out again: one whose version failed, was cancelled or was deleted is offered again, and one a person answered in a version of their own is not. The run also records which version confirmed which, as history. A suggestion the answer cell cannot hold is never offered, and the report counts only the ones a step confirms. While a version of the copy is still being made, the route answers `409`, as an edit would. People confirm with one button, "Confirm 3 suggested answers", on the Jobs screen's done view and in Studio over the copy's newest ready version while no version of it is being made, in the revised-copy bar ([studio](studio.md#revised-copies)); both list every open suggestion in a dialog first and post the route with the run's v1 id and no cells.

`GET /job-packs/jobs/{job}/settings` reads the firm's settings for a job: every setting the pack declares, with its label, description, default and value, and the checker, a text model by provider, name and connection, or none to check on the answering model. `PUT` sets them whole, a setting left out going to its default; a setting the job does not declare, a value that is not true or false, and a checker that is neither the local runtime nor a connection that exists are refused with `422` ([`service.py`](../../surfsense_local/backend/modules/jobs/settings/service.py)). They are kept in `job_settings`, one row per job, and a setting a newer pack no longer declares is dropped when a run starts.

`GET /job-packs` lists the installed packs, each job with whether it may run, the sentence why not and its `locked_code` (`listing.py`); `POST /job-packs/download` and `POST /job-packs/import` get them ([Delivery](#delivery)); `POST /job-packs/install` takes a folder or `.zip` path on this computer, for developers and the live tests; `DELETE /job-packs/{id}` removes one.

## The agent

While a pack is installed the job tool is listed, naming the pack's jobs ([`run_job.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/run_job.py), [agent](agent.md#surfsensess-tools)), and each job's skill folder joins opencode's `skills`, allowed by name ([agent](agent.md#the-configuration)). The skill tells the agent to call `surfsense_run_job` with the ticked workbook and policies, never to answer the questions itself, and to report the counts and the exceptions. The tool starts the run and waits up to 150 seconds; a longer run says it will appear in Studio. Its reply says how many answers are suggested; once the user has checked them and asks, `surfsense_confirm_job_suggestions`, listed while a pack is installed, confirms them, all or by cell, and waits for the version as the job tool waits for a run ([`confirm_job.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/confirm_job.py)).

Both tools are in `VERSION_STEPS`, so their steps link a version as a render's does ([agent](agent.md#surfsensess-tools)). A finished run's reply starts with `Rendered artifact <id>, version 1: <title>`, and one still answering with `Queued artifact …`; its step reads "Filled in" the workbook, or "Started filling in" it while no copy is linked. A confirmation's reply starts with the new version's line, and its step reads "Confirmed suggested answers in" that version, or "Started confirming suggested answers". After its first line a run's reply gives the tally, how many of its questions were answered, left to a person, suggested and skipped, and names the report's two sheets. A Basic (Q&A) chat has no tools, which is why the Jobs screen runs jobs without the agent.

## Evals

`scripts/run_job_eval.py run --pack <pack> --eval <eval folder> --model anthropic:<id> --model openrouter:<id>` runs a pack's cases, each a `case.json` naming a real workbook, real source files and a gold file, with each file's source and licence ([`cases.py`](../../surfsense_local/backend/scripts/job_eval/cases.py)). Sources are read as ingest reads them: Word through the app's own reader, PDF from its text layer, Markdown and text as they are. Each run writes its filled workbook and a record: questions found, accuracy over the gold cells (an answer the cell could not hold counts as the blank the requester gets, and a gold answer the cell cannot hold expects that blank), false Yes (a Yes the gold does not support), Yes without a quote, dropdown violations, integrity problems (a sheet moved, a cell changed outside the answers, a dropdown, protection, merge, macro, chart or medium changed, or a file openpyxl cannot open), tokens, dollars and seconds, and per row its trace and the passages it was shown ([`score.py`](../../surfsense_local/backend/scripts/job_eval/score.py), [`workbook_integrity.py`](../../surfsense_local/backend/scripts/job_eval/workbook_integrity.py)); `report` rolls them up per case and model. `--checker <model>` makes the second checks on another model and `--setting key=true` turns on one of the job's firm settings. `openrouter:<model>@<provider>` pins a model to one OpenRouter provider with no fallback, as Claude needs while it goes through OpenRouter, and every run records which providers served its calls; `--reasoning low` runs a model that must think, as OpenRouter's Sonnet 5.5 must, at low effort. `report` gives runs that differ in their checker, their firm settings or their options lines of their own. A suggestion scores as the person's blank it is, and one its cell can hold is counted apart, as right when it is the gold answer, a confirmation one step away, or else wrong; and since the provider setting changes only how a checked provider answer ends, written or suggested, never a call, each run is also scored as if the setting were the other way round. Claude runs through Anthropic's Messages API with structured outputs, open models through OpenRouter with the schema required of the provider; neither falls back to another model, and Opus and Fable are refused. `--reasoning off` turns an open model's thinking off, which the app's connection does not. Passages are found with the app's bundled embedder, as on a fresh install, unless `--embedder none`. The cases and their gold live with the pack, outside this tree, and are built from real documents only. `tests/live/test_job_run_live.py` runs one case through the app itself.

## Known gaps

- A pack is checked, signature and files, each time the installed packs are read, but the runner reads the job's config and prompts, and opencode the job's skill, by path afterwards, so a process that can write to `<data>/job-packs` could swap a file between the check and the read, and a run started between the delivery's in-use check and the swap reads the new version. Like the licence check, this is honesty, not enforcement.
- A computer that cannot reach the licence server gets a pack only as a file SurfSense support sends by hand, imported with Import pack file.
- A `.xlsm` workbook cannot be added as a source, though a run accepts one, so a macro workbook runs only once saved as `.xlsx`.
- The Claude Code engine gets no job skills: only opencode is given a pack's skill folder.
- The packs' and the renewal's daily checks are two loops of the same shape, each with its own startup check and its own day.
- Until the licence server's `LICENSE_TRIAL_BUSINESS` is on, the trial that the screen's Start 14-day trial leads to carries no jobs.
- Quitting SurfSense stops a run, and the quit question counts only chat replies, not runs.
- A workbook copy has no Clean download, so SurfSense's two sheets go with the copy unless the user deletes them.
- A pack imported by hand under a second id for a code already installed is listed beside the first, and the higher version runs.
- Scoping questions (HECVAT's REQU rows, which decide which tabs apply) are answered like any other question; nothing marks the tabs they rule out N/A.
- CAIQ's "SSRM Control Ownership" column and other required columns that are not an answer, comment or evidence column are left empty.
- An approved answer library is not built: past answers count only as another source the user ticks.
- A run's first embedding of a library is not kept across app restarts, and ingest's own chunk vectors are not reused, since a job cuts its passages differently.
- A checker on a second local model takes turns with the answering one, and each turn still loads a model, which costs a local run some minutes; with the local runtime holding one model at a time, there is no way to keep both loaded.
- A No that rests on a provider is never suggested, only an N/A: the gate sends it to a person with no answer to confirm.
- Claude connections reach the job through Anthropic's OpenAI-compatible API, which takes no structured schema without `strict` and no effort setting, while the eval calls the Messages API at low effort: the live tests are what measure the app's own path.
