# Packaging

One build per platform (on Linux an AppImage, a deb and an rpm, and a snap made from the same folder) carries everything the desktop app needs to run offline: the API and the worker frozen into one PyInstaller binary, the renderer, the embedding, voice and parser model packs, the llama.cpp, sd.cpp and audio.cpp runtimes, and opencode with ripgrep for the agent. PyInstaller follows only `import` statements, so anything the app reaches by a path or a string must be named in the spec's inputs, and each omission shows up only in a frozen build on a clean machine; the inputs name those files, and packaging tests freeze the real binary to catch the ones that slip. Generation weights are never bundled; the app downloads them when the user asks ([egress](egress.md)).

**Code:** [`surfsense_local/backend/bundling/`](../../surfsense_local/backend/bundling/), [`surfsense_local/backend/scripts/build_binaries.py`](../../surfsense_local/backend/scripts/build_binaries.py), [`surfsense_local/backend/scripts/notices/`](../../surfsense_local/backend/scripts/notices/), [`surfsense_local/backend/scripts/opencv/`](../../surfsense_local/backend/scripts/opencv/), [`surfsense_local/electron/electron-builder.yml`](../../surfsense_local/electron/electron-builder.yml), [`surfsense_local/electron/scripts/`](../../surfsense_local/electron/scripts/), [`.github/workflows/release-local.yml`](../../.github/workflows/release-local.yml), [`surfsense_local/backend/tests/packaging/`](../../surfsense_local/backend/tests/packaging/)
**Decisions:** [ADR 0021](../adr/0021-no-intel-mac-build.md), [ADR 0012](../adr/0012-vulkan-only-gpu-backend.md), [ADR 0056](../adr/0056-speech-recognition-runs-on-a-second-audiocpp-server.md)

How to cut a release is in [`surfsense_local/RELEASE.md`](../../surfsense_local/RELEASE.md); how a release reaches installed apps is in [updates](updates.md).

## An installed app

The asar holds only the Electron main and preload bundles. Everything else rides beside it in `resources/`, where the main process spawns the binaries and loads the SPA by path:

| `extraResources` target | Staged in | Holds |
|---|---|---|
| `backend` | `backend/dist/backend` | the frozen onedir binary, `surfsense-backend`, which runs as the API or as a worker |
| `frontend/dist` | `frontend/dist` | the Vite SPA, loaded from disk |
| `models` | `backend/models` | the embedding model and the Docling parser pack |
| `llamacpp` | `electron/llamacpp` | `llama-server` and the libraries it links |
| `sdcpp` | `electron/sdcpp` | `sd-server`, for local image generation |
| `audiocpp` | `electron/audiocpp` | `audiocpp_server`, its libraries, the curated model specs and eSpeak-ng, for podcast voices and speech recognition |
| `opencode` | `electron/opencode` | `opencode` and `rg`, for the agent, with their licences; absent only from a build staged with `SURFSENSE_LOCAL_OPENCODE_ENABLED=0` |
| `licenses` | `electron/licenses` | `THIRD_PARTY_NOTICES.json` and `.txt`, the licence notices for everything above ([third-party notices](#third-party-notices)) |

The app icon lives in `electron/build/icons/`: `packaged/` holds the `.icns`, `.ico` and `.png` that `electron-builder.yml` names per OS, and `dev/` a variant with a "DEV" badge, which `electron/src/main/dev-app-identity.ts` sets on the Dock, taskbar, window and About panel only while unpackaged, alongside the name "SurfSense Dev", because development runs inside Electron's own bundle and would otherwise show Electron's icon. The macOS menu bar name and the About panel icon stay Electron’s in development; only packaging changes them. Artwork on Windows and Linux fills its canvas; on macOS it sits at 824 of 1024 px with a transparent margin, Apple's icon grid, so `icon.icns` and `dev/icon-macos.png` carry that margin and the `.ico` and `.png` files do not.

Packaged, Electron runs `resources/backend/surfsense-backend api` and one `surfsense-backend worker <queue>` process per queue, `ingest`, `studio` and `plugins`, and gives each `SURFSENSE_LOCAL_MODELS_DIR` pointing at `resources/models` and `HF_HUB_OFFLINE=1` (`electron/src/main/sidecars/python.ts`). The first argument names the role; a launch without one exits with status 2 rather than start a server nothing waits on (`backend/frozen_entry.py`). In development the same sidecars run `main.py` and `worker.py` on the backend's `.venv` interpreter ([`overview.md`](overview.md) says why not `uv run`). The Studio worker starts its own binary again, as `surfsense-backend --run-document-script <folder>`, for each document script it runs, and for each analysis script the agent's `surfsense_analyze_data` queues, so a script imports only what the frozen worker carries: python-docx, ReportLab, python-pptx, xlsxwriter, openpyxl, matplotlib, Pillow, numpy and pandas ([studio](studio.md#script-documents)). The PDF tools run in the API on pypdf, which the API imports statically ([agent](agent.md#pdfs-the-agent-works-on)).

## Freezing the backend

`scripts/build_binaries.py` runs PyInstaller on `bundling/backend.spec` into `dist/backend/`. PyInstaller cannot cross-compile, so each platform builds on itself. The script refuses a Python whose `sqlite3` lacks `enable_load_extension`: python.org's macOS builds omit it, and the frozen app would then die on its first migration, which is why CI freezes with uv's managed Python (`UV_PYTHON_PREFERENCE: only-managed`).

The API and the worker were two binaries through 2.2.3, and 1,531 of their files were identical: 184 MB unpacked that the installer packed twice, because electron-builder's NSIS archive compresses every file on its own. One binary carries both now. Its entry, `frozen_entry.py`, takes the role from the first argument and keeps the shapes the app re-runs itself with (`--probe-devices`, `--run-document-script`, `--decode-audio`, the `--check-*` flags), so no caller changed.

The API role imports exactly what an API-only freeze would carry. The spec runs a second, API-only analysis, of `main.py` with the worker's stack excluded (`bundling/api_inputs.py`), and writes the bundle's other modules to `api_absent_modules.txt` (`bundling/api_absent_modules.py`): those collected as bytecode, as native extensions and as source shipped as data, which is how OpenCV's hook collects `cv2`. The API role puts `None` in `sys.modules` for each before it imports anything, so `import torch` raises `ModuleNotFoundError` and `importlib.util.find_spec("torch")` returns `None`, as in a binary that never carried it, and an optional import cannot quietly change what the API does. `--check-retrieval-runtime` fails when torch, transformers, Docling, OpenCV, pandas or scipy are reachable from the API role.

Both roles take the database inputs from `bundling/common.py`:

- `collect_all("sqlite_vec")` ships `vec0`, which `sqlite_vec.load()` finds by the package's own path. Every connection loads it, so without it the migration on launch is the first thing to fail.
- `alembic/` ships as data. `shared/migrations.py` resolves it from its own `__file__`, which PyInstaller sets correctly. `env.py` is data rather than analysed code, so `alembic.context`, `alembic.runtime.migration` and `alembic.runtime.environment` are hidden imports.

What else each role's inputs name, and why the analyser cannot find it on its own:

| Inputs | Adds | Because |
|---|---|---|

Office support adds nothing to the binary. LibreOffice is downloaded only when the user turns it on, or is the user's own, and runs as its own process from `<data>/runtime/office/` ([office pack](office-pack.md)): the API starts it for a Word or PowerPoint version's previews and a source's pages, the Studio worker for a workbook's recalculation and a PDF conversion. The worker writes recalculated values with lxml, which python-docx already brings; openpyxl reads LibreOffice's values in the worker only, so the API role needs none.

### What the bundle leaves out

Hooks and `collect_all` gather whole packages; these parts of them are reached by no code path the app runs, so `backend.spec` drops them. Sizes are from the 2.2.3 installs, the Linux and macOS rows from those builds. `test_real_binaries.py` checks that each file and module in the table stays out, and the Linux and macOS jobs run every native extension after stripping.

| Left out | Where | Why it can go |
|---|---|---|
| RapidOCR's own copy of its ONNX models (30 MB) | `bundling/unused_payload.py` | scan OCR and Docling read only the parser pack's copy (`scan_ocr/rapid.py`, `parsing.py`'s `artifacts_path`) |
| onnxruntime's C API library (`onnxruntime.dll`, `libonnxruntime.*`; 17 to 64 MB by platform) | `unused_payload.py` | Python loads the pybind module, which links none of it |
| OpenCV's FFmpeg video plugin, Windows (29 MB) | `unused_payload.py` | RapidOCR, Docling and TableFormer only decode images. The release's own `cv2` carries no FFmpeg on any platform ([Building OpenCV](#building-opencv)); the filter covers a freeze from PyPI's wheel, such as `pnpm dist`'s |
| torch's `protoc`; on Linux, torch's C++ tests and their libraries (137 MB) | `unused_payload.py` | for building extensions and testing torch; `torch_shm_manager` stays, `import torch` refuses to start without it |
| every transformers model family but `auto`, `rt_detr`, `rt_detr_v2` and `encoder_decoder` | `bundling/excluded_modules.py` | listed from the installed package, so a new family never ships unseen |
| pytest, `win32ui`/`pywin` (MFC), `hf_xet`, faker and polyfactory, onnxruntime's conversion tooling | `excluded_modules.py` | dev tooling; pywin32's GUI; Hub transfers under `HF_HUB_OFFLINE=1`; Docling's Pydantic-template extraction, which the app never builds; tooling that only builds models. pluggy, `win32com`, `pythoncom` and `win32api` stay: Docling, torch, mcp and mpire use them |
| torch's and torchvision's `.py` sources (53 MB) | `bundling/torch_bytecode_only.py` | they ship as bytecode; only the config modules that read their own source at import keep it, found by scanning torch for `install_config_module(`, or `import torch` fails |
| OpenCV's Qt GUI (30 MB on Linux) | `pyproject.toml` | `opencv-python-headless` replaces `opencv-python`, which `[tool.uv] exclude-dependencies` drops from RapidOCR's requirements; the same `cv2`, pinned at 5.0.0.93 |
| symbol tables: Linux `strip --strip-unneeded` (most of 268 MB), macOS `strip -x` (175 MB) | `scripts/linux_symbol_tables.py`, `scripts/macos_local_symbols.py`, run by `build_binaries.py` | the loader reads only the dynamic or external symbols; only native crash traces lose the names of internal functions. On Linux each file is stripped as a copy and replaces the original only if every loadable segment still passes glibc's alignment check: strip leaves some libraries patchelf rewrote unloadable (numpy's OpenBLAS, torchvision's `image_stable.so`), and those ship unstripped. macOS signs each stripped file again, ad hoc. Neither strips the bootloader, which carries its archive appended |

`test_frozen_docling_reading.py` converts a page with a ruled table and a scanned line in the frozen binary and from source and requires the same Markdown, so none of this may change what Docling reads; `test_frozen_native_extensions.py` imports every native extension in the bundle in a script, so a strip step that broke a library fails the build.

## Model packs

Four packs are staged into `backend/models` before packaging and ship as `resources/models`, so the first PDF parses, the first query embeds and the first podcast voices with no network, and silence never reaches a speech model. Every other audio model is downloaded like any other model ([`local-models/catalog.md`](local-models/catalog.md)).

| Pack | Staged by | Holds |
|---|---|---|
| Embedding | `build:model`, `scripts/fetch_embedding_model.py` | `bge-small-en-v1.5`: the ONNX model and its tokenizer, from a pinned revision, sha256-checked |
| Voice | `build:voice`, `scripts/fetch_bundled_voice.py` | `audio/`: the manifest's first audio model in its default build, Kokoro 82M `Q8_0` (190 MB), with its install record, fetched as a catalog install is: from its pinned commit, sha256-checked |
| Voice activity | `build:vad`, `scripts/fetch_silero_vad.py` | `silero-vad/`: Silero VAD's 16 kHz ONNX build, `silero_vad_16k_op15.onnx` (1,289,603 B, MIT), and its licence, from v6.2.3's commit of `snakers4/silero-vad`, sha256-checked; the API and the worker read it in place ([admission](local-models/admission.md#speech-recognition)) |
| Parser | `build:parser`, `scripts/fetch_docling_models.py` | Docling's layout, table and RapidOCR weights, pruned of the variants ingest never loads |

The release workflow runs the four scripts directly. Without the parser pack, Docling downloads its weights on first use and RapidOCR writes into `site-packages`, which is read-only inside a frozen bundle, so the first PDF would fail rather than merely be slow. `worker/ingestion/parsing.py` points `HF_HOME` at the models directory before Docling loads and, once the parser pack is complete, sets `HF_HUB_OFFLINE=1`.

## Native runtimes

- `scripts/fetch-llamacpp.mjs` stages a pinned llama.cpp build, checked against its pinned SHA-256, into `electron/llamacpp/`, keeping `llama-server` and the libraries it links. Its rules, the pin, the Vulkan-only GPU backend and the pruning, are in [local-models/runtime.md](local-models/runtime.md). It also stages each licence file the archive carries under its own name, and llama.cpp's own `LICENSE` on every platform. The Windows archives carry only LLVM OpenMP's (`LICENSE-LLVM-OpenMP`, for their `libomp.dll`), so that `LICENSE` comes from the copy in `scripts/llamacpp/`, taken at the pinned build. An archive that carries its own must match that copy, or the fetch stops.
- `scripts/sdcpp/stage.mjs`, which `build:sdcpp` runs, stages stable-diffusion.cpp's `sd-server` into `electron/sdcpp/` with the libraries it loads from beside itself and its licences, leaving `sd-cli` behind. It runs `sd-server --help` from the staged folder before it swaps the folder into place.
  - Windows downloads upstream's Vulkan archive, checked against its pinned SHA-256, and copies the MSVC and OpenMP runtimes beside it, which the archive needs and does not carry.
  - Linux and macOS compile the pinned commit, because upstream's Linux archives need glibc 2.38 and its macOS archive needs macOS 26.0. The recipe, `scripts/sdcpp/recipe.mjs`, builds Vulkan on Linux, with one ggml library per micro-architecture, and Metal on macOS, for 13.3.
  - Compiling needs CMake, a C++ compiler and the Vulkan SDK (`glslc` and headers) on Linux, or Xcode's command line tools on macOS; Windows needs Visual Studio 2022 or newer with the C++ tools, for the runtime it ships. Without them the script stages an empty folder and says why, and the app runs without local images. Release CI and `pnpm dist` pass `--strict`, which fails instead, naming everything missing and the command that installs it with the machine's package manager.
- `scripts/audiocpp/stage.mjs`, which `build:audiocpp` runs, stages audio.cpp's `audiocpp_server` into `electron/audiocpp/` with the model specs of the five curated families, `FAMILIES` in `scripts/audiocpp/pins.mjs`: Kokoro, Supertonic and Kitten for voices, and Nemotron's `nemotron_asr` and Canary's `canary_asr` for speech recognition, which the same binary serves from a second process ([ADR 0056](../adr/0056-speech-recognition-runs-on-a-second-audiocpp-server.md)). It adds eSpeak-ng 1.52.0 from the pinned `espeakng-loader` wheel, which Kokoro and Kitten phonemise through (Kokoro finds it through the server's environment, Kitten through `server.json`, [`local-models/catalog.md`](local-models/catalog.md)), and eSpeak-ng's GPL licence text, which the wheel does not carry. Its data keeps 21 of eSpeak's 114 dictionaries, the ones a curated voice can reach (`scripts/audiocpp/espeak/dictionaries.mjs`): the voices' own (en, es, fr, hi, it, pt), the 13 eSpeak 1.52.0 switches to when a word is in another script (el, hy, hi, bn, pa, gu, ta, te, kn, ml, si, ka, ko), and the ones those dictionaries send words to (ru, de, pl), 7 MB less. Staging reads every kept dictionary's word list and rule phonemes and fails if one switches to a language whose dictionary is not staged (`scripts/audiocpp/espeak/switches.mjs`), since eSpeak then half-builds its translator and can crash the server. The list records the eSpeak version, audio.cpp tag and curated families it was worked out for, and a test fails when any of them changes. A server kept as already staged has its eSpeak data trimmed in place the same way, so a stage from before the trimming does not ship every dictionary. Before it swaps the folder into place, it runs `--list-devices` from it, then starts the server once per curated family on an empty model package (`scripts/audiocpp/built-families.mjs`): a family the build has fails inside its own loader, and one it lacks is refused by name first, so a family missing from the build stops the stage. It prints the staged size and how long staging took. A server already staged is kept only when the same check finds every curated family in it (`scripts/audiocpp/staged-server.mjs`); one staged before a family joined the pins is compiled and swapped again, since it would answer that family's model with "unsupported model family hint", and so is one that does not start at all. Without `--strict` the stale server stays, with a warning that names what it lacks, when no toolchain is installed, when the app holds `electron/audiocpp/` (checked before compiling), or when staging again fails, so `pnpm dev` goes on with every family it has.
  - macOS downloads upstream's archive, checked against its pinned SHA-256.
  - Windows and Linux compile the pinned commit, because upstream's Linux archives need glibc 2.38 and its Windows archive compiles AVX-512 into the executable. The recipe, `scripts/audiocpp/recipe.mjs`, builds only the CPU backend, since the server runs with `--backend cpu`, with one ggml library per micro-architecture and only the curated model families.
  - Compiling needs CMake and GCC 13 or newer on Linux, or Visual Studio 2022 or newer with the C++ tools on Windows. On Windows the build names Visual Studio's generator (`msvc-runtime.mjs`), since a CMake from MinGW or MSYS2 defaults to Ninja, which refuses `-A x64` and finds no compiler outside a Visual Studio prompt. Without them the script stages an empty folder and says why, and the app runs without local audio. Release CI and `pnpm dist` pass `--strict`, which fails instead, naming everything missing and the command that installs it with the machine's package manager.

- `scripts/opencode/stage.mjs`, which `build:opencode` runs, stages opencode `2.1.2` and ripgrep `15.1.0` into `electron/opencode/`, each archive checked against its SHA-256 in `scripts/opencode/pins.mjs`. opencode 2.x is published on npm only, one `@opencode/cli-<platform>` package per platform; on x64 it takes the `-baseline` package, which opencode compiles without AVX2. The packages carry only the executable, so opencode's licence comes from its tag, also pinned; ripgrep's three licence files ship in `opencode/ripgrep/`. Before it swaps the folder into place, `scripts/opencode/check-stage.mjs` checks the folder holds both executables and the licences and runs `rg --version` and `opencode --version` from it, opencode in a throwaway home and temp folder, since 2.x writes a log even for `--version`, reading its release from `opencode v2.1.2`; `stage.mjs` restages unless the staged folder passes that same check, so a version bump restages. The Linux executable needs glibc 2.30 or later; ripgrep's Linux build is static. The Windows stage is 223,259,987 B unpacked (**measured**, 22 Oct 2026). `scripts/opencode/enabled.mjs` turns staging on for every build; `SURFSENSE_LOCAL_OPENCODE_ENABLED=0` turns it off for one, and off it removes an earlier stage. An empty value keeps the default, and any value but `1` or `0` stops the build, so a `true` or a `no` never ships an installer without the agent.

`pnpm dist` in `electron/` runs every staging step before `electron-builder`, the native runtimes first and the third-party notices last, so a missing toolchain stops it before the frontend and the frozen backend are built. It stages sd.cpp and audio.cpp with `--strict`, so an installer never ships without them; `predev` does not, so dev runs without a toolchain. On Windows, the rename that swaps each stage into place waits up to a minute while another process still has a file in it open, such as a Windows service reading an executable the script just ran.

`frontend/` and `electron/` each pin their pnpm in `packageManager` (`pnpm@11.27.1`), which pnpm switches to locally and the desktop workflows read through `package_json_file`. The repository root's `packageManager` is the web app's, `pnpm@10.26.0`, and does not apply here.

## Third-party notices

`build:notices` in `electron/` writes the licence notices the installer ships, after every staging step because it reads what was staged. Four generators each write a fragment into `electron/licenses/fragments/`, and `scripts/notices/merge.mjs` merges them into `electron/licenses/THIRD_PARTY_NOTICES.json`, one entry per component with its name, version, tree, licence id and full text, and a plain `.txt` of the same, ordered by tree and then by name in code-unit order, so every machine writes the same file. Only those two files ship, as `resources/licenses/`; the folder is generated and ignored by git.

| Generator | Tree | Reads |
|---|---|---|
| `electron/scripts/notices/npm.mjs` | `frontend`, `electron` | `pnpm licenses list --json --prod` in each pnpm tree, and every `LICENSE`, `LICENCE`, `COPYING` and `UNLICENSE` file at the top of each package. A `NOTICE` file ships after that text but is attribution, not licence terms, so a package carrying only a `NOTICE` has no text for the gate. A package that ships no text but whose terms a maintainer established takes the text recorded for its exact version, with its source, in `electron/scripts/notices/reviewed-texts.json` |
| `backend/scripts/write_python_notices.py` | `python` | the names `uv export --frozen --no-dev` gives for this platform, since CI's `uv sync` also installs the dev tools, then `importlib.metadata` for each: its `License-Expression`, `License` or classifiers, and the licence files it installs, the dist-info's first and then those in the package's own folders, such as a vendored library's. A `NOTICE` file, or a third-party notices file such as onnxruntime's `ThirdPartyNotices.txt`, ships after that text, as on the npm side, but never counts as it. It adds PyInstaller, whose bootloader runs inside the frozen backend binary, and CPython, whose interpreter and standard library it carries, with the `LICENSE.txt` from the standard library or, failing that, the installation root, where uv's Windows Python keeps it |
| `electron/scripts/notices/native.mjs` | `native` | the licence files the stage scripts already leave in `llamacpp/`, `sdcpp/`, `audiocpp/` and `opencode/`, and Electron's own; versions come from the stage scripts' pins. On Windows it also reads `llamacpp/LICENSE-LLVM-OpenMP`, for the `libomp.dll` only that platform's archive carries; a component listed for other platforms is skipped. Every file a staged component lists must hold text, or the generator fails naming it, since ripgrep's `COPYING` names its licences without their terms. A folder absent or empty, as in a dev checkout or a build staged with `SURFSENSE_LOCAL_OPENCODE_ENABLED=0`, is reported and left out. eSpeak NG's entry carries a note saying SurfSense modified the copy and when, naming the dictionaries shipped and linking eSpeak's full source at the pinned tag |
| `backend/scripts/write_model_notices.py` | `model` | the pinned specs of the embedding, voice, parser and Silero VAD packs: repository, revision and licence id. Silero VAD's text is the `LICENSE` `build:vad` stages beside its weights; the others ship no licence file, so each says only the id is known and no text ships |

The merge fails the build when a fragment is missing, or when an npm, Python or native entry has no licence text and `electron/scripts/notices/allowed-without-text.json` has no entry for it at that exact version with a reason, so a version bump is reviewed again. A reviewed entry adds its reason to the notice in place of the text.

## Building audio.cpp

[`build-audiocpp.yml`](../../.github/workflows/build-audiocpp.yml) compiles the Windows and Linux builds with `stage.mjs --strict`, checks them, and hands each staged folder on as an artifact. `release-local.yml` calls it, and its packaging jobs unpack the artifact before `stage.mjs`, which then finds the server already staged. A pull request that changes `scripts/audiocpp/`, `scripts/not-staged/`, the audio.cpp adapters or engine, the transcription slice, the manifest or either server's test runs it too. It caches the staged folder by the scripts' contents, so a release that does not change them reuses the last checked build, and voices and transcribes with it again. The recogniser's 930 MB file is cached by its pinned sha256, while the voices are downloaded every run.

Why it compiles rather than downloads, in plain words: upstream's ready-made programs for Linux and Windows do not run on many of the computers the app supports, for a different reason on each.

- **Linux: the age of the system.** Upstream's program needs a recent Linux, Ubuntu 24.04 or later (glibc 2.38). The app runs on older ones too, back to Ubuntu 22.04 and Debian 12 ([the Linux floor](#the-linux-floor)).
- **Windows: the processor, not the Windows version.** Upstream's program uses AVX-512 instructions that many common processors lack, so it crashes on them, recent ones included: Intel's 12th to 14th generation, and AMD's before Zen 4. The app's build picks the right code for the processor it runs on.

macOS needs neither, so the app ships upstream's program there. The app's builds are upstream's own code at a pinned commit; only the build settings differ.

It is a stopgap. Once upstream publishes archives that meet both floors, the app downloads those as it does llama.cpp's, and the compile path and the workflow go.

- Linux builds on `ubuntu-22.04`, the release's own runner, with GCC 13 from the toolchain PPA. The PPA replaces the runner's libstdc++ with a newer one, so the build runs in its own job, and the frozen backend never bundles it.
- libstdc++ is linked statically into every file, ggml's CPU modules included, since those take CMake's module flags. libgcc stays dynamic, because GCC 12 and 13's static unwinder on 22.04 calls `_dl_find_object`, from glibc 2.35.
- OpenMP is off, so no `libgomp` ships.
- Linux gates on no symbol newer than `GLIBC_2.34` or `GCC_7.0.0`, which RHEL 9's glibc and libgcc provide, stricter than [the app's floor](#the-linux-floor), and on no file that needs libstdc++, libgomp or Vulkan. The runner's own libstdc++ is newer than a user's, so only that gate, not the voicing test, catches a dynamic one.
- Windows copies the MSVC runtime beside the executable, so a clean Windows needs no redistributable.
- Staging checks that the build has every curated family, and a change to `FAMILIES` changes the cache key, so adding a family compiles again and runs both floors' gates on the new build.
- A third job stages upstream's macOS archive on `macos-15` the same way, so a family added to the pin that the archive lacks fails on the pull request; the release's macOS job stages it again.
- With the four families, the Windows stage is 32.6 MB, and cloning and compiling it took 4.8 minutes on a 16-thread Ryzen 7 5800X; `nemotron_asr` added 0.24 MB to the executable (**measured**, 14 Oct 2026).
- Both run `test_audiocpp_voicing.py` on the staged folder, cached or not, with each curated model's pinned file downloaded from the URL its manifest entry names ([Packaging tests](#packaging-tests)).
- An artifact drops symlinks and file modes, so the staged folder travels as a tar.

## Building sd.cpp

[`build-sdcpp.yml`](../../.github/workflows/build-sdcpp.yml) compiles the Linux and macOS builds with `stage.mjs --strict`, checks each against the app's floors, runs `test_sdcpp_generation.py` on the staged folder, cached or not, with Stable Diffusion 1.5's pinned file downloaded from the URL its manifest entry names ([Packaging tests](#packaging-tests)), and hands each staged folder on as an artifact, as `build-audiocpp.yml` does. A pull request that changes `scripts/sdcpp/`, `scripts/not-staged/`, the image engine, the local manifest or that test runs it too, so a compile that a pin bump or a new runner image breaks, or a server that starts and cannot diffuse, fails in review rather than in a release. It caches the staged folder by the scripts' contents. Windows is a pinned download, so the release job stages it itself, as it does llama.cpp.

Why it compiles on Linux and macOS, in plain words: upstream's ready-made programs start only on the newest systems there, Ubuntu 24.04 (glibc 2.38) and macOS 26.0, while the app runs back to Ubuntu 22.04 ([the Linux floor](#the-linux-floor)) and to macOS 13.3, the macOS floor its llama.cpp and audio.cpp builds already set. Upstream's Windows program runs on any x64 processor, since its AVX-512 code sits only in the per-processor ggml libraries ggml picks at start, so Windows takes it as built.

- Linux builds on `ubuntu-22.04` with LunarG's Vulkan SDK, as llama.cpp's own 22.04 release does, because 22.04 packages no `glslc` to compile ggml's shaders.
- libstdc++ is linked statically into every file, ggml's modules included, and OpenMP is off, so neither `libstdc++` nor `libgomp` ships. libgcc stays dynamic.
- Linux gates on no symbol newer than `GLIBC_2.34` or `GCC_7.0.0`, stricter than [the app's floor](#the-linux-floor), on no file that needs libstdc++ or libgomp, and on only the Vulkan backend needing the system's Vulkan loader, which comes with the GPU driver.
- macOS gates on every file targeting 13.3 or older and linking only the system's libraries and its own.
- It is a stopgap, like audio.cpp's: once upstream publishes a Linux archive built on 22.04 and a macOS one for 13.3, the app downloads those and the compile goes.

## Building OpenCV

[`build-opencv.yml`](../../.github/workflows/build-opencv.yml) builds `opencv-python-headless` from the sdist `uv.lock` pins, with only the OpenCV modules the app's `cv2` calls reach, on the three release runners, checks each wheel against PyPI's, and hands it on as an artifact. `release-local.yml` calls it, and each packaging job installs the wheel over PyPI's right after `uv sync`, so the frozen backend carries it. A pull request that changes `backend/scripts/opencv/` or `uv.lock` runs it too. It caches the wheel by the pinned sdist's hash and the build scripts' contents, and runs every gate on a cached wheel again.

Why, in plain words: PyPI's wheel carries all of OpenCV and the libraries behind it: video, neural networks, feature matching, camera calibration, stitching, FFmpeg (on macOS Homebrew's GPL-3 build with x264 and x265) and, on Linux, OpenBLAS. The app, RapidOCR, Docling and its table model only resize, convert, draw on and find shapes in images, warp a text line straight and write PNG and JPEG.

- `scripts/opencv/recipe.py` holds the switches, `pins.py` the sdist (read from `uv.lock`, so a version bump rebuilds), the build tools and the Linux image, and `build_wheel.py` builds as upstream's CI does (`setup.py bdist_wheel --py-limited-api=cp37`); a local build runs the same script.
- The modules are core, imgproc, imgcodecs, geometry, which holds `getPerspectiveTransform`, `minAreaRect` and `boxPoints` in 5.0, and flann, which geometry needs. FFmpeg, TIFF, WebP, JPEG 2000, OpenEXR, AVIF, protobuf and flatbuffers are off.
- Everything else is upstream's, so every kept call returns PyPI's bytes: Intel IPP on x86 (29 MB of the Windows `cv2.pyd`; without it, `resize` with `INTER_CUBIC` and on float images differs from PyPI's, **measured**), OpenCL, ITT, the CPU baseline and dispatch, KleidiCV and carotene on Apple silicon, and zlib as upstream takes it: built from the sdist on Windows and macOS, the system's `libz.so.1` on Linux. libpng is the sdist's 1.6.57 everywhere; upstream's Linux wheel ships 1.6.58, whose only change is in reading.
- OpenCV 5.0 requires LAPACK. Linux builds the sdist's CLAPACK, as Windows does, instead of linking OpenBLAS (39 MB): OpenCV solves the 3×3 and 8×8 systems the app's calls make itself, under its 25-row threshold for LAPACK.
- Linux builds in upstream's own image, pinned by digest in `pins.py`, the one PyPI's 5.0.0.93 wheel was built in: the same GCC 14, and glibc 2.28. It gates on no symbol newer than `GLIBC_2.34`, `GCC_7.0.0`, `GLIBCXX_3.4.29` or `CXXABI_1.3.13`, RHEL 9's glibc and GCC 11 runtimes and so stricter than [the app's floor](#the-linux-floor), and on linking only the C and C++ runtimes and zlib. macOS builds for 13.0, as upstream, and gates on 13.3 and on linking only the system's libraries. Windows builds on `windows-2022`, because opencv-python's `setup.py` names Visual Studio 2022's generator and `windows-latest` moved to Visual Studio 2026, and installs NASM, which libjpeg-turbo's SIMD needs; the recipe sets `REQUIRE_SIMD`, so a build without it fails.
- `setup_patch.py` lets upstream's `setup.py` package a build with neither the FFmpeg plugin nor typing stubs. The stub generator names features, calib and dnn symbols and gives up on a smaller build, so the wheel has no `.pyi` stubs, `py.typed` or `cv2.typing`, which nothing the app runs imports.
- The gate, `check_same_outputs.py`, makes two venvs with the backend's locked numpy, Pillow, RapidOCR and onnxruntime, one with PyPI's wheel and one with the built one. In each, `record_calls.py` makes every call site's `cv2` call on five seeded images in each layout the sites pass, first with `cv2`'s defaults, as scan OCR runs, then after `setNumThreads(0)` and `ocl.setUseOpenCL(False)`, as Docling's table model sets them, then has RapidOCR read rendered text as the app configures it and with every stage on, upside down too. `compare_outputs.py` fails on any byte that differs. On Windows all 28,858 outputs matched, RapidOCR's text, boxes and scores included (**measured**, 22 Oct 2026).
- Windows' `cv2.pyd` is 51,877,888 B against PyPI's 85,848,064 B (its FFmpeg plugin was already left out), and the wheel 20.3 MB against 43.8 MB (**measured**).
- The packaging job sets `UV_NO_SYNC=1` once the wheel is in: `uv run` otherwise syncs the venv to `uv.lock` and silently puts PyPI's wheel back.

## Release builds

`release-local.yml` builds on a `v*` tag, or on `workflow_dispatch` with a version and `publish: never` for a dry run:

| Runner | Artifacts |
|---|---|
| `macos-15` | `SurfSense-arm64.dmg`, `SurfSense-arm64.zip` |
| `windows-latest` | `SurfSense-Setup.exe`, NSIS, x64 |
| `ubuntu-22.04` | `SurfSense.AppImage`, `SurfSense.deb`, `SurfSense.rpm`, x64 ([Linux packages](#linux-packages)) |

The dmg is LZFSE (`dmg.format: ULFO`): smaller than electron-builder's default zlib, and faster to decode, so macOS verifies it on first open and copies the app out no slower; LZMA (ULMO) would be smaller still but decodes 5 to 9 times slower, a wait every install would see. Last, after the installers are uploaded and the dmg is checked, `scripts/check-installer-size.mjs` prints each one's size and fails the job when one is over its budget in `scripts/installer-size-budgets.json`, each installer's measured size plus 25 MiB (dry run 39844562498, 22 Oct 2026, with opencode 2.1.2 and the minimal OpenCV; the rpm's is provisional, see [Known gaps](#known-gaps)), so growth past that is caught on a dry run, not after a release; lower a budget whenever an installer shrinks. Before that, the macOS job checks the dmg is LZFSE, verifies and mounts it, checks the app's signature inside, times the copy out and runs the copied app's backend.

The Linux runner is pinned because `ubuntu-latest` moves to 26.04 and would silently raise [the Linux floor](#the-linux-floor): PyInstaller copies the runner's `libgcc_s.so.1` into the frozen backend. There is no Intel Mac build, because torch and onnxruntime no longer publish Intel macOS wheels.

Each runner, in order, checks the version (semver; on a tag push it must equal `surfsense_local/VERSION`; whenever it publishes it must carry no prerelease suffix), installs the minimal `cv2` over PyPI's ([Building OpenCV](#building-opencv)), refuses to build with the test signing key ([license](license/app.md)), freezes the backend, stages the model packs, smokes the frozen worker's Docling vision imports (`--check-vision-runtime`) and scan OCR against the staged pack (`--check-scan-ocr`), runs `test_real_binaries.py`, `test_frozen_docling_reading.py`, `test_frozen_document_scripts.py` and `test_frozen_native_extensions.py` against the binary it just froze, builds the SPA and the Electron bundles, stages llama.cpp, opencode, audio.cpp and sd.cpp, generates the third-party notices, and runs `electron-builder`. On macOS and Windows, electron-builder's `afterSign` hook, `scripts/opencode/after-sign.mjs`, runs `check-stage.mjs` on the packaged opencode folder once the app is signed, and on macOS notarized, before any installer is made, so a tag's build never uploads one whose opencode signing broke; unsigned builds run it too. Linux signs nothing, so electron-builder skips the hook there with a warning. Every runner then runs `check-stage.mjs` again on the folder its build packaged: `win-unpacked`, `linux-unpacked` or `mac-arm64/SurfSense.app`. The three runners wait for the `audiocpp`, `sdcpp` and `opencv` jobs, unpack audio.cpp's Windows and Linux builds and sd.cpp's Linux and macOS builds, and install their platform's OpenCV wheel. On Linux it then starts the API from the packaged `linux-unpacked` resources and runs `llama-server --list-devices`, `audiocpp_server --list-devices` and `sd-server --help` from their packaged directories, because ggml finds its backends only next to the running executable, and checks that eSpeak-ng and its licence are packaged beside `audiocpp_server`, sd.cpp's Vulkan backend and licence beside `sd-server`, and the notices in `resources/licenses` without their fragments.

The macOS build is signed with the hardened runtime and notarized whenever the signing secrets are available, a dry run in this repository included. electron-builder signs every Mach-O file in the bundle, `Contents/Resources` included, with `entitlementsInherit`, except `opencode`: `mac.signIgnore` leaves it with its vendor's Developer ID signature, hardened runtime, secure timestamp and the five entitlements Bun asks for, among them `disable-executable-page-protection`, which the app's file lacks (**measured** on the pinned `opencode-darwin-arm64.zip`, 7 Oct 2026). The notary service takes it so: v2.2.0's tag build was notarized carrying it (9 Oct 2026). `rg` arrives only ad-hoc signed, so it is signed with the app. Azure Trusted Signing for the Windows build runs only on tag pushes, and signs every `.exe` under `resources/` as electron-builder copies it, replacing any signature it carries. `opencode.exe` arrives Authenticode-signed by its vendor and `rg.exe` unsigned, and a tag's build runs both signed with SurfSense's certificate. A dry run has no Azure credentials and `CSC_LINK`, the macOS certificate, reaches only the macOS runner, so a dry run's Windows build is unsigned; before that it reached Windows too and electron-builder signed every `.exe` with it through signtool (the 2.1.0 dry run's log, 3 Oct 2026).

The Apple notarization credentials are checked by their own workflow, [`notarization-credentials.yml`](../../.github/workflows/notarization-credentials.yml), with `notarytool history`: weekly on Mondays, on demand, and as a job the release build waits on, dry runs included; the audio and image sidecar and OpenCV builds run alongside it. A lapsed agreement or credential fails there in seconds, not at the end of a build, as the 2.1.0 dry run's did with Apple's 403 on 3 Oct 2026. Without the secrets it passes with a notice, except on a run that publishes, a tag's included, which must notarize.

The entitlements file also carries `com.apple.security.device.audio-input`, without which the hardened runtime keeps the microphone from the app and from its helpers, which inherit the file, and `mac.extendInfo` sets `NSMicrophoneUsageDescription`, the sentence macOS's microphone prompt shows: "SurfSense turns your speech into text on this computer." Electron's `systemPreferences.askForMediaAccess`, which the main process calls before the page opens the microphone, needs both: without the entitlement it can crash the app, and without the sentence the prompt shows Electron's own. [`scripts/mac-microphone.test.mjs`](../../surfsense_local/electron/scripts/mac-microphone.test.mjs) checks that both stay configured. Which page may use the microphone once macOS allows it is decided at runtime ([overview](overview.md#frontend)).

The installer's version is the one the workflow resolved, passed as `-c.extraMetadata.version`. The tree carries it too: `surfsense_local/VERSION` is the one number, and `surfsense_local/scripts/bump-version.sh` writes it into the backend's `pyproject.toml`, both `package.json` files, `www/features/downloads/app-release.ts` and `backend/license/release.py`, then refreshes `uv.lock`.

## Linux packages

The `ubuntu-22.04` job packages one `linux-unpacked` folder three ways, and the snap is made from the same folder. The deb and the rpm install it to `/opt/SurfSense` as the package `surfsense-local-electron`, with the executable `surfsense-local`.

| Package | Built by | Dependencies |
|---|---|---|
| `SurfSense.AppImage` | the release's `ubuntu-22.04` job | none declared: the host needs [the floor](#the-linux-floor)'s libraries and `libgomp.so.1`, but no libfuse2 |
| `SurfSense.deb` | the same job | electron-builder's depends (GTK, NSS, X and the rest) plus `libgomp1` and `libc6 (>= 2.35)`, so apt refuses a system below [the floor](#the-linux-floor); recommends `libappindicator3-1` and `libvulkan1` |
| `SurfSense.rpm` | the same job | electron-builder's requires without `libXScrnSaver`, which EL10 ships only in EPEL and Electron 44 neither links nor loads (**measured** on `electron-v44.2.0-linux-x64`, 22 Oct 2026), plus `(libgomp or libgomp1)`, the Fedora and openSUSE names; recommends `vulkan-loader` |
| `SurfSense.snap` | its own job, from that `linux-unpacked` | the GNOME extension's content snaps (`gnome-46-2404`, `mesa-2404`, `gtk-common-themes`); stages electron-builder's libraries plus `libgomp1` and `libvulkan1` |

- **The AppImage** uses electron-builder's static type-2 runtime (`toolsets.appimage: "1.0.3"`, runtime 20251108), which carries its own FUSE library, so it starts without libfuse2, which Ubuntu 22.04 and later do not install. electron-builder 26.16.1 still labels that toolset beta. It compresses the image with zstd, where the legacy toolset used gzip. Its `.desktop` entry runs `AppRun %U` without the legacy entry's `--no-sandbox`: AppRun adds the flag itself when `unshare -Ur true` fails, where unprivileged user namespaces are blocked.
- **The deb and the rpm depend on the OpenMP runtime**, because llama.cpp's libraries (`libggml-base` and every `libggml-cpu-*`) link the host's `libgomp.so.1`, which its archive does not carry ([runtime](local-models/runtime.md#packaging)). Both pass it to fpm as an extra `--depends`, since setting `depends` would replace electron-builder's list; [`deb-control.test.mjs`](../../surfsense_local/electron/scripts/deb-control.test.mjs) and [`linux-packages.test.mjs`](../../surfsense_local/electron/scripts/linux-packages.test.mjs) hold that. fpm has no recommends option for rpm, so `--rpm-tag` writes `Recommends: vulkan-loader` into the spec as it is. fpm leaves `AutoReqProv` off, so no linked library becomes a requirement by itself. electron-builder brings its own fpm 1.17.0; the rpm also needs the build host's `rpmbuild`.
- **Both write `resources/package-type`**, `deb` or `rpm`, and `app-update.yml` into the shared `linux-unpacked` before packing it. electron-builder finishes the AppImage first, then builds the deb and the rpm in `linux.target`'s order, so each package carries its own type, the AppImage none, and `linux-unpacked` is left with `rpm`. electron-updater picks its updater from that file, so anything that reads the folder afterwards, the smoke steps and the snap job among them, must not assume `deb`. `stable-linux.yml` lists the rpm with the AppImage and the deb, so the app's feed check accepts `.rpm` names ([`manifest-checks.ts`](../../surfsense_local/electron/src/main/update-feed/manifest-checks.ts)).
- **The snap** is not in `linux.target`. A separate job builds it from the `snapcraft:` block with `electron-builder --linux snap --prepackaged` and uploads it to the Snap Store, not to the release. It is a strictly confined core24 snap, grade stable, named `surfsense-local` after `executableName`, with electron-builder's GNOME extension. Its plugs are electron-builder's defaults plus `browser-support`, `network-bind` for the local API and `audio-record` for speech to text. Listing them drops the `browser-support` plug with `allow-sandbox` that electron-builder otherwise adds, which needs store review, so the launcher passes `--no-sandbox`, `chrome-sandbox` is left out and confinement is the sandbox. `snapcraft.publish` names GitHub, as the top-level `publish` does, because a snap build without a publish entry of its own falls back to `snapcraft upload`. electron-builder points the snap's `TMPDIR` at `$XDG_RUNTIME_DIR`, a small tmpfs; the app replaces it, and keeps its data, in `SNAP_USER_COMMON` ([`data-dir.ts`](../../surfsense_local/electron/src/main/data-dir.ts)). The job builds in an LXD container (`-c.snapcraft.core24.useLXD=true`), not on the runner: in destructive mode electron-builder drops the GNOME extension, and with it GTK, Mesa and the fonts, so the snap would not start. At pack time snapcraft's extension adds the `gnome-46-2404`, `gpu-2404` and theme content plugs, their layout, and the `desktop-launch` and `gpu-2404-wrapper` command chain; [`linux-packages.test.mjs`](../../surfsense_local/electron/scripts/linux-packages.test.mjs) builds electron-builder's descriptor with the flags the job passes and checks that it keeps the extension and writes no root plugs or layout of its own. The job then checks the packed snap's files and metadata: no `chrome-sandbox` or electron-updater file, strict confinement, the name and the version. The snap is never installed or launched in CI.

## The Linux floor

The Linux packages need glibc 2.35 and GCC 12's libstdc++ (`GLIBCXX_3.4.30`) or newer: Ubuntu 22.04 and later, Debian 12 and later, current Fedora, and EL10. Two parts set it:

- PyInstaller copies the runner's `libgcc_s.so.1` into the frozen backend's `_internal/`. On `ubuntu-22.04` that is GCC 12's, which calls `_dl_find_object`, from glibc 2.35.
- llama.cpp's Linux archive loads the host's libstdc++, since none ships beside it, and four of the libraries the app keeps (`libllama-server-impl.so`, `libllama-common.so`, `libggml-vulkan.so` and `libggml-rpc.so`) need `GLIBCXX_3.4.30`. The archive's libraries also link the host's `libgomp.so.1` and OpenSSL 3, which it does not carry either.

RHEL, Rocky and Alma 9 ship glibc 2.34 and GCC 11's libstdc++ (`GLIBCXX_3.4.29`), below the floor. EL 9.0 to 9.6 lack glibc's `_dl_find_object` (`GLIBC_2.35`), so the frozen backend's bundled `libgcc_s.so.1` cannot load and the app does not start. EL 9.7 and later backport it (glibc-2.34-216 and later), so the app starts, but `llama-server` cannot load its libraries (`GLIBCXX_3.4.30`) and no local model runs. The gates in `build-audiocpp.yml`, `build-sdcpp.yml` and `build-opencv.yml` check stricter symbols, RHEL 9's, for what each builds; nothing gates llama.cpp's archive or the frozen backend.

## The NSIS size limit

`makensis` is 32-bit and cannot map a payload over 2 GB, so the Windows installer has a hard ceiling. The Windows build hit it before 2.0.0 through the bundled Ollama's CUDA runners, which were pruned; 2.2.0's `SurfSense-Setup.exe`, the first to carry opencode and ripgrep, is 1,209,002,840 bytes on the release, about 1.2 GB. No CUDA payload ships.

Keep `nsis.differentialPackage` at its default. The per-file 7z payload is what lets a Windows update move about 128 MB instead of the whole installer ([updates](updates.md#update-size)); a solid archive (`differentialPackage: false`) would save 72 MB once and make every Windows update a full download. `electron-updater` is packed from pnpm's patched copy: `patches/electron-updater@6.8.9.patch`, listed under `patchedDependencies` in `electron/pnpm-workspace.yaml`, so `pnpm install --frozen-lockfile` applies it and electron-builder copies the patched files into `app.asar` with no build step of its own.

## Known gaps

- `pnpm dist` freezes with PyPI's `cv2`; only the release installs the minimal one.
- No packaging test checks that the frozen binary carries the minimal `cv2`; the release step checks the venv's modules before freezing.
- macOS compiles with the runner's Xcode 16 where upstream's wheel used Xcode 15 (SDK 14.2); only the byte-for-byte gate holds them together.
- No issue on audio.cpp asks for archives that meet the app's floors yet, so `build-audiocpp.yml` has no end date.
- On macOS `nemotron_asr` and `canary_asr` are checked only for a loader: the `macos-archive` job stages upstream's archive and transcribes nothing, so a macOS server that cannot transcribe would still ship.
- No packaging test checks that the frozen API carries the agent's `SKILL.md`; `api_inputs.py` collects it, and it was checked by hand.
- The packaged `llama-server`, `audiocpp_server` and `sd-server` are started only on the Linux runner ([#1986](https://github.com/MODSetter/SurfSense/issues/1986)).
- Only a tag's build exercises Windows signing: a dry run's Windows build is unsigned, so a lapsed Azure client secret shows on the tag first.
- No notarized macOS build has shown the microphone prompt yet: the entitlement and the usage sentence are checked only as configuration, and the Privacy › Microphone address `openSettings()` opens is unchecked on macOS 13 to 15.
- The sidecars are signed with `entitlementsInherit`, so they carry the audio-input entitlement too: once macOS lets SurfSense use the microphone, a sidecar may open it without the page, the Studio worker running a model's analysis script among them, as any process may on Windows and Linux. electron-builder gives every file but the app's own executable that one list, so narrowing it needs a signing hook of the app's own.
- What matplotlib adds to the installer has not been measured against its size gate. A scratch freeze of the worker put it at about 15 MB unpacked under `_internal/matplotlib`, plus about 0.6 MB for contourpy and kiwisolver.
- Nothing gates [the Linux floor](#the-linux-floor): no step checks the symbols the frozen backend or llama.cpp's archive need, so a runner image or a llama.cpp bump can raise it unseen.
- The static AppImage runtime has not been run on a host without FUSE or libfuse2; the release's smoke steps run `linux-unpacked`, never the AppImage.
- The AppImage's size since the switch from gzip to zstd has not been measured: its budget in `installer-size-budgets.json` is the gzip one and must be measured again on the next dry run. The first AppImage update after the switch may download most of the file.
- The rpm's budget is provisional, the deb's, until a dry run measures the rpm.
- The rpm has not been installed on EL10, Fedora or openSUSE. `(libgomp or libgomp1)` names OpenMP for all three, but whether the rest of its requires (`gtk3`, `nss`, `libnotify` and the others it restates from electron-builder) resolve under each one's package names is unchecked. A new Electron that loads libXss again would need `libXScrnSaver` back, from EPEL on EL10.
- The snap has not been built or installed, and CI never launches it: a snap that builds but cannot start would still reach the candidate channel, and `release-channels.yml` promotes it to stable. `audio-record` is not connected automatically, so speech to text needs `snap connect` or a store grant.
