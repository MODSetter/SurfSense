# App updates

The desktop app updates itself with electron-updater from the GitHub Releases of `MODSetter/SurfSense`, and only once the user has allowed it. From 2.4.0 it reads a signed manifest, `release.yml`, `release-mac.yml` or `release-linux.yml`, straight from GitHub's Latest release, and uses it only when SurfSense's update key signed it ([ADR 0091](../adr/0091-an-update-key-vouches-for-every-update-from-2-4-0-on.md)). The installer comes from the release that manifest names, and the platform's own signature check then accepts any signer the operating system trusts, so certificates in any name can follow the company's. Apps before 2.4.0 read the `stable` channel's manifests, which every release after 2.4.0 freezes on 2.4.0, the last build their checks accept ([generations](#each-generation-of-the-app)). Updates are free for everyone and carry no license logic. The legacy 0.0.x desktop app reads the same releases, so the apps are kept apart by the names of the manifests each one reads.

## Consent

Updates are a call the app makes on its own, so they are off until the user turns them on.

- A new install asks in onboarding's first step, Privacy choices, beside usage statistics, with neither answer chosen for the user ([usage statistics](usage-statistics.md#consent)). An install that finished onboarding earlier keeps the setting it had.
- The preference is `updates.json` in Electron's user data: `automatic`, false by default; `lastCheckedAt`, which Settings › Network shows as the App updates row's last call; and `lastAutomaticDay`, the UTC day of the last automatic check.
- The automatic check runs at most once a UTC day: at launch, and from an hourly tick once the day turns while the app stays open. The day is marked only once a check reads a manifest, from either host. A check that reads none is tried again on the hourly tick, at most three times a UTC day. A day's automatic checks therefore approximate the installs open that day, with no identifier on the wire; a retry after a failed check can add a second event from one install.
- Check now in Settings › About, the title bar's pill on every platform, and Check for Updates… in the macOS app menu share one check (`useCheckForUpdates`), which asks first while `automatic` is off, naming the host it asks. Allow turns `automatic` on, which also enables the daily check. Settings shows a check's progress and result. A check from the title bar or the menu, with Settings perhaps closed, reports its outcome in the title bar's pill, opened for 2.5 seconds to "Up to date", or to "Couldn't check" with a yellow info icon when it failed (`check-outcome.ts`); Settings › About holds a failure's reason. A found update shows in the title bar. A check the user did not ask for, such as the daily one, shows no result there.
- The title bar holds a small pill beside the right-panel toggle. With nothing to install it is a muted check button, a spinner while any check runs. While downloading, a ring around its arrow fills with the percentage electron-updater reports, sent to the window once per whole percent; with no size known yet, part of the ring turns. Once ready, the pill fills and restarts into the update on click. On hover or focus it widens to show its label, "Check for updates", "Downloading 64%" or "Update", with no tooltip. Where updates are locked, by policy or a package manager, it shows nothing to check and keeps no space.
- An admin policy file with `"updates": "off"` turns both off and locks the setting; Check now is disabled and says why. `"updateFeed"` names an `https` mirror instead of GitHub, and nothing else is asked. The mirror serves the installers too, and copies `release*.yml` verbatim, since their signature is checked as GitHub's is ([usage statistics](usage-statistics.md#policy) says where the file lives).
- An install a package manager owns never checks: Scoop, the AUR and Nix, whose packages write `resources/install-channel`, a snap or a flatpak, known from their environment, and a deb from SurfSense's apt repository, known from `/etc/apt/sources.list.d/surfsense.list` ([contract 5](../contracts/05-desktop-telemetry.md), part C, has the order). The setting is locked as under the policy, which names the lock when both apply. Settings › About then shows only "Updates come from" that package manager, with no daily check described and no "Show exactly what's sent". The app does not construct electron-updater at all for such an install, so a repackaged deb's `package-type` cannot start its deb updater.
- Scoop and the AUR must first be submitted with the first release that carries `install-channel/`, not earlier: an older release has no channel lock, so it would update itself out from under them ([packaging](../../surfsense_local/packaging/README.md)).
- Homebrew and winget run the release's own installer, so nothing marks them and the in-app updater stays available beside `brew upgrade` and `winget upgrade`. The Homebrew cask declares `auto_updates` inside `on_macos` only, so plain `brew upgrade` updates the Mac app while its bundle's version is older than the cask's, as it is whenever the in-app updater is off, and always updates the Linux AppImage, which has no bundle version to compare.
- `autoDownload` is false. The download starts from the `update-available` event, so it only ever follows a check the user enabled or clicked.
- A downloaded update installs when the user restarts from Settings or the title bar's pill, which calls `quitAndInstall()` once the download is ready, or else the next time they quit: `autoInstallOnAppQuit`, electron-updater's default, is set to true on purpose. The update prompt says both.

## What a check sends

A custom electron-updater provider asks `https://github.com/MODSetter/SurfSense/releases/latest/download/<channel file>`, where the file is `release.yml`, `release-mac.yml`, `release-linux.yml` or `release-linux-arm64.yml`. That request carries the IP address and `User-Agent: SurfSense`, which the outbound session sets on every request, with no version, no header of SurfSense's and no ID. The file name says which operating system asks. GitHub redirects release files, the manifest included, to its download host on `githubusercontent.com`, which also sees the IP address. The provider waits 30 s, follows the redirects and asks nowhere else: when GitHub fails, the check fails ([contract 5](../contracts/05-desktop-telemetry.md), part A).

With a policy mirror, the mirror is the only host asked, within 10 s, and that one request also carries three headers:

| Header | Example |
|---|---|
| `X-SurfSense-Version` | `2.4.0` |
| `X-SurfSense-Platform` | `win32-x64`, `darwin-arm64`, `linux-x64` |
| `X-SurfSense-OS` | `windows-11`, `macos-15`, `linux` |

It goes through an in-memory session with no cache and no cookies. The installer then downloads from the release the manifest's version names, `releases/download/v<version>/`, or from the mirror, with no SurfSense header. electron-updater keeps a random install ID in `userData/.updaterId` for staged rollouts and hands every provider an `x-user-staging-id` header; this provider ignores it, and `requestHeaders` is empty, so the ID leaves on no request. `stagingPercentage` still reads the local file. Versions up to 2.2.3 sent the ID.

Settings › About's "Show exactly what's sent" shows the last request with its URL and headers, the user agent included, kept in memory since launch, or, before the first check, the only headers a check sends: the user agent, and a mirror's three. Without the privacy bridge, an Electron main from before this provider, the update prompt and Settings describe GitHub's releases list instead.

Apps from 2.2.4 to 2.3.1 ask `updates.surfsense.com/api/updates/stable*.yml` first, with the three headers, and GitHub's `latest/download/stable*.yml` whenever that host fails; the route records one personless event per request ([ADR 0070](../adr/0070-opt-in-id-less-update-checks-and-usage-statistics.md)). From 2.4.0 nothing asks it, so GitHub's download counts of `release*.yml` are the only count of update checks ([what GitHub counts](#what-github-counts)).

This is not an `egress.require()` destination, because electron-updater runs in the Electron main process where the backend's check cannot see it ([egress](egress.md)). A development build shows the same controls and never checks.

An inactive electron-updater, such as its AppImage updater in an AppImage run without `$APPIMAGE`, answers a check with null and emits nothing. The check then puts back the state it found, idle unless an update was already downloaded, so Settings never stays on "Checking…". A check that throws keeps the `error` state electron-updater emitted first.

## Who signed an update

From 2.4.0 three checks stand between a release and an install, and the first one vouches for the others:

1. **The manifest's signature.** The first line of each `release*.yml` is `surfsenseSignature: <base64>`: an Ed25519 signature over `surfsense-update-manifest/1\n`, the file's own name and `\n`, then the rest of the file byte for byte ([`manifest-signature.ts`](../../surfsense_local/electron/src/main/update-feed/manifest-signature.ts)). The provider checks the bytes GitHub served against the two public keys the app compiles in ([`update-keys.ts`](../../surfsense_local/electron/src/main/update-feed/update-keys.ts)), and parses only the signed part. A file with no signature line, one made by another key, one changed after signing, or one signed for another platform's file fails the check: Settings shows "Could not check for updates: github.com could not be used (release.yml carries no SurfSense signature)", or "(the signature on release.yml does not match)". A signed manifest may name any URL; the key vouches for it.
2. **The installer's sha512.** electron-updater compares every download, whole or differential, with the sha512 the signed manifest names, and discards one that differs.
3. **The platform's own check**, relaxed because the key already vouched:
   - **Windows:** NsisUpdater's `verifyUpdateCodeSignature` is the app's own ([`installer-signature/any-trusted-publisher.ts`](../../surfsense_local/electron/src/main/installer-signature/any-trusted-publisher.ts)). It runs electron-updater's `Get-AuthenticodeSignature` call and accepts any status Valid, whatever the publisher's name, so 2.4.0 installs builds signed by certificates it cannot know. NsisUpdater calls it only while `resources/app-update.yml` names a publisher, so `publish.publisherName` in `electron-builder.yml` writes `SurfSense` there whatever signs the build, and the release build fails when the file names none. As in electron-updater, a PowerShell that cannot run `ConvertTo-Json` skips the check.
   - **macOS:** Squirrel.Mac installs an update only if it meets the running app's designated requirement, once in SQRLUpdater and again in ShipIt. From 2.4.0 every signed file carries [`build/designated-requirement.txt`](../../surfsense_local/electron/build/designated-requirement.txt): `anchor apple generic` with the Developer ID CA and leaf markers, and no team or identifier clause, so a Developer ID build from any team installs. electron-builder applies `mac.requirements` to every file it signs, helpers and frameworks included, which is why it names no identifier. Apps before 2.4.0 carry the default requirement, which names the company's Team ID.
   - **Linux** checks no signature beyond the manifest's.

A first build from another Apple team prompts once for the keychain item behind `secret.bin`. Refused, the old file is kept as `secret.bin.unreadable` and tried again at each launch rather than overwritten ([connections](connections.md)).

## Update size

Downloads are differential: electron-updater fetches only the blocks that changed, using the `.blockmap` files electron-builder publishes with each release. The app's provider asks for one byte range per request, as electron-updater's `GitHubProvider` does (`update-feed/surfsense-feed-provider.ts`): GitHub's release CDN serves a single range and answers several with 501, which would turn every update into a whole download. Any failure falls back to downloading the whole file, so the result is always the published file.

A proxy or antivirus web shield that drops the `Range` header answers each of those requests with the whole file. electron-updater 6.8.9 writes that body out once per range and checks the sha512 only at the end, so a Windows update would keep downloading until the disk filled. [`patches/electron-updater@6.8.9.patch`](../../surfsense_local/electron/patches/electron-updater@6.8.9.patch), applied by pnpm through `patchedDependencies` in `electron/pnpm-workspace.yaml`, makes any reply other than 206 end the differential attempt at the first request, and the update then downloads whole, as it did before differential downloads were on. It covers the AppImage's blockmap read too. `scripts/electron-updater-ranges.test.mjs` runs electron-updater against a server that ignores `Range`. An electron-updater upgrade has to carry the patch over, because it names 6.8.9.

| Platform | Patches | Typical update |
|---|---|---|
| Windows | `installer.exe` in `%LOCALAPPDATA%\surfsense-local-electron-updater\`, the copy of the installer every install leaves there | about 128 MB instead of 1.16 GB (v2.2.2 → v2.2.3, planned from the real blockmaps; 129 MB measured end to end the other way) |
| macOS | `update.zip` in `~/Library/Caches/surfsense-local-electron-updater/`, the copy of the last downloaded zip | whole (1.28 GB) until a first update leaves `update.zip`, then about 187 MB (planned) |
| AppImage | the running AppImage, through the blockmap embedded in it | about 42 MB |
| deb | nothing; electron-updater always downloads a deb whole | 1.28 GB |
| rpm | nothing; downloaded whole, like the deb | the whole rpm |

An app at 2.2.3 or earlier still downloads its next update whole, because those versions turn differential downloads off.

### macOS: the 1 GiB limit

However few bytes the download fetches, electron-updater hands the whole rebuilt zip to Squirrel.Mac, Electron's own updater, through a loopback server, and Squirrel.Mac installs it. Before Electron 44.7, Squirrel.Mac held that zip in one in-memory buffer; past 1 GiB the buffer's next growth asks for 2 GiB, Electron's allocator refuses it by design, and the app dies with `EXC_BREAKPOINT` and no `error` event ([electron/electron#55089](https://github.com/electron/electron/issues/55089)). Measured on Electron 44.2.0: 1023 MiB installs, 1025 MiB crashes, whatever the free memory. Every Mac zip from 2.1.0 to 2.3.0 is over 1 GiB (1.13–1.34 GB), so those versions never installed an update themselves, and an app holding a finished download crashed shortly after each launch.

Electron 44.7.0 streams the zip to disk instead. `electron/package.json` therefore pins `44.10.1`, the version this was tested on: it fetched a 1.13 GB zip at about 35 MB of memory. The fix lives in the running app, so a Mac app on 2.3.0 or earlier still crashes on any update over 1 GiB. Nothing holds those apps back: no smaller bridge release, no feed rule, no renamed manifest. Their users install the new version once from the DMG or with `brew upgrade`, as the release notes, the downloads page and the user docs say, and the data folder carries over.

Fewer bytes do not always mean a shorter wait. A Windows update is about 800 range requests made one after another, with a 1 s pause after every 100; 129 MB took 47–69 s in testing. On a link faster than roughly 150–200 Mbit/s the "Downloading" state can therefore last longer than a whole download would. On macOS electron-updater keeps the last download as `update.zip` (about 1.28 GB), the base of the next update. From a download until the installed version's first launch, which frees `pending/` (below), the cache holds that copy as well as the one in `pending/`, about 2.55 GB in all.

On Windows a differential update needs `installer.exe` and `current.blockmap` to describe the same version. Every install, through the updater or by hand, overwrites `installer.exe` with the installed version, but electron-updater replaces `current.blockmap` with each download's, copying it out of `pending/` right after `update-downloaded`. A download that is not installed yet, or a version installed by hand, breaks that pairing: the patched file fails its sha512, and the update downloads whole after the wasted differential attempt. Without the file, electron-updater fetches the installed version's blockmap (about 1 MB) from that version's release, which fails once the release is pulled, and the update again downloads whole. So on `update-downloaded` `updater-cache/` records the version in `current-blockmap-version.json` beside the blockmap, and before every check it deletes both unless the record names the installed version. An update installed through the updater therefore keeps its own blockmap, and the next update does not depend on its release staying published. A download whose blockmap could not be fetched goes whole and saves no blockmap, so it clears the record instead. A second download in one session reuses `pending/` without emptying it, so on `update-available` `updater-cache/` also deletes any blockmap an earlier download left there, unless `pending/` already holds the offered version. On macOS `update.zip` and `current.blockmap` normally come from the same download and stay together, with no record (see Known gaps); Linux uses neither.

electron-updater downloads into `pending/` beside that base and empties it only when a download fails or a later launch downloads another version, so the installer of the version just installed would sit there until the next update. The app records the downloaded version in `pending/downloaded-version.json`. At launch `updater-cache/` empties `pending/` unless it holds a version newer than the running app. A download with no record was made by an app from before this one, so it is emptied too; a record that cannot be read keeps the download. It is also emptied when a check finds nothing newer than the running app, for instance after a release is pulled, unless this session was offered an update, since quitting installs that download. Every check waits until this tidying is done, so a download never lands in a folder being emptied. `installer.exe` and `update.zip` stay, because they are the base of the next update.

## Each generation of the app

| Installed | Reads | Is offered |
|---|---|---|
| Legacy 0.0.x | `latest*.yml` from `/releases/latest` | v0.0.40, by the bridge below |
| 2.0.0 | `stable*.yml` of `/releases/latest`, through electron-updater's `GitHubProvider` | after 2.4.0, 2.4.0: the frozen `stable.yml` and `stable-mac.yml` carry `tag: v2.4.0`, and that provider downloads from the tag |
| 2.0.1 to 2.2.3 | `stable*.yml` of the newest entry in the releases feed (`allowPrerelease`), falling back to `latest*.yml` | the same, through the same tag |
| 2.2.4 to 2.3.1 | `stable*.yml` through `updates.surfsense.com`, then GitHub | the same: these build installer URLs from the manifest's version, 2.4.0 |
| 2.4.0 and later | signed `release*.yml` from `/releases/latest` | the newest build the update key vouches for |

Linux apps before 2.4.0 check no signature, so `stable-linux.yml` is each release's own and they skip the hop. Mac apps on 2.3.0 or earlier still crash on any update over 1 GiB ([below](#macos-the-1-gib-limit)).

`publish.channel: stable` in `electron-builder.yml` gave the 2.x app its own manifest names, so it never wrote the legacy feed; its providers never read `latest*.yml`, which `updates.surfsense.com` also refuses with a 404. Since 21 Sep 2026 GitHub's Latest names the newest 2.x release, so a legacy client asking `/releases/latest` lands on a 2.x release. The `legacy-update-bridge` job in `release-local.yml` answers it: on a tag push, once all three builds succeed, it downloads v0.0.40's three `latest*.yml`, prepends `tag: v0.0.40`, checks the tag and version lines, and uploads them onto the new release. electron-updater lets a manifest's `tag` override the release it resolved and builds download URLs from it, so legacy clients are offered v0.0.40 and fetch it from v0.0.40's own assets, with nothing duplicated. That was verified against electron-updater 6.8.3, which every legacy release from v0.0.30 on pins. The frozen `stable` files use the same mechanism for 2.0.0 to 2.2.3, under electron-updater 6.8.9.

Without the bridge every legacy update check 404s on a missing `latest*.yml`. The job must therefore be green on every release, and must stay while 0.0.x clients still check in.

Versions from 2.0.1 to 2.2.3 take the newest entry of the releases feed rather than `/releases/latest`, even when it is a prerelease or a bare tag with no release. While they are in the field this repository never publishes a prerelease-semver tag, and after the last release never pushes a bare tag either: a tag-only entry would make every one of their checks 404 until another release came after it. Testing happens in a throwaway repository or through an admin mirror. The 2.2.4 to 2.3.1 provider and the 2.4.0 one read only `releases/latest/download`, which GitHub serves from the release marked Latest.

## What a release carries

A `v[1-9]*` tag equal to `surfsense_local/VERSION` starts the workflow, which fails when the two differ. The repository variable `UPDATE_HANDOVER_VERSION` names the handover release, 2.4.0, and decides the path; a tag before it is refused ([`RELEASE.md`](../../surfsense_local/RELEASE.md)).

- **The handover release** builds on the `stable` channel. electron-builder uploads the installers and its three `stable*.yml` onto a draft, `update-manifests` signs copies of them as `release*.yml` with the secret `UPDATE_SIGNING_KEY`, and the bridge job adds the three `latest*.yml`.
- **Every later release** builds with `-c.publish.channel=release`. `update-manifests` signs its own `release*.yml`, writes `stable-linux.yml` as their unsigned Linux copy, and freezes `stable.yml` and `stable-mac.yml`: 2.4.0's own, downloaded from its release, with `tag: v2.4.0` prepended and the tag and version lines checked, as the bridge does.
- **A release with no signed Windows build** (`WINDOWS_SIGNING=off`) uploads none of the Windows build and carries Latest's signed `release.yml` forward, so Windows apps stay on the last signed version until a certificate signs again.

`update-manifests` checks each signature against the keys the app compiles in, so a wrong secret fails the release rather than every update. `update-gate` then reads the draft as each generation will: the nine manifests are there, `release*.yml` verify, the frozen files name 2.4.0, and 2.4.0's installers still hash to what they say ([`check-release-manifests.mjs`](../../surfsense_local/electron/scripts/update-signing/check-release-manifests.mjs)). The build legs have already failed on an `app-update.yml` with no publisher, and on a Mac app without the designated requirement, Gatekeeper's yes or a stapled ticket. The draft is published only once every one of those jobs is green, because publishing makes it Latest and every updater reads its manifest off it at once. 2.4.0's release stays as it is forever: its assets are what the frozen files pin.

| Platform | Installer | Updates through |
|---|---|---|
| macOS arm64 | `SurfSense-arm64.dmg` | `SurfSense-arm64.zip`; electron-updater needs the zip, so the target is `[dmg, zip]` |
| Windows x64 | `SurfSense-Setup.exe` | the same NSIS installer |
| Linux x64 | `SurfSense.AppImage` | the AppImage |
| Linux x64 | `SurfSense.deb` | the deb, through electron-updater's deb updater, which it picks from `resources/package-type`; apt instead once the apt repository is set up |
| Linux x64 | `SurfSense.rpm` | the rpm, through the rpm updater, picked the same way |
| Linux x64 | the `surfsense-local` snap, uploaded to the Snap Store by its own job and not to the release | snapd, from the Snap Store; the app never checks |
| Linux x64 | `SurfSense.deb` from the flat apt repository on the release (`Packages`, `Packages.gz`, `Release`, `Release.gpg`, `InRelease`, `surfsense-archive-keyring.gpg`) | apt, once `/etc/apt/sources.list.d/surfsense.list` exists; the app never checks |

The apt source is `deb [signed-by=/usr/share/keyrings/surfsense-archive-keyring.gpg] https://github.com/MODSetter/SurfSense/releases/latest/download/ ./`, so apt, like the updater, reads the release marked Latest.

## What GitHub counts

A daily job saves every asset's download count, and says which client each count measures: people, the 2.x updater or legacy clients ([release stats](release-stats.md)). From 2.4.0 an update check reaches only GitHub, so each `release*.yml` count is a check by an app on 2.4.0 or later; release stats still file those as `other`.

## Download links

Every installer link outside the app goes through one redirect on the website, `/downloads/<platform>` for `windows`, `mac`, `linux-appimage`, `linux-deb` and `linux-rpm` (`www/app/(home)/downloads/[platform]/route.ts`). It answers a 302 to the GitHub asset, so the bytes still come from GitHub, and counts the download on the way: a personless `installer_download` event with the platform, `src` (where the link was: `site`, `readme`, `email`, `app`, `pricing`, else `other`), the version and the country Vercel derives, sent from the server so a content blocker does not hide it. Obvious bots and mail scanners, matched by User-Agent, are redirected but not counted. The response is `no-store`.

The redirect's `v` pins a tag: the license email (`backend/license/release.py`) sends `src=email&v=<tag>`, so a mail already sent keeps offering the build it was sent for. Without `v`, or with a tag older than 2.0.2, it uses `APP_RELEASE_VERSION` in `www/features/downloads/app-release.ts`; `surfsense_local/scripts/bump-version.sh` writes that pin into both files, and it moves when the web app and the backend are deployed with the bump. The site's `/downloads` grid (`src=site`) and every README's table (`src=readme`) use the pin, so they follow a release on deploy rather than on GitHub's Latest.

A tag counts only once GitHub serves it. The redirect checks it against the newest 30 published releases from the GitHub API, cached for an hour, and otherwise sends the link to `/releases/latest/download/<file>` with the version recorded as `latest`. That covers release day, when the bump is deployed while its release is still a draft whose assets 404 for anyone signed out (about an hour, longer when a release run fails), a tag that was never published or is older than those 30, and a GitHub API that cannot be reached. Artifact names have carried no version since 2.0.2, which is why the redirect builds each URL from a tag and a fixed file name and why Latest has every file but the rpm, which exists only from the first release that builds it. Until that release is Latest, `/downloads/linux-rpm` falls back to a file Latest does not have, and still counts the download. Renaming an installer breaks every link already sent.

## The legacy app

`surfsense_desktop/` left the tree on 17 Sep 2026; its source is at tag `archive/hosted-2026-09`. v0.0.40 caps its updater below 1.0.0, downloading only an offered version that starts with `0.`, and at startup reads `sunset` from the hosted `/health` to load the live `/sunset` page ([contract 4](https://github.com/MODSetter/SurfSense/blob/261edd605ba67f19e47a5e1b6852e2ef045235af/docs/contracts/04-sunset-flag.md), [sunset](https://github.com/MODSetter/SurfSense/blob/261edd605ba67f19e47a5e1b6852e2ef045235af/docs/architecture/sunset.md)). The cap is not a live guard: it hangs off `update-available`, and a release without `latest*.yml` fails the check with a 404 before that event fires. The channel names keep 2.x manifests away from legacy clients, and the bridge keeps their checks from failing.

## Known gaps

- The deb updates itself through electron-updater's deb updater unless SurfSense's apt source is configured, and the rpm through its rpm updater. Neither has been run on an installed package: each downloads the whole package and installs it as root through `pkexec` or `sudo`.
- The macOS differential path has only been planned from the real blockmaps, not run end to end. A failure there falls back to a whole download.
- On macOS a download whose blockmap could not be fetched replaces `update.zip` but not `current.blockmap`, so the next update downloads whole after a wasted differential attempt.
- Uninstalling leaves `%LOCALAPPDATA%\surfsense-local-electron-updater\` behind, with the 1.16 GB `installer.exe` in it.
- A Mac app on 2.3.0 or earlier crashes when it installs any later release, shortly after each launch while automatic checks are on, until its user reinstalls by hand.
- No signed, notarized build on Electron 44.10.1 has yet installed an update over 1 GiB end to end; only Squirrel.Mac's download of one was tested.
- Removing the app on macOS leaves `~/Library/Caches/surfsense-local-electron-updater/` behind, with the 1.28 GB `update.zip` in it.
- Nothing takes an installed previous version through an update before users get it. The updater reads only published releases, so [`RELEASE.md`](../../surfsense_local/RELEASE.md)'s check from the previous version is by hand: the draft's installer over that version before publishing, the update itself only after. The handover's own tests, through an admin mirror and a throwaway repository, are in [`UPDATE-HANDOVER-TESTS.md`](../../surfsense_local/UPDATE-HANDOVER-TESTS.md).
- The handover is not yet proven on signed builds: notarization and Gatekeeper with the team-less designated requirement, Squirrel.Mac installing a build from another team, and NsisUpdater installing an installer from another publisher outside the tests.
- `updates.surfsense.com` answers a frozen `stable*.yml` with a 502, because its route refuses the `tag:` line. Apps from 2.2.4 to 2.3.1 then read GitHub directly and still reach 2.4.0, one request later.
- A release with no Windows build leaves the website's Windows link, the READMEs and `install.ps1` pointing at a Latest release that has no Windows installer. `install.ps1` also pins `CN=SurfSense`, so the first installer signed under another name needs it widened.
