# Agent

A chat thread can be the agent's. opencode, started by Electron, then answers it in steps: it finds passages with SurfSense's search, reads a folder of the workspace's extracted text with its own tools, cites what it found as a chat answer does, makes Word documents, PDFs, PowerPoint decks and Excel workbooks as versioned scripts that SurfSense runs and lets it look at, starting a Word document or a deck from the user's own file when asked, starts other Studio jobs, writes what else it produces to an output folder, and reaches every model through SurfSense. It has no shell ([ADR 0039](../adr/0039-document-scripts-run-without-approval.md)). Which engine a thread gets is decided when the thread opens. No model is on the tested list yet, so opencode is off: no installer or dev run carries it unless `SURFSENSE_LOCAL_OPENCODE_ENABLED=1` is set when it is staged, and even then only a developer switch lets a model in. How to run it from a dev build is in [07-dev-setup](../proposals/file-agent/07-dev-setup.md).

**Code:** [`surfsense_local/backend/modules/agent/`](../../surfsense_local/backend/modules/agent/), [`surfsense_local/electron/src/main/sidecars/opencode.ts`](../../surfsense_local/electron/src/main/sidecars/opencode.ts), [`surfsense_local/electron/src/main/docx-snapshot/`](../../surfsense_local/electron/src/main/docx-snapshot/), [`surfsense_local/electron/scripts/opencode/`](../../surfsense_local/electron/scripts/opencode/), [`surfsense_local/frontend/src/features/agent/`](../../surfsense_local/frontend/src/features/agent/), [`surfsense_local/frontend/src/features/docx-snapshot/`](../../surfsense_local/frontend/src/features/docx-snapshot/)
**Decisions:** [ADR 0039](../adr/0039-document-scripts-run-without-approval.md), which supersedes [ADR 0028](../adr/0028-model-written-code-runs-with-approval.md) in part. The remaining work is in the [agent proposal](../proposals/agent/README.md) and the [file agent proposal](../proposals/file-agent/README.md).

## Which threads get it

A new thread is the agent's when the selected text model is in `TESTED_MODELS`, or `SURFSENSE_LOCAL_AGENT_UNTESTED_MODELS=1` is set in the environment Electron starts the API from, and the model is known to call tools: llama-server reports `supports_tool_calls` for a local model's template, or the remote catalog records `tool_call: true` for the model under its connection's catalog provider. A runtime that cannot be read counts as no. A catalog that says nothing counts as no for a tested model and as yes under the developer switch, because the packaged catalog lags the providers and a model released after it is the one most worth trying; a stated `tool_call: false` keeps a model out either way ([`engine_choice.py`](../../surfsense_local/backend/modules/agent/engine_choice.py)). `TESTED_MODELS` is empty: a model goes on it once it passes the agent test at a window of 32,768 tokens or more ([proposal](../proposals/agent/01-which-engine.md#what-tested-means)). When opencode is not staged, or does not become ready, the thread opens as a chat. A thread keeps its engine; its row stores the opencode session that holds its turns ([data model](data-model.md)). Once the selected model changes to one that fails the check, a turn sent to the thread is refused with `409` before any prompt is sent: the user chooses another model or starts a new chat.

## From a thread to a running opencode

1. **Electron, at boot.** Where an opencode is staged, Electron picks its port, a random password and a random Word snapshot key, passes them to the API alone, and removes any `agent/opencode.json` the last run left. opencode does not start yet. Where none is staged, Electron passes nothing, and the API mounts none of the routes opencode calls or that answer it: the model endpoint, the tool endpoint, the permission answer and the Word snapshot routes.
2. **The API, when a thread first needs the agent.** `ready_opencode()` reads the selected model's window: what llama-server loaded a local model with, or the `context` the remote catalog records, else 32,768. It reads whether the model reads images ([Image input](#image-input)). It writes `<data>/agent/opencode.json`, readable by this user only, and only when its contents change.
3. **Electron, on that file.** Checked every 2 seconds: opencode starts once the file exists and stops when it goes. A crash restarts it, at most once every 10 seconds. A rewrite does not restart it.
4. **The API, until opencode serves it.** opencode reads its configuration per folder, the first time the folder is used, and keeps what it read. So the API checks the running server's version is `1.18.34`, reads `GET /config`, and calls `POST /global/dispose` once if what is loaded is not the launch key, window and image input just written. It returns when they match, or after 60 seconds with "not ready". Every call has a timeout, because opencode accepts a connection a moment before it answers it.

## The configuration

| Setting | Value |
|---|---|
| Provider | one, `surfsense`, on `@ai-sdk/openai-compatible`, at `http://<API host>:<API port>/agent/model/v1`, with the launch key as its API key; `enabled_providers` lists only it |
| Models | `model` and `small_model` both name the selected model, so nothing asks for a second one the router would load in its place. Its entry declares `tool_call`, and image input (`modalities.input` `["text", "image"]` and `attachment: true`) only for a model that reads images |
| Limits | `context` and `input` are the window W; `output` is min(W/4, 32,000); `compaction.reserved` is min(output, max(W/10, 8,192)), with `compaction.auto` on |
| Waiting | `headerTimeout` off and `chunkTimeout` 30 minutes, because a local model can take minutes before its first byte |
| Skills | `skills.paths` names the shipped skills folder, inside the API's own files when frozen |
| Permissions | `bash` is denied; `edit` and `write` are allowed under a thread's `outputs/` and denied elsewhere: the allow matches any path holding `/agent/threads/*/outputs/`, so denies after it refuse such a path under a thread's `sources/`, `.opencode/` (which opencode loads agent definitions from), its tool-output folder and the skills folder, and any file named `AGENTS.md`, `CONTEXT.md` or `CLAUDE.md` in three spellings, since the match ignores case only on Windows; another thread's `outputs/` matches the allow but is outside the thread's folder, which `external_directory` refuses; `external_directory` is denied except the skills folder, with any path holding `/../` denied after that allow; `skill` allows only `surfsense-documents`; `webfetch`, `websearch`, `task` and `question` are denied; SurfSense's tools run without asking, by opencode's default |
| Agent | `surfsense`, the default, whose prompt replaces opencode's coding prompt with how to work on the user's sources ([`prompts/agent.md`](../../surfsense_local/backend/modules/agent/prompts/agent.md)) |
| Off | `share`, `snapshot`, `autoupdate` |

The API makes a new launch key at every start ([`launch_key.py`](../../surfsense_local/backend/modules/agent/launch_key.py)), so a configuration from an earlier run never opens the model endpoint or the tools. opencode adds its own allow for its tool-output folder after these rules, where it keeps a long tool result for the agent to page through; nothing here denies it.

## The documents skill

[`skills/surfsense-documents/SKILL.md`](../../surfsense_local/backend/modules/agent/skills/surfsense-documents/SKILL.md) is SurfSense's own text. It teaches the script contract (write the file to `OUTPUT_PATH`, open source images at `IMAGES_DIR/<name>.png`, a template's copy at `TEMPLATE_PATH`, python-docx for Word, ReportLab for PDF, python-pptx for decks, xlsxwriter or openpyxl for workbooks, matplotlib for charts saved as a PNG and placed), clean-document habits (built-in heading and list styles, real tables with a header row, A4 unless the user is in the US or Canada, images at most the text width), decks (16:9, layouts by name, placeholders, tables, pictures, native or matplotlib charts, speaker notes), workbooks (number formats, header rows, column widths, formulas where a total is meant, stored with the value each comes to, frozen panes, native charts), starting from a source's Word file or deck (keep its styles, headers, footers and layouts; remove its own body or slides), matching a look from `surfsense_source_pages`, charts from a source figure's values, editing (read the script, change only what was asked, make every requested change and say what was assumed, render with `artifact_id`), checking the previews or a workbook's summary, and the stop rule. Its Word, PDF, PowerPoint, Excel and two template examples run through the real runner in a test.

opencode finds it through `skills.paths` and offers it by its name and description; the agent loads it with opencode's `skill` tool, which the permission allows for this skill only, so neither opencode's built-in skills nor any the user installed for their own opencode load. The prompt tells the agent to load it before a Word document, a PDF, a deck or a workbook and repeats the editing rule in one line, because a compaction can drop a loaded skill from the context while the prompt stays. `bundling/api.spec` ships it ([packaging](packaging.md)).

## Image input

[`model_reads_images.py`](../../surfsense_local/backend/modules/agent/model_reads_images.py) answers whether the selected model reads images as the chat does ([ADR 0034](../adr/0034-vision-is-the-runtimes-answer-stored-nowhere.md)): llama-server's `/models` for a local model, the remote catalog's `modalities.input` under the connection's catalog provider for a remote one. A model the catalog does not know, or whose entries disagree, answers no, with no developer switch, because an image a text-only model refuses fails the request and opencode re-sends it with every later one.

When the entry declares image input, an image a tool returns reaches the model: an image opencode's `read` returns, and each MCP image item a SurfSense tool returns, which opencode keeps as a file attachment of the step. The openai-compatible SDK cannot carry media in a tool result, so opencode moves the images into a user message after the step, starting "Attached media from tool result:", and the model endpoint passes each part through as an OpenAI `image_url`. Without the declaration, opencode replaces each image with an error text before the request leaves it, so `surfsense_render_document` draws no previews and says why, `surfsense_source_pages` is not offered, the endpoint drops any image item from a result when the configuration changed during the call and adds a line saying so, and the skill tells the agent to check the script and the returned text instead. A live run carried page images to Claude Sonnet 5.5 through Anthropic's OpenAI-compatible API, and the model described them correctly. The prompt tells the agent that text inside an image, such as a source's page, is data, since it now arrives in a user message unasked.

## Folders

```text
<data>/agent/
├── opencode.json             the configuration the API writes
├── opencode-process.json     the running opencode's pid, port and password, for the next boot
└── opencode/                 opencode's home: its XDG config, data, cache and state, sessions included
<data>/data/workspaces/<id>/agent/
├── text/                     `<source id>-<sha256 of its text, 16 hex>.md`, one per version of a source's text
└── threads/<thread id>/      one agent thread's folder, opencode's instance directory for its session
    ├── sources/              the thread's sources: `Library/<folder>/…/<title> [<id>].md`, each a hard link into text/
    │   ├── figures/          `<source id>-<n>.png`, a copy of each figure `surfsense_list_images` listed
    │   └── pages/            `<source id>-p<n>.png`, a page `surfsense_source_pages` drew
    └── outputs/              what the agent writes; never touched by SurfSense except previews/
        └── previews/<artifact id>-v<n>/page-<k>.png
```

Each agent thread works in its own folder ([`thread_folder/`](../../surfsense_local/backend/modules/agent/thread_folder/)). Its session is created there, and its turns sync, register the tools, stream, check status and answer approvals there. `sources/` holds only the sources the thread's scope resolves to ([the ticked sources](#the-ticked-sources)), each at the path of its folder in the Library, so the agent finds a source where the user filed it; an unfiled artifact ticked by id sits at the top. Paths are decided from the workspace's live folders and the source's own row, never the scope, so a tick never moves another source ([`mirror_path.py`](../../surfsense_local/backend/modules/agent/thread_folder/mirror_path.py)): characters a file system refuses become `_`, leading and trailing dots and spaces go (a leading dot would hide a folder from `grep` and `glob`), a name is cut at 100 characters, a Windows device name, an instruction file's name, `outputs` (so no mirrored folder passes for the agent's on macOS, where the edit rules match case as written but the disk ignores it) or a top-level `figures` or `pages` gains `_`, siblings equal once made safe get ` [f<folder id>]`, and a folder whose directory would pass 247 characters, or leave under 24 for a file within 259, has the deepest uncut folder of its chain cut to 8 characters and its id, so a folder is always one directory. A title is then cut to fit; past that the file goes to the top as `<8 characters> [<id>].md`, and one that fits nowhere is left out with a warning. The `[<id>]` always stays.

Before each turn the folder is brought in line in short transactions, never writing a file inside one ([`sync.py`](../../surfsense_local/backend/modules/agent/thread_folder/sync.py)): the layout and the sources with text in one, then their text 200 at a time. Each text is written once to `text/` under its digest and hard-linked into the thread, so threads share one file per version and Defender scans it once; on a disk without hard links (FAT, exFAT) each thread gets a copy, logged once. Anything else in `sources/`, file, folder, link or junction, is removed without following links, empty folders are pruned, and figures and pages of sources no longer in scope go. Anything under `outputs/` named like an instruction file is renamed with a trailing `_`. At most every 10 minutes, cache files older than 10 minutes that no thread links are deleted. Syncs of one thread are serialised; two threads syncing one changed source at once may leave one a turn behind. The first sync in each workspace per run removes the folders every thread once shared, `agent/sources/` and `agent/outputs/previews/` (the rest of `agent/outputs/` stays until the workspace goes), and any `threads/<n>/` that is no agent thread of the workspace.

Deleting a thread aborts and deletes its session, disposes its opencode instance with `POST /instance/dispose?directory=<thread folder>`, deletes the row (its artifacts stay), then removes the folder once any sync of it has finished; a turn that reaches its sync after that answers `404` and writes nothing. Deleting a workspace disposes each of its threads' instances first.

**Legacy threads.** A thread opened before threads had folders has its session in `agent/`, and a session cannot move. Such a thread is told apart by its session's directory (`GET /session/{id}`) and stays readable, but a turn is refused with `409` before anything is sent: "This agent chat was started before each chat kept its own sources. Start a new chat to continue." ([`legacy_thread.py`](../../surfsense_local/backend/modules/agent/agent_threads/legacy_thread.py)). The screen shows that sentence in the user's language under the unsent message, with "Start a new chat" in place of Retry ([`outdated-thread.ts`](../../surfsense_local/frontend/src/features/agent/outdated-thread.ts)). Its old files in `agent/outputs/` stay until the workspace is deleted. Moving the data folder makes every agent thread legacy.

## The model endpoint

`POST /agent/model/v1/chat/completions` ([`model_endpoint/`](../../surfsense_local/backend/modules/agent/model_endpoint/)) is opencode's only way to a model. It refuses a request without this process's launch key with `401`, resolves the selected model on every request, and marks it in use while the turn runs.

- **Local:** llama-server's router at `{llamacpp_base_url}/v1`, under the selected model's name.
- **Remote:** the connection's URL with its own key, once `egress.require()` allows its host; a refused host answers `403` naming it, before any connection opens ([egress](egress.md)).
- **The request:** `tools` and `tool_choice` pass through; every `system` and `developer` message is joined into one system message first, because local chat templates want one there; assistant turns with no text and no call are dropped; control tokens such as `<|im_end|>` in user and tool text are split by a zero-width space, because tool results carry the user's documents. Image parts pass through untouched.
- **The reply:** the model's own status and body pass through, so opencode reads a full window from llama-server's own wording and compacts. SurfSense's own errors are `{"error": {"message": …}}`. Every stream ends with `[DONE]`, added when the model leaves it out. There is no limit on waiting; opencode's configuration sets its own.

## SurfSense's tools

`POST /agent/tools/workspaces/{workspace_id}/threads/{thread_id}` ([`tool_endpoint/`](../../surfsense_local/backend/modules/agent/tool_endpoint/)) answers opencode's MCP client: MCP `2025-11-25` over Streamable HTTP, stateless and JSON only, written without an MCP library. It answers `initialize`, `tools/list`, `tools/call` and `ping`, and `202` to a notification. It refuses a request without the launch key with `401`, one carrying an `Origin` header, as a web page's does, with `403`, another protocol version with `400`, a workspace that does not exist with `404`, and `GET` with `405`. The workspace and thread in the path scope every tool, because a tool call names neither its folder nor its session ([the ticked sources](#the-ticked-sources)); the old address without a thread answers `404`.

| Tool, as the model sees it | Takes | Does |
|---|---|---|
| `surfsense_search_sources` | `query` | the chat's own `retrieve()` over the thread's sources; up to 5 passages, each as `<passage cite="[<chunk id>]" source="sources/<path>" lines="<a>-<b>">`, the path being the source's in the thread's folder and the lines that file's |
| `surfsense_create_artifact` | `format`, one of Studio's formats except `docx`, `pdf`, `pptx` and `xlsx`; `source_ids`, the numbers at the end of the source files' names; `instructions`, at most 2,000 characters | Studio's own `create_artifact_job()`, which returns at once with the artifact pending. A source not ticked for the turn is refused. Asked for one of those four, it refuses and names `surfsense_render_document`, because Studio's draft keeps no script to edit |
| `surfsense_render_document` | `title`; `format`, `docx`, `pdf`, `pptx` or `xlsx`; `script`; `artifact_id`, to make the next version of, refused for a version that keeps no script, such as Studio's Markdown, which Refine rewrites; `images`, names from `surfsense_list_images`, of ticked sources only; `template_source_id`, a ticked source's own `.docx` for `docx` or `.pptx` for `pptx`, kept by later versions | runs the script as a new version in Studio and waits for it ([below](#documents-the-agent-makes)) |
| `surfsense_read_document` | `artifact_id`, of any version; `offset`, an optional 1-based line to start from | the newest version's number, artifact id, title, format, status and the images it places, and its script in pages of at most 1,000 lines and 40,000 bytes under "Script, lines a-b of n", ending with the offset of the next page, so a result stays under opencode's truncation limits ([`script_page.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/script_page.py)) |
| `surfsense_list_images` | `source_ids` | each source's figures, one line each: its name, size in pixels, page and caption when known, and its copy under `sources/figures/` to open with `read`; or that the source has none, is not in this workspace, or has its figures being extracted, which queues the figures-only pass ([documents](documents.md#figures)). A source not ticked for the turn is refused |
| `surfsense_source_pages` | `document_id`; `pages`, at most four page or slide numbers from 1, the first ones when left out | a PDF, Word or PowerPoint source's own pages as images with the result, in ascending order, with the source's page or slide count; copies at most 1,000 pixels on their long side stay in `sources/pages/<id>-p<n>.png` for a closer look ([below](#source-pages)). Offered only when `opencode.json` declares image input. A source not ticked for the turn, an image, a note or any other kind of file is refused in a sentence saying what to use instead |

The schemas are flat, in a fixed order, and the same on every turn, and a test pins them. A call the tool cannot carry out comes back as a tool error the model reads: no query, no sources named, Studio's own reason such as "Needs a chat model", or a search before onboarding has chosen an embedder or while its files are missing, which points the model at `grep`. A source's own text loses any `passage` tag, so it cannot make up a label. A tool runs in one transaction off the event loop, except a tool that waits on another process or does slow file work (`waits` on [`tool.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/tool.py)), which commits its own short transactions so the write lock never stays held meanwhile: `surfsense_render_document`, `surfsense_list_images`, which reads each source's index once and copies the figures after its commit, and `surfsense_source_pages`, which may wait on Electron. A tool returning images (`needs_image_input`) is listed and run only for a model that reads images; it comes last, so the rest keep their order. A result is one text item, then, for `surfsense_render_document` and `surfsense_source_pages`, one MCP image item per page (`{type: "image", data, mimeType: "image/jpeg"}`, a `ToolResult` in [`tool.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/tool.py)); an error is text only, since opencode drops an error's images.

Before each turn the API adds the tools to the thread's folder with opencode's `POST /mcp?directory=…`: the server `surfsense`, the thread's URL, the launch key as a header, OAuth off, and a call timeout of 200 seconds, where a call would otherwise get the MCP SDK's 60 ([`registration.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/registration.py)). opencode keeps it in memory for that folder's instance alone and drops it when it reloads, so it is added on every turn, nothing is written to `opencode.json`, which every folder shares, and two threads' turns at once each keep their own. opencode then lists the tools and names them `surfsense_<tool>`. When it cannot reach them, the turn runs with its own tools and the API logs why. The chat panel shows their steps as "Searched the sources for …", "Started … in Studio", "Created *Title* v1", "Read the script behind a document" and "Looked for images in 2 sources".

## Documents the agent makes

[`render_document.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/render_document.py) gives each call one deadline when it starts, 190 seconds, 10 inside the registration's timeout, so opencode never reports a bare timeout for a version that was made:

1. **Create.** Studio's script-documents service makes the version in one short transaction: v1 of a new document, or the next version of the one `artifact_id` names, and queues Studio's job to run it ([studio](studio.md#script-documents)). A refusal, such as an image name the workspace does not hold, comes back as a tool error.
2. **Wait.** Up to 150 seconds, within the deadline, it looks at the version's status every half second, each look its own committed read; a look that finds the database locked rolls back and tries again on the next ([`job_outcome.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/job_outcome.py)).
3. **Ready.** The result starts with `Rendered artifact <id>, version <n>: <title>` ([`rendered_label.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/rendered_label.py)), then the page count of a PDF, the slide count of a deck, the sheet count of a workbook or the paragraph count of a Word file, the first 1,500 characters of its text, and up to four page or slide previews as images after the text, in page order, or why there are none. The text names the pages shown ("come with this result as images, in order: page 1, page 2"), tells the agent to look at every one, and names the folder of the larger copies once rather than each path, so the agent is not invited to open every page again with `read`. A page that cannot be encoded is left out and named with its path; when none can be, the result says there are no previews. A Word version's text adds that Word previews leave out headers and footers, a deck's that the slide viewer can differ from PowerPoint. A workbook has no previews: its result carries its whole summary instead (each sheet's used range and first rows, and its formulas, [studio](studio.md#script-documents)) and asks the model to check it. Reading the ready version is tried again while the database stays locked past SQLite's busy wait; at the deadline the result says the version is ready without its text.
4. **Failed.** A tool error with the run's error and the traceback's last lines, and the stop rule. A failure of the script itself, whose stored reason starts `Script error: `, asks for a fix rendered from the `artifact_id`; any other, such as a full disk or the embedder, asks for the same script to be rendered again and the user told if it fails the same way. The stop rule reads: "If this is your third failed run for this request, stop and tell the user what failed." Studio does not retry a failed script document, so the version stays failed and the fix is the next version.
5. **Not done in time.** A version still being made, behind other Studio work, comes back as a plain result starting `Queued artifact <id>, version <n>: <title>`, saying it appears in Studio when ready and must not be rendered again. A cancelled or deleted version is a tool error without the stop rule.

The script, not the file, is what a version keeps, so the next edit reads it with `surfsense_read_document`, changes it and renders it again. Another format, such as a PDF of a Word document, is a new document at v1.

## Previews

`previews_for()` ([`previews/`](../../surfsense_local/backend/modules/agent/previews/)) draws up to four pages or slides of a ready version as PNGs 1,000 pixels wide, at most 4,000 high, into the calling thread's `outputs/previews/<artifact id>-v<n>/`, with pypdfium2 under the process's one lock ([`shared/pdfium.py`](../../surfsense_local/backend/shared/pdfium.py)). It runs only when `opencode.json` declares image input for the model. A page that would come out under 100 pixels on a side is skipped and named in the reason. It is called after the version's files are read and the transaction committed, with the time the call has left. Each page drawn goes into the result as a JPEG made from its PNG ([`inline_images.py`](../../surfsense_local/backend/modules/agent/previews/inline_images.py)): flattened on white, scaled down to at most 750,000 pixels and 1,568 on the long side, at quality 80. Anthropic bills an image by its pixels, so an A4 page costs about 1,000 tokens rather than the PNG's 1,890, and at about 80 to 100 KB it is half the PNG's bytes. The encoding is deterministic, which the live harness relies on. The PNGs stay on disk for a closer look with `read`.

- **PDF:** the file's own pages.
- **Word and PowerPoint:** the app has no Office converter, so Electron prints the file. The API queues a request and waits up to 30 seconds, or what the call has left, and skips the preview below 3 seconds. Electron polls the routes below every 2 seconds, opens the frontend's snapshot page ([`docx-snapshot.html`](../../surfsense_local/frontend/docx-snapshot.html)) in a hidden window with the file's URL and format, lays it out with the in-app viewer's library for that format, docx-preview for Word or pptx-renderer for a deck, and prints pages 1 to 4 with `printToPDF`; pypdfium2 then draws that PDF. The pages show the file as the app's viewer lays it out, not as Microsoft Office does; a Word document's leave out headers and footers, which docx-preview places in a page box that print pagination replaces.
- **No Electron**, as in the Docker stack and the tests: the snapshot service counts Electron gone after 60 seconds without a poll, and a Word or PowerPoint version gets no pages and the reason.
- **Excel:** none; the result carries the workbook's summary.

### Source pages

`surfsense_source_pages` ([`tool_endpoint/source_pages.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/source_pages.py), [`previews/source_pages.py`](../../surfsense_local/backend/modules/agent/previews/source_pages.py)) draws a source's own pages so the agent can match a look it cannot take as a template, such as a PDF brand guide. It only reads the source's original file. A PDF's pages are drawn from the file with pypdfium2, and its page count is exact. A deck's slides are counted from its package and a slide it lacks is refused before printing; Electron prints the slides asked for, as it prints the agent's own decks. A Word file is printed the same way; its count is the one Word saved in the file when there is one, exact when the print comes up short of the pages asked for, else "at least" the last page drawn. A print that comes back with another number of pages than asked for draws none, rather than label a page as another. Each page drawn comes back with the result as a JPEG made as a render's previews are, and its PNG, at most 1,000 pixels on its long side, stays under `sources/pages/`.

The snapshot routes, mounted only beside an opencode ([`previews/router.py`](../../surfsense_local/backend/modules/agent/previews/router.py)):

| Method | Path | Does |
|---|---|---|
| `GET` | `/agent/previews/docx-snapshots/next` | takes the oldest waiting request as `{id, file_url, format, pages}`: `file_url` is the artifact's `files/primary` URL, or for a source the request's own `file` route; `format` is `docx` or `pptx`; `pages` is `printToPDF`'s page ranges, `1-4` for a version's previews; `204` when none |
| `GET` | `/agent/previews/docx-snapshots/{request_id}/file` | the source's original file a taken request prints, until it is answered; `404` otherwise |
| `POST` | `/agent/previews/docx-snapshots/{request_id}/pdf` | the printed PDF; `413` over 50 MB, `422` for a body that is not a PDF, `404` when no one waits for it |
| `POST` | `/agent/previews/docx-snapshots/{request_id}/failure` | why it could not be printed, at most 500 characters |

Each but `file` refuses a caller with an `Origin` header, and one without `Authorization: Bearer <key>`, the key Electron made at boot and passed to the API as `SURFSENSE_LOCAL_DOCX_SNAPSHOT_KEY` ([`snapshot_key.py`](../../surfsense_local/backend/modules/agent/previews/snapshot_key.py)), because any process on the machine can reach loopback. The `file` route is fetched by the print window itself, which sends an Origin and holds no key, as it fetches an artifact's file: the request id, a random 128-bit value only the key's holder is handed, lets it in, and only while that request is being printed.

Electron's side ([`docx-snapshot/`](../../surfsense_local/electron/src/main/docx-snapshot/)) takes the next request at once after taking one, prints up to three at a time, gives each print 25 seconds, under the API's 30, and each call to the API 10. A request names its format, `docx` or `pptx`, and its pages as `printToPDF` page ranges; one without them is a Word file's pages 1 to 4, and a format or range it cannot print is reported as the request's failure without printing. A PDF the API refuses is reported as the request's failure. The page lays a Word file out as above, and a deck with @aiden0z/pptx-renderer, the in-app viewer's library: every slide on a page of the deck's own slide size, read from the file, printed with no margin, once each slide's pictures, backgrounds and charts are drawn ([`features/docx-snapshot/`](../../surfsense_local/frontend/src/features/docx-snapshot/)). The document is untrusted, since a source can steer the script that wrote it, so the hidden window runs sandboxed with no preload, in its own in-memory session whose requests may reach only the page's own files and object URLs and the one file being printed, and it never navigates. The page's policy allows only its own script, inline styles, data-URL and object-URL images, data-URL fonts, and connections to loopback; docx-preview renders no altChunk, whose HTML it would put in an unsandboxed frame, and the deck renderer gets no pdf.js, which would start a worker. A page whose script did not start is reported as such, with the window's first console error.

## A turn

The thread routes in [chat](chat.md#agent-threads) hand an agent thread to `agent_threads/`:

1. The turn's sources are stored and resolved ([the ticked sources](#the-ticked-sources)) and opencode is made ready. A legacy thread is then refused ([folders](#folders)), and so is a model that cannot run the agent. The thread's folder is brought in line, and the tools are added to the thread's opencode instance at the thread's address.
2. The thread folder's event stream is opened before the message is sent, so no event of the turn is missed. The message goes with `prompt_async`, naming the selected model, so a thread keeps working after a model change, and with the scope note beside it unless the thread's scope is every source.
3. Events for the thread's session become the chat's frames, plus `agent-step`, `permission-request` and `permission-replied` ([`turn_frames.py`](../../surfsense_local/backend/modules/agent/agent_threads/turn_frames.py)). A completed `surfsense_render_document` step carries `artifact: {id, title, version, created}`, read from its result's first line, which only a ready version gets; it is null while the call runs and when the script failed ([`steps.py`](../../surfsense_local/backend/modules/agent/agent_threads/steps.py)). A version not ready in time has none in the turn's frames; reading the thread back fills it from the result's `Queued artifact` line once that version is ready ([`ready_renders.py`](../../surfsense_local/backend/modules/agent/agent_threads/ready_renders.py)). `created` is true when no earlier version of the same root has made its file, so a document whose v1 failed is "Created" at v2; it is looked up in the database for the stream and on read-back, and a step sent while the database is locked goes without it and gets it on read-back. The screen then reads "Created *Title* v1" or "Updated *Title* to v2", whatever the format, and a click opens that version in Studio. A step carries no attachment: the page images opencode keeps on a render's or a source-pages step never reach the thread, live or read back. A `surfsense_source_pages` step reads "Looked at pages of *Title*", the title taken from the turn's scope, else, for a turn on every source or past 200, from the first line of the step's result, or "Looked at pages of a source" while the step runs. Text parts of one turn on either side of a tool call are kept as separate paragraphs, live and stored.
4. A stream silent for 20 seconds, twice opencode's heartbeat, is reopened, and so is one that drops; after a reopen, an idle session ends the turn. Twenty failures in a row end it with an error.
5. On `session.idle`, `completed` carries the reply as opencode stored it: the text of every assistant message opencode wrote for this turn, joined. A label one of the session's searches returned becomes `[citation:<chunk id>]` through the chat's own `resolve_citations()`, and any other bracketed number is dropped ([`citations.py`](../../surfsense_local/backend/modules/agent/agent_threads/citations.py)). A `citations` frame comes first when the reply cites anything.
6. When the client hangs up before that, the session's turn is aborted.

**Compaction.** When the window fills, opencode compacts the session mid-turn: a user message holding a compaction part, a summary it writes for itself, then a user message that carries the turn on. [`compaction.py`](../../surfsense_local/backend/modules/agent/agent_threads/compaction.py) tells them apart, so they fold into the turn they happened in: the summary is never streamed as the reply nor joined into the stored one, and the carrying-on message opens no new turn when the thread is read back. opencode's `ContextOverflowError` is not shown, since opencode compacts and carries on from it. A summary that fails ends the turn with one error frame, and one that failed because even the summary was too long says "The conversation is too long to continue here; start a new thread."

## The ticked sources

The chat panel sends the sources ticked in the sources panel with every message, and they bound an agent turn as they bound a chat's retrieval, resolved the same way in one transaction ([`turn_sources.py`](../../surfsense_local/backend/modules/agent/agent_threads/turn_sources.py)): a sent `source_scope` is stored on the thread; with none, `document_ids` is checked as a chat checks it (`load_selected_sources`, `422` for a source not in the workspace, `409` for one not ready) and stored as `{document_ids}`; with neither, the thread's stored scope holds, and a thread that never stored one uses every source. The scope resolves to its ready sources, with no cap, so a ticked folder of any size is the whole turn; every source means the workspace's files and notes and its filed artifacts, never an unfiled one ([source scope](chat.md#source-scope)). An empty result is no sources.

- **The folder holds it.** The thread's `sources/` is brought in line with the resolved sources before the turn, so `read`, `grep` and `glob` reach no other source ([folders](#folders)). A Studio artifact filed in a ticked folder is mirrored like any source.
- **The model is told.** Unless the stored scope is every source, the message goes to opencode with a second text part marked `synthetic`, which opencode 1.18.34 accepts on `prompt_async`, keeps as not the user's, and passes to the model inside the user's message ([`scope_note.py`](../../surfsense_local/backend/modules/agent/agent_threads/scope_note.py)). Its first line is SurfSense's tag, `[surfsense-scope: 3,7]`, past 200 sources `[surfsense-scope: count=N]`, or `[surfsense-scope: none]`; the rest says the user chose N sources for this chat, that they are the files in `sources/`, to use only those, and that passages read earlier from other sources no longer apply, or that no sources are selected, or, when every ticked source is still being read, that none is ready yet. It names no file. It lives in the session, so a compaction keeps it, and each turn carries the ticks of the moment it was sent.
- **The tools hold to it.** Each thread registers the tools at its own address, and a tool call resolves the thread's stored scope in one short transaction ([`turn_scope.py`](../../surfsense_local/backend/modules/agent/tool_endpoint/turn_scope.py)), so ticks stored between turns hold the next call. `surfsense_search_sources` searches only those sources, and with none says so instead; `surfsense_list_images`, `surfsense_source_pages` and `surfsense_create_artifact` refuse a source outside them, naming at most 20 of the sources that are in it and then "and N more: the files in `sources/`"; `surfsense_render_document` refuses an image or a template from one, including the template a next version would keep from its base. An address naming no agent thread of the workspace is refused rather than widened. Artifacts the agent rendered are its outputs, so `surfsense_read_document` needs no scope, nor does a render that continues one, beyond its template.
- **The thread shows it.** Reading the thread back takes the note out of the user's text and returns `content.scope`: `{document_ids, titles}`, keeping the sources that still exist, or for a counted tag `{document_ids: [], titles: [], count}`. Under the user's message the screen shows "Working from Plan.pdf", up to three names inline, else "Working from 5 sources" with the names on hover, "Working from 5,000 sources" with nothing on hover for a counted tag, or "Working from no sources": live from the `agent-scope` frame the stream opens with, which carries the same shape, and on read-back from the stored scope ([`working-from.tsx`](../../surfsense_local/frontend/src/features/agent/working-from.tsx)). A turn on every source, and every chat thread, shows none.

## Approvals

The agent has no shell, so it asks for no command. opencode still asks for a permission left at its default, such as `doom_loop` when the same tool call with the same input comes a third time in a row. The request reaches the thread as `permission-request`. The screen shows the oldest waiting one in an alert dialog, with Deny and Allow once, and Esc answering Deny. The answer goes to `POST /chat/threads/{thread_id}/permissions/{request_id}`, which passes `once` or `reject` to opencode. SurfSense never answers `always`. opencode rejects every other request waiting in the same session when one is rejected, and the dialog says so when others wait.

## Network

opencode needs no host beyond loopback: its model is the model endpoint, and its tools are its own and SurfSense's, on the API's port. Its environment is built from a few system variables rather than inherited. It sets `OPENCODE_DISABLE_MODELS_FETCH`, `OPENCODE_DISABLE_SHARE`, `OPENCODE_DISABLE_LSP_DOWNLOAD`, `OPENCODE_DISABLE_AUTOUPDATE`, `OPENCODE_DISABLE_DEFAULT_PLUGINS`, `OPENCODE_PURE`, `OPENCODE_DISABLE_PROJECT_CONFIG`, `OPENCODE_DISABLE_EXTERNAL_SKILLS` and `OPENCODE_DISABLE_CLAUDE_CODE`. Its proxy variables point at `127.0.0.1:9`, where nothing listens, with loopback exempted, so a fetch this misses fails rather than leaving the machine. The npm install opencode would otherwise run at startup is skipped: its config folder holds an empty `node_modules` and a lockfile naming the package. ripgrep is the shipped one, first on its `PATH`. Settings › Network gains nothing: opencode is never a destination, and a remote model's host is checked as its connection's.

A document script is another matter: it runs in the Studio worker's runner, which gives it an environment of a few system variables and no secrets but does not stop it opening connections ([ADR 0039](../adr/0039-document-scripts-run-without-approval.md), [studio](studio.md#script-documents)).

## Known gaps

- No model is on the tested list, and no agent test exists to put one there; only the developer switch lets a model in.
- A turn refused because the selected model cannot run the agent shows as an error with Retry; the composer does not offer a new thread, as the [proposal](../proposals/agent/01-which-engine.md#when-a-thread-gets-its-engine) has it.
- The model endpoint neither simplifies tool schemas to what llama.cpp's grammar takes nor turns a tool call a model writes as text into a real one, so small local models stall where a remote one would not.
- A file the agent writes to `outputs/` with its own tools does not become an artifact; only `surfsense_render_document` makes one.
- A Studio job the agent starts with `surfsense_create_artifact` runs on the same local model as the agent, so the agent's next step waits behind it.
- An artifact the agent starts or renders records neither the thread nor the step that made it: the tool call reaches SurfSense without either.
- A thread's folder narrows what its agent can reach to its own sources, but does not close it. Through two holes in opencode, each below, an agent can still read what is outside its folder: a git repository above the data folder opens every thread's folder, and opencode's tool-output folder is shared by all; closing either needs a change in opencode. Through SurfSense's own tools it can too: a script `surfsense_render_document` runs can read any file the user can ([Studio](studio.md#known-gaps)), and the text the render returns shows what it put in the document, another thread's sources included; and `surfsense_read_document` reads any document the agent rendered in the workspace, from any thread and filed in an unticked folder too, and such a script can hold what that thread's agent took from its own sources.
- After the ticks change mid-turn through `PUT /source-scope`, the tools follow the new ones at once but the folder only at the next turn; the app sends ticks with each message, never mid-turn.
- A folder renamed or moved renames its sources' files between turns; the agent finds them again with `glob`.
- Each thread used in a run keeps its opencode instance until the thread is deleted or opencode restarts: about 30 MB of opencode's memory each after a turn with SurfSense's tools, measured on 1.18.34 (`test_thread_isolation.py`), and deleting the thread did not give it back to the system right away. No cap disposes idle instances.
- A passage's label is its chunk id, a number of several digits, which a small local model copies less reliably than a chat answer's `[1]` to `[5]`. A mistyped label is dropped, so the citation is lost rather than wrong. Nothing has measured how many are lost.
- A bracketed number the agent writes that no search returned is dropped from the stored reply but not from the streamed one, so the two differ. In a live run Claude cited files it had read without searching by the `[n]` at the end of their names, as labels, and the saved reply lost them.
- Bringing a thread's `sources/` in line reads the text of every source in its scope before each turn, to hash it: at 3,000 sources of 40 KB, 0.8 s a turn once synced, 2.8 s for a second thread linking them, and 13 s the first time, writing the cache (`test_thread_folders.py`, Windows with Defender on). The first `grep` over a newly written cache pays Defender's scan of each file once per machine.
- On a disk without hard links each thread holds its own copy of each text, and pays Defender's scan again.
- A configuration rewrite, which a change of model, window or image input causes, ends every running agent turn in every workspace.
- Opening the first agent thread waits for opencode to start and for a local model to load, up to a minute, with nothing on screen but the thread being created.
- When SurfSense's data folder sits inside a git repository, such as a home folder kept in git, opencode counts the repository's root as its project, not the thread's folder. Then every thread's agent can read, `grep` and `glob` every other thread's folder, including sources not ticked for it, and every other workspace's, without asking. Nothing detects it.
- No test runs opencode with every connection beyond loopback refused to check that it opens none.
- No signed installer has carried opencode: a notarized build on macOS and a signed build under Defender on Windows are untried. It adds about 180 MB unpacked.
- opencode's tool-output folder is shared by every thread in every workspace and open to each one's agent: a tool result over 50 KB or 2,000 lines is kept there for 7 days (SurfSense's own tools stay under that limit; `surfsense_read_document` pages long scripts), and another thread's agent, in the same workspace or another, can list and read it without asking. Per-thread folders do not change this.
- On macOS and Linux, opencode checks an absolute path as written, so its own allow for its tool-output folder also matches a path that climbs out of it with `..`. The skills folder's allow has a `..` deny after it; the tool-output folder's cannot, since opencode adds that allow after SurfSense's rules. Windows normalises the path first.
- Every page image the agent is shown, each render's previews and each page it opens, stays in its context until a compaction, and Anthropic's OpenAI-compatible API reports no prompt caching, so each request bills them again: about 1,000 tokens a page a request. Nothing drops the images of a version a newer one superseded. Anthropic caps the images in one request, so about 25 four-page renders in one uncompacted thread could reach it.
- opencode's compaction estimates base64 as text, so one inline page is over its 15,000-token budget for the recent turns it keeps: a turn holding a page image is always summarised, never kept as it was.
- A thread whose model changes to one that reads no images sends opencode's "Cannot read image" error in place of every stored image on every later request.
- opencode's stored messages carry every attachment, about 0.35 MB a four-page render, and the API reads them all at every turn's end and when a thread opens.
- claude-sonnet-5-5's window is the 1,000,000 tokens the catalog records, not confirmed against Anthropic's OpenAI-compatible endpoint. No live run has come near it; if the real window is smaller, a request fails on it before compaction starts.
- Word previews leave out headers and footers, and lay a document out as docx-preview does, which can differ from Word. The agent is told the first. Slide previews are pptx-renderer's, which can differ from PowerPoint; the agent is told so.
- A Word source's page count is known only when Word saved one in the file or a print comes up short; a page asked for past the end fails as Electron's print does.
- A next version keeps its template; to drop it, the agent starts a new document.
- The Word preview path through a real Electron window has no automated test; it was checked by hand, and the live tests print Word with LibreOffice behind the same routes.
- A fourth Word snapshot requested while three print waits for a free print, and the API's 30 seconds start when the request is queued, so it can time out before Electron answers.
