# Plugins

A plugin is a remote MCP server whose tools the agent can use. The user connects one of SurfSense's own plugins from the list packaged into the app, a verified or community plugin from the signed [registry](plugin-registry.md), or any server by its URL, in Settings → Plugins, signs in with a key, the license or an account, chooses which of its tools the agent may use and which ask first, and the agent's opencode calls the server itself, under rules SurfSense writes each turn ([agent](agent.md#plugins)). Plugins in Basic threads, and what else is not built, are the [proposal](../proposals/plugins/README.md).

**Code:** [`surfsense_local/backend/modules/plugins/`](../../surfsense_local/backend/modules/plugins/), [`surfsense_local/frontend/src/features/plugins/`](../../surfsense_local/frontend/src/features/plugins/)
**Decisions:** [ADR 0051](../adr/0051-plugins-are-mcp-servers-behind-one-tool-gateway.md), [ADR 0053](../adr/0053-plugins-are-listed-in-a-registry-and-third-party-ones-start-off.md)

## SurfSense's own plugins

[`lists/first_party/plugins.json`](../../surfsense_local/backend/modules/plugins/lists/first_party/plugins.json) lists them, packaged into the API with their icons in `icons/` beside it (`bundling/api.spec`), so `GET /plugins/first-party` answers with no network or consent. Each entry names its icon in `icon`, by file name, and the tools its server offers in `tools`, which its page shows before it is connected and the plugin host's tests check against each server ([plugin host](plugin-host.md#tests)); Web Crawl's is the web app's `web.svg`, and Google Maps' its flat vector pin, since the web app's file embeds a 4 MB raster. It holds SurfSense's scraper plugins, one per platform: Google Search, Web Crawl, YouTube, TikTok, Google Maps, Amazon, Walmart and Indeed. Reddit and Instagram are written but left out until they can read anonymously again ([plugin host](plugin-host.md#known-gaps)). Each is its own server at `https://plugins.surfsense.com/<id>/mcp`, served by the [plugin host](plugin-host.md), so the user connects, pauses and mentions each apart, and one consent for `plugins.surfsense.com` covers them all.

- **The check.** Every entry follows the schema both lists share ([`list_entry.py`](../../surfsense_local/backend/modules/plugins/lists/list_entry.py)): its id, an `https` URL with no credentials, `hosts` naming the URL's host and no loopback, and an `access_note` when `access` is `external`. A first-party entry carries no `verification`, its `icon`, when it names one, is a plain file name present in `icons/`, it has an `about` of up to 600 characters, it lists its `tools`, each an MCP tool name once, and the month it was `added` as `YYYY-MM`, and one with `auth: license` sits on `https://plugins.surfsense.com` ([`first_party_list.py`](../../surfsense_local/backend/modules/plugins/lists/first_party/first_party_list.py)). A bad entry fails naming its field, and a unit test checks the packaged list, so it fails CI.
- **Connecting.** `POST /plugins/first-party/{id}`: an id not listed is `404`; one connected already, or whose URL is, is `409 plugin_already_connected`; a host not allowed is `403 egress_disabled`, as below. The server's tools are listed with the license, and the plugin is stored with `source: first_party` and `credential_kind: license`. A `401` or `403` still connects it, its check saying why, since a missing license is the server's to report; any other failure is `502 plugin_unreachable`.
- **The license.** Every request to a license plugin's server carries `Authorization: License <key>`, the key read from the imported license each time and never stored on the plugin ([`plugin_headers.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/plugin_headers.py), [`license_key.py`](../../surfsense_local/backend/modules/license/license_key.py)). Its expiry is not checked here: the server decides. The key goes only to a URL on the plugin host this build reaches; a plugin connected elsewhere is sent no key.
- **In an agent turn.** opencode is given each plugin on the plugin host with `x-surfsense-text-only: 1`, which asks the host to put a call's items in the text alone, since opencode reads only the text when there is any, and no other server is sent it ([`turn_plugins.py`](../../surfsense_local/backend/modules/agent/plugin_tools/turn_plugins.py)). A call to one may go 300 seconds without progress, against 200 for every other server; when opencode gives up on one, its `MCP error -32001`, the app ends the thread's calls on the host through `POST /cancel`, as Stop does, since opencode's own cancel cannot reach a host that keeps no session; the host ends every call of the thread at once, so the cancel waits until no other call of the turn runs there ([`stop_plugin_calls.py`](../../surfsense_local/backend/modules/agent/plugin_tools/stop_plugin_calls.py), [agent](agent.md#plugins)).
- **A developer's plugin host.** `SURFSENSE_LOCAL_PLUGIN_HOST_URL`, such as `http://127.0.0.1:8000`, moves every listed URL and host on `plugins.surfsense.com` to a plugin host run locally ([`plugin_host.py`](../../surfsense_local/backend/modules/plugins/lists/plugin_host.py)), and the license key with them.
- A custom plugin never takes a first-party id: one named Amazon is `amazon-plugin`.

## Third-party plugins

`GET /plugins/registry` lists the [registry](plugin-registry.md#in-the-app)'s entries, fetched at most every five minutes and only while third-party plugins are allowed; while they are off it answers `third_party_off: true` and fetches nothing ([`routes.py`](../../surfsense_local/backend/modules/plugins/lists/registry/routes.py), [`registry_read.py`](../../surfsense_local/backend/modules/plugins/lists/registry/registry_read.py)). Each entry carries its name, description, author, `verification` and `verified` for a plugin proven to be run by its author, `server_host`, the host every call goes to, and `sign_in_hosts`, an OAuth plugin's other hosts, `access` and `access_note`, `auth_type` with a token entry's `auth_title` and `auth_description`, `hosts`, `homepage`, `privacy_policy`, `about`, `tools` (null when the entry lists none), `added`, `has_icon` and `connected`; the answer carries `fetched_at` and `removed`.

- **Connecting.** `POST /plugins/registry/{id}`, with `{token}` for a `token` entry, `{headers}` with a value for each header a `headers` entry names, or `{oauth_client}` for an `oauth` entry with `user_client`, which without it is kept signed out needing the user's own app, `201`, sending nothing to the provider ([below](#signing-in-with-oauth)): third-party plugins off is `403 third_party_off`; an id not listed is `404`; one connected already, or whose URL is, is `409 plugin_already_connected`; any of the entry's hosts not allowed is `403 egress_disabled` naming them all. An `oauth` entry then starts a sign-in, `202` ([below](#signing-in-with-oauth)). Any other lists the server's tools over the entry's `transport`, with the key as `Authorization: Bearer`, or each named header's value after its entry's `prefix`, a header the entry does not name being `422 plugin_header_not_allowed` ([`entry_headers.py`](../../surfsense_local/backend/modules/plugins/lists/registry/entry_headers.py)), refused as a server added by URL is, and is stored with `source: registry`, its publisher and entry, and a key as `credential_kind: token` or headers as `credential_kind: headers`. Editing a registry plugin's headers fills the same named headers and keeps its entry ([`registry_plugin.py`](../../surfsense_local/backend/modules/plugins/installed/registry_plugin.py)).
- **Removed.** A maintainer moves an entry to `removed`, often after a report through the [Report a plugin](../../.github/ISSUE_TEMPLATE/plugin-report.yml) issue form. A plugin connected from the registry whose id is in `removed` keeps its row and key, but `list_tools()` leaves it out, and its row carries `removed_reason`. A custom plugin with the same id is untouched.
- A custom plugin never takes a registry id, a removed one included ([`custom_plugin.py`](../../surfsense_local/backend/modules/plugins/installed/custom_plugin.py)).

## Connecting a server

`POST /plugins/custom` with `{url, name, headers?, token?}`, in this order:

1. `headers`, a list of `{name, value}`, are checked before anything else ([`header_rules.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/headers/header_rules.py)): at most 10, each name an HTTP token of at most 64 characters, given once whatever its case, and none the transport sets (`Host`, `Content-Length`, `Content-Type`, `Accept`, `Connection`, `Transfer-Encoding`, `Cookie`, `Mcp-Session-Id`, `MCP-Protocol-Version`, `Last-Event-ID`); each value non-empty, at most 4 KB, with no line break. A refusal is `422 plugin_header_not_allowed`, naming the header, never its value. A bare `token` is one header, `Authorization: Bearer <token>`.
2. The URL is put in one spelling: scheme and host lowercased, no default port, trailing slash or fragment ([`server_url.py`](../../surfsense_local/backend/modules/plugins/installed/server_url.py)), so one server is never connected twice.
3. A name already in use is `409 plugin_name_taken`, and a server already connected is `409 plugin_already_connected`, each with `name`. A name becomes the id, lowercase words joined by hyphens; `surfsense` is never one, since it is the agent's own server.
4. A server off this computer not on HTTPS is `422 plugin_needs_https`: the agent reaches remote servers only through a TLS tunnel ([agent](agent.md#network)).
5. A host not allowed is `403 egress_disabled` with `hosts` and `purpose: "plugin"`, so the prompt words its question for a plugin's server, and the host is recorded off for Settings › Network ([egress](egress.md)).
6. SurfSense lists the server's tools with the official MCP SDK's client, sending the headers, over Streamable HTTP, then over the older HTTP+SSE when the POST is refused with `400`, `404` or `405`, as the spec's backward compatibility says ([`either_transport.py`](../../surfsense_local/backend/modules/plugins/remote/either_transport.py)); the transport that answered is recorded on the entry, `transport: streamable_http` or `sse`. A `401` to a request with no headers, from a server that asks for OAuth, starts a sign-in instead, `202` ([below](#signing-in-with-oauth)), as the user's own app when `oauth_client` is given. Every failure is then one outcome, the same for every connect path, with none of the server's own text ([`connect_refusal.py`](../../surfsense_local/backend/modules/plugins/remote/connect_refusal.py)): any other `401` or `403` is `422 plugin_needs_sign_in`; a `410` is `422 plugin_gone`, an address its server retired, as DeepWiki did its `/sse` for `/mcp`; another `4xx`, or an answer that is not MCP, such as a web page, is `422 plugin_not_mcp`; a network failure, a timeout or a `5xx` is `502 plugin_unreachable`. When neither transport answers, an SSE address that answered anything but `400`, `404` or `405` exists, so its answer is the one judged: a key it asks for, an address retired, a server down. Otherwise the Streamable HTTP refusal is. A refusal's HTTP status wins over a JSON-RPC error in its body, so a `401` carrying one still asks for a key.
7. The plugin is stored with its headers, names and values together, encrypted as one credential, `credential_kind: headers` (`shared/secrets.py`, [`headers_credential.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/headers/headers_credential.py)); the names alone are also kept in its entry's `auth`, so they survive disconnecting. Every tool it listed starts on.

## The MCP client

SurfSense lists a server's tools itself, to connect it and to notice tools that change; it never calls one, which the agent's runtime does, through the gateway ([agent](agent.md#the-gateway)) ([`mcp_client/session.py`](../../surfsense_local/backend/modules/plugins/remote/mcp_client/session.py)). It speaks Streamable HTTP, and the older HTTP+SSE for a plugin whose entry records `transport: sse`, through the official MCP SDK, pinned to `mcp` 2.3.x ([`transports.py`](../../surfsense_local/backend/modules/plugins/remote/mcp_client/transports.py)); the SDK refuses an SSE `endpoint` event on another origin. A server started by a command cannot be connected.

- Each listing opens its own connection and closes it, since the SDK's tasks must close where they opened; nothing stays open between listings.
- `tools/list` is followed page by page through its cursor.
- A network error, `408`, `429` or `5xx` is retried twice, 0.2 and 0.4 seconds apart ([`retries.py`](../../surfsense_local/backend/modules/plugins/remote/mcp_client/retries.py)). A server that forgot the session is listed once more on a new one.
- A refusal keeps its HTTP status, an SSE stream's refused `GET` included, and the `reason` in its body, which is how a license refusal reaches the [checks](#checks), and a `403`'s `insufficient_scope` challenge keeps the scopes it names ([`scope_challenge.py`](../../surfsense_local/backend/modules/plugins/remote/mcp_client/scope_challenge.py)).

## Signing in with OAuth

A registry entry with `auth: oauth`, or a server added by URL that asks for it, signs in with the user's account in their browser ([`plugin_sign_ins.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/plugin_sign_ins.py)). The plugin is stored once the sign-in's page is ready, signed out (`check_failure: sign_in`) with no tools and no token ([`awaiting_sign_in.py`](../../surfsense_local/backend/modules/plugins/installed/awaiting_sign_in.py)), so a sign-in declined, abandoned or cancelled leaves it in Yours, needing a sign-in; the sign-in finishing fills in that row. It is never stored earlier, since a host still to be allowed retries the same request.

1. **Discovery.** The server's `401` names its protected resource metadata (RFC 9728), whose first authorization server is the one used; a server with none but `/.well-known/oauth-authorization-server` on its origin is its own ([`oauth_discovery.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/oauth_discovery.py)). A refusal that names neither is not OAuth.
2. **Consent.** The authorization server's host is asked about before any request reaches it: `403 egress_disabled` with `purpose: "plugin"`. Every request of the sign-in goes through a client that refuses a host not allowed before it leaves ([`consented_client.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/consented_client.py)), and the host joins the plugin's `hosts`, so readiness and the plugin proxy require it too.
3. **The page.** The MCP SDK's OAuth client runs registration, PKCE and the code exchange ([`sign_in_flow.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/sign_in_flow.py)). The connect route answers `202` with `{id, plugin_id, authorization_url}` once the URL is ready, within 60 seconds, or `502 plugin_sign_in_failed` ([`start_sign_in.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/start_sign_in.py)). The screen opens it in the browser and polls `GET /plugins/sign-ins/{id}`, `waiting`, `connected` or `failed` with a sentence; `DELETE` abandons it. A sign-in lives ten minutes in the API's memory, so a restart ends it, and a new one for the same plugin cancels the earlier.
4. **The way back.** The `state` sent is `<port>.<nonce>`, the API's port and the SDK's own state ([`sign_in_state.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/sign_in_state.py)). `GET /plugins/oauth/callback` answers only a state this API issued; a provider's `error` ends the sign-in, `access_denied` as declined. The tools are then listed with the new token, on Streamable HTTP or the older SSE as adding a server lists them, the transport that answered recorded, the plugin stored, and the browser's page says it is signed in or why not ([`callback_page.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/callback_page.py)).

**Who SurfSense signs in as** ([`sign_in_client.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/sign_in_client.py)). A packaged app is one public client, `https://plugins.surfsense.com/oauth/client.json`, a client ID metadata document whose redirect is the plugin host's callback page, which forwards the browser to the API's port ([plugin registry](plugin-registry.md#oauth-files)); a server that does not take such documents gets dynamic registration with the same redirect. A server whose registration refuses a public client, as those listing only `client_secret_*` token methods do, is registered once more as a confidential client, `client_secret_post`, its secret issued to this install by that registration and kept in the credential ([`start_sign_in.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/start_sign_in.py)). An unpackaged API, or one with `SURFSENSE_LOCAL_PLUGIN_HOST_URL`, registers dynamically with its own `http://127.0.0.1:<port>/plugins/oauth/callback` (RFC 8252). An entry's `auth.client_id` is used as a client registered in advance, and its `auth.scopes` are asked for. No client secret ships.

**The user's own app** ([`own_app.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/own_app.py)). Before registering, the authorization server's metadata is read ([`registration_offer.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/registration_offer.py)): a provider publishing one with neither a `registration_endpoint` nor, for a packaged build, client ID metadata documents registers no app, GitHub's among them, and needs the user's own app at once, with no registration sent only to fail. A provider publishing none is tried, as the spec has a client guess `/register`. A registration that fails is read the same way: with a `registration_endpoint`, the provider refused SurfSense, since it may take only apps it approved; otherwise it registers no one. Either way the plugin is kept, a new one stored signed out and a saved one marked, its entry's `auth.needs_own_app` saying which, `needs_client` or `refused` ([`own_app_needed.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/own_app_needed.py)): adding answers `201` with it, and signing in again answers `422 plugin_oauth_needs_client` or `plugin_oauth_refused`. A sign-in that finishes clears it. Each refusal SurfSense handles is logged as one line of its own, not as the SDK's error with a traceback ([`handled_refusals.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/handled_refusals.py)). Each carries the `redirect_uri` this build signs in with, also at `GET /plugins/oauth/redirect-uri`. The user registers an app with the provider and gives `oauth_client: {client_id, client_secret?, scopes?}` to the custom route, a registry connect, or a sign-in again. It is used as a client registered in advance, sending its secret with `client_secret_post`; the id and scopes go on the entry's `auth`, marked `own_app`, so it is told from a registry entry's own `client_id`, the secret only into the credential, so a refresh and a sign-in again reuse it. A registry entry with `auth.user_client: true` is kept needing it, `needs_client`, before anything is sent.

**The credential.** The tokens, their expiry, the client signed in as, the token endpoint and the resource indicator are one encrypted JSON blob in the row's credential, `credential_kind: oauth` ([`oauth_credential.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/oauth_credential.py)). Only the access token leaves the app, as `Authorization: Bearer` ([`plugin_headers.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/plugin_headers.py)); none is logged or returned.

**Refreshing** ([`token_refresh.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/token_refresh.py)), one at a time per plugin, since providers rotate refresh tokens. Before an agent turn, a token that expires within 30 minutes ([agent](agent.md#plugins)); and a listing the server refuses with `401`, at a check or Refresh tools, is refreshed once and listed again ([`listed_after_refresh.py`](../../surfsense_local/backend/modules/plugins/remote/sign_in/oauth/listed_after_refresh.py)). A refused refresh, or none possible, records `check_failure: sign_in`, and an OAuth plugin so marked is not ready. A token endpoint that cannot be reached, or whose host is off, leaves the sign-in as it was.

**Signing in again.** `POST /plugins/{id}/sign-in` signs the same row in again, so its tool settings stay, reusing the client an earlier sign-in registered when its redirect still matches, and the user's own app with its secret; `{oauth_client}` switches to another. A plugin that does not sign in with an account is `422 plugin_not_oauth`.

**More access.** A listing the server refuses with `403` and `error="insufficient_scope"`, or an agent's tool call the gateway sees refused so ([agent](agent.md#the-gateway)), records `check_failure: sign_in` and the scopes it named as the entry's `auth.needs_scopes`, which the screen reads as Needs more access; signing in again asks for them with the scopes asked before, and a sign-in that succeeds clears them.

## Ready tools

`list_tools()` in [`gateway/listing.py`](../../surfsense_local/backend/modules/plugins/gateway/listing.py) is the one answer to which tools may be used now: a tool switched on, of a plugin switched on and not disconnected, whose hosts are all allowed, not removed from the registry, not an OAuth plugin signed out, not a plugin whose license the plugin host refused, and, unless SurfSense publishes it, only while third-party plugins are allowed. `needs_approval()` in [`gateway/approval.py`](../../surfsense_local/backend/modules/plugins/gateway/approval.py) says which ask: a first-party read-only tool never does, a tool that does not say it is read-only and does not say it is harmless (`destructiveHint` absent or true) always does, and any other asks unless set to Always allow.

These two are the gateway today: it decides readiness and approval, and calls no tool. `list_tools()` returns `ReadyTool` records that name no engine ([`ready_tool.py`](../../surfsense_local/backend/modules/plugins/gateway/ready_tool.py)); the agent reads them each turn. Their `qualified_name`, `<plugin>__<tool>`, waits for the chat engine; opencode names a tool `<plugin>_<tool>` itself ([agent](agent.md#plugins)).

**Tools added later.** Each listing after the first is recorded by [`recorded_tools.py`](../../surfsense_local/backend/modules/plugins/installed/recorded_tools.py): a new tool starts off, a tool whose description changed or whose annotations became less safe is switched off, and a tool the server dropped is deleted. The agent lists again before a turn at most every five minutes, and in the background after a turn ([agent](agent.md#plugins)).

## Checks

Every listing of a server is a check, recorded on its row ([`plugin_check.py`](../../surfsense_local/backend/modules/plugins/installed/plugin_check.py)): connecting, the agent's listing before a turn when the last check is five minutes old, which the turn waits on for at most 3 seconds, a listing still running then being recorded when it ends, the agent's listing after a turn, in the background, when the last check is over 200 seconds old, so the next turn rarely waits ([`changed_tools.py`](../../surfsense_local/backend/modules/agent/plugin_tools/changed_tools.py), [agent](agent.md#plugins)), and **Refresh tools**. The agent's checks list a plugin one at a time: a turn waits on a check of the agent's already running rather than starting another. Only ready plugins are listed, so a host the user has not allowed is never contacted. One that answers records its tools; one that fails keeps the tools last recorded and says why: a `401` or `403` as `sign_in`, unless its body's `reason` is one of [contract 2](../contracts/02-scraper-api-auth.md)'s, `missing_license`, `expired`, `revoked` or `invalid`, which become the license failures; anything else is `unreachable`. An OAuth plugin's `401` is refreshed and listed once more first ([above](#signing-in-with-oauth)). A server whose recorded transport answers `400`, `404` or `405` is tried on the other, since servers move from SSE to Streamable HTTP; one that answers there is recorded with its new `transport` ([`transport_moved.py`](../../surfsense_local/backend/modules/plugins/remote/transport_moved.py)).

A tool switched off by a check, because it is new or its description or annotations changed, is marked `added` or `changed`. Switching it on clears the mark: the user has allowed it as it now reads.


## The license verdict

Whether the license unlocks SurfSense's paid plugins is the plugin host's to say, never the app's: the imported license file is only a hint of when to ask ([`license_verdict/`](../../surfsense_local/backend/modules/plugins/license_verdict/)). `POST /plugins/license/check` asks `GET /license` on the plugin host once, for every paid plugin connected, and applies the one answer to all of them: `missing_license`, `expired`, `revoked` or `invalid` become their license failure, and a valid license clears one. A host without `/license` is no answer, like one out of reach: it serves 2.2.1 and earlier apps, which learn the license from their listings, so it is deployed before an app that asks.

- **When it asks.** At once after a license is imported, replaced or removed (Settings › License calls it). With `if_stale`, on opening Settings › Plugins and before each agent turn: when no verdict came in the last five minutes, or the license file's expiry passed since the last one. The time is kept in memory, so a restart asks again.
- **What it never does.** No paid plugin, or `plugins.surfsense.com` switched off in Settings › Network, asks nothing. No answer, the host out of reach or `503 license_service_unavailable`, keeps every verdict as it was; so does any check that cannot reach the server, so a refused license is never turned back into a plugin that seems ready.
- **What it changes.** A plugin whose license is refused is not ready, so `@` and the agent leave it out, and it stays connected: the next verdict that says the license works brings it back, renewed on the server or imported again.
## What a plugin can reach

A plugin's server gets the arguments of the calls opencode makes to it, and nothing else of the user's: no plugin code runs in the app, nothing it returns reaches Sources unless the user saves it ([agent](agent.md#plugins)), and opencode's connections are tunnelled only to the hosts of a ready plugin ([agent](agent.md#network)). Against text in a source or a result steering the model, the defences are approval with the exact arguments, hosts the user consented to, a changed description switching its tool off, which hides it from the model, and third-party plugins off until allowed. None of this is a sandbox.

| `POST` | `/plugins/first-party/{id}` | Connects one, as above |
| `POST` | `/plugins/custom` | Connects a server by URL, as above; `202` with a sign-in for one that asks for OAuth |
| `GET` | `/plugins/registry` | The registry's plugins, each with `connected`, and the removed ones |
| `GET` | `/plugins/registry/icons/{id}` | An entry's verified icon, from the copy held |
| `POST` | `/plugins/registry/{id}` | Connects one, as above; `202` with a sign-in for an `oauth` entry |
| `GET` / `DELETE` | `/plugins/sign-ins/{id}` | A sign-in's progress; abandons it |
| `GET` | `/plugins/oauth/callback` | Where the browser comes back from the provider |
| `GET` | `/plugins/oauth/redirect-uri` | The callback a user registers their own OAuth app with, for this build |
| `POST` | `/plugins/{id}/sign-in` | Signs an OAuth plugin in again, keeping its tool settings; `{oauth_client}` as the user's own app |
| `PUT` | `/plugins/{id}` | `{enabled}`: off pauses a plugin, keeping its key and tool settings |
| `POST` | `/plugins/{id}/check` | Lists the server again and records the check |
| `PUT` | `/plugins/{id}/headers` | `{headers}`, checked as at connect: the server lists its tools with the new headers first, and only ones it accepts replace the old, recorded as a check; the tool settings stay. | `PUT` | `/plugins/{id}/key` | `{token}`: the server lists its tools with the new key first, and only a key it accepts replaces the old one, recorded as a check; the tool settings stay. A refusal is the same `422` or `502` as connecting |

| `GET` / `PUT` | `/plugins/third-party` | `{allowed}` |

Refresh tools on it is `409 plugin_disconnected` |

## Known gaps

- Only remote MCP servers, reached over HTTP. A local server started by a command, such as `npx` or `uvx`, cannot be added: local servers come with [bundles](../proposals/plugins/README.md#local-mcp-servers).
- A server on the older SSE transport only, behind OAuth, that refuses the POST with `405` and asks for a sign-in only on its stream cannot be signed in to: a sign-in starts from the POST's `401`. Of 13 providers probed on 20 Oct 2026, none does; Asana's, Atlassian's, Square's, Intercom's, PayPal's, Webflow's and Neon's `/sse` all answer the POST `401` and sign in.
- A server that reports missing access inside a tool's result, rather than as a `403 insufficient_scope`, is not seen as needing more access.
- A key in a custom plugin's URL is kept as typed, stored in the clear with the URL; nothing warns.
- OAuth sign-in has been tried only against a stand-in authorization server, never a live provider.
- The tests stand in for the callback page's forward to the API by calling the API's callback themselves; the deployed page is not exercised by any test.
- A failed sign-in reads "The sign-in didn’t finish" whatever the cause; the API's `message` saying why is not shown.
- A server added by URL whose authorization server is on another host raises a second consent prompt, for that host, after the one for the server's own.
- A removed plugin's reason shows only on its connected row; the Third-party list leaves removed entries out and does not show `removed`.
- A check runs at connect, before or after an agent turn, and on request, never on a timer, so a server that went down is seen only then.
- A tool whose server changed it and takes more than 3 seconds to list is offered as recorded, as with a server that cannot be listed, to every turn that starts before its listing ends, for the whole of each such turn, even once the late check has switched it off.
- No activity view: a plugin's recent calls are kept in each thread's opencode session, and the screen does not gather them yet.
- Plugins reach Agentic threads only; Basic threads get none until the chat engine's router step ([proposal](../proposals/plugins/README.md#the-chat-engines-router-step)).
- A server's `notifications/tools/list_changed` is not read; a changed tool is seen at the next check.
- Settings › Network lists a plugin's hosts without the plugin's name.
- No organisation policy can turn plugins off or hold third-party plugins off ([proposal](../proposals/plugins/README.md#organisation-policy)).
